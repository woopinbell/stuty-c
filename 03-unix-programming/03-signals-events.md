# 시그널과 비동기 이벤트 전달

유닉스 시그널은 커널이 프로세스에게 "지금 당장" 알려야 하는 사건(자식 프로세스 종료, 파이프 상대방 소멸, 타이머 만료, 사용자의 Ctrl-C)을 전달하는 수단이다. 문제는 이 전달이 프로그램 실행 흐름의 임의의 지점에서, 심지어 `malloc` 한복판이나 락을 쥔 채로 끼어든다는 점이다. 시그널 처리기(signal handler)는 보통의 함수 호출과 전혀 다른 규칙 아래에서 동작하며, 이 규칙을 무시하면 데드락이나 데이터 손상처럼 재현하기 어려운 버그로 이어진다. 이 문서는 시그널 처리기를 안전하게 작성하는 법, 그리고 시그널이 전달하는 "일이 일어났다"는 정보를 이벤트 루프가 다룰 수 있는 형태로 옮기는 self-pipe 기법을 다룬다.

## 시그널 처리기에서 할 일을 줄이기

시그널 처리기는 메인 실행 흐름을 언제든 가로챌 수 있기 때문에, 처리기가 실행되는 순간 프로그램의 나머지 부분이 어떤 상태였는지 전혀 알 수 없다. 힙이 정리되던 중일 수도 있고, 표준 라이브러리 내부 락이 걸려 있을 수도 있다. 이런 상황에서 처리기가 복잡한 일을 하면 그 자체로 위험하다.

그래서 원칙은 단순하다: 처리기 안에서는 "무언가 일어났다"는 사실만 최소한의 방법으로 기록하고 즉시 반환한다. 실제 처리(로그 기록, 자원 정리, 상태 갱신)는 처리기 밖(이벤트 루프의 정상적인 흐름 안)으로 미룬다.

```c
#include <signal.h>
#include <stdatomic.h>

static volatile sig_atomic_t g_got_sigterm = 0;

static void on_sigterm(int signo) {
    (void)signo;
    g_got_sigterm = 1;  // 플래그만 세운다. 여기서 로그를 찍거나 정리하지 않는다
}
```

`main` 루프는 이 플래그를 주기적으로, 혹은 self-pipe를 통해 깨어난 시점에 확인해서 실제 종료 절차를 수행한다. 처리기 자체는 몇 개의 명령어로 끝나야 한다.

## async-signal-safe

처리기 안에서 호출해도 안전한 함수는 극히 제한적이며, 이 목록을 "async-signal-safe 함수"라고 부른다. POSIX에서 이 목록을 명시적으로 정의하는 이유는, 시그널이 프로그램 실행 중 임의의 지점에서 끼어드는데 그 지점이 하필 같은 함수(혹은 같은 락)를 사용하던 중이면 처리기가 그 함수를 다시 호출했을 때 재진입 문제가 생기기 때문이다.

대표적으로 안전한 함수는 `write`, `read`, `_exit`, `signal`, `sigaction`, `kill`, `sigprocmask` 정도이고, 안전하지 않은 함수의 대표 사례는 다음과 같다.

- `malloc`/`free`, 그리고 이들을 내부에서 쓰는 거의 모든 함수: 힙 락을 이미 쥐고 있는 도중에 시그널이 들어오면 처리기가 다시 락을 잡으려다 데드락이 난다.
- `printf` 계열: 내부 버퍼와 락을 사용한다.
- `strtok`, `localtime`처럼 정적/전역 버퍼를 쓰는 함수: 재진입 시 데이터가 섞인다.

가장 흔한 실수는 디버깅하려고 처리기 안에 `printf`를 넣는 것이다. 평소에는 문제없이 동작하다가 하필 메인 흐름이 `printf` 내부 락을 쥔 순간 시그널이 들어오면 그 자리에서 멈춘다. 처리기 안에서 뭔가 출력해야 한다면 `write(2)`를 직접 써야 한다.

```c
static void on_fatal_signal(int signo) {
    const char msg[] = "fatal signal received\n";
    write(STDERR_FILENO, msg, sizeof(msg) - 1);  // write는 async-signal-safe
    _exit(1);
}
```

## `errno` 보존

`errno`는 스레드마다(또는 재진입 문맥마다) 하나씩 존재하는 전역 변수다. 문제는, 메인 흐름이 어떤 시스템 콜 직후 `errno`를 아직 읽기 전에 시그널이 들어오고, 처리기 안에서 또 다른 시스템 콜이 `errno`를 덮어써 버릴 수 있다는 점이다. 처리기가 반환한 뒤 메인 흐름이 원래 자기가 확인하려던 `errno`를 읽으면 완전히 다른 값을 보게 된다.

그래서 처리기 안에서 `errno`를 건드릴 수 있는 함수(`write` 포함, 실패 시 `errno`를 설정한다)를 호출한다면, 처리기 진입 시 기존 값을 저장했다가 반환 직전에 복원해야 한다.

```c
static void on_sigchld(int signo) {
    (void)signo;
    int saved_errno = errno;

    // 예: self-pipe에 통지 바이트를 쓴다 (아래 Self-pipe 절 참고)
    ssize_t n = write(g_selfpipe_write_fd, "x", 1);
    (void)n;

    errno = saved_errno;   // 메인 흐름이 보게 될 errno를 원래대로 되돌린다
}
```

이 절을 빼먹으면, 예를 들어 메인 흐름이 `read()`가 -1을 반환한 이유를 `errno == EAGAIN`인지 확인하려는 그 짧은 틈에 시그널이 끼어들어 `errno`를 `EINTR`이나 다른 값으로 바꿔놓는 식의 버그가 생긴다.

## `sigaction`

오래된 `signal()` API는 처리기 등록 시 동작(재시작 여부, 처리 중 시그널 마스크 등)이 플랫폼마다 달라서 이식성 있는 코드에는 적합하지 않다. `sigaction(2)`는 이 모든 것을 명시적으로 지정할 수 있는 대체 API다.

```c
#include <signal.h>
#include <string.h>

void install_handler(int signo, void (*handler)(int)) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);  // 처리 중 추가로 막을 시그널 없음
    sa.sa_flags = SA_RESTART;  // 아래 절 참고

    if (sigaction(signo, &sa, NULL) == -1) {
        // 초기화 단계의 실패이므로 여기서는 perror + exit 정도가 적절하다
        perror("sigaction");
        exit(1);
    }
}
```

`sa_mask`는 "이 처리기가 실행되는 동안 추가로 차단할 시그널 집합"을 뜻한다. 예를 들어 `SIGTERM` 처리기 안에서 `SIGINT`도 같이 막고 싶다면 `sa_mask`에 `SIGINT`를 넣는다. 이렇게 하면 `sa_mask`에 넣은 시그널이 처리기 실행 중에는 대기(pending) 상태로 큐잉되고, 처리기가 반환한 뒤에야 전달된다. `sa_handler` 대신 `sa_sigaction`을 쓰면 시그널을 보낸 프로세스의 PID나 발생 원인 같은 추가 정보(`siginfo_t`)를 받을 수 있는데, 이 경우 `sa_flags`에 `SA_SIGINFO`를 반드시 넣어야 한다.

## `SA_RESTART`

시그널이 블로킹 시스템 콜(`read`, `write`, `accept`, `wait` 등) 도중에 도착하면, 그 시스템 콜은 처리기가 실행된 뒤 `-1`과 함께 `errno = EINTR`을 반환하며 중단된다. `SA_RESTART` 플래그를 주면 커널이 (일부 시스템 콜에 한해) 자동으로 그 시스템 콜을 재시작해 주므로, 매 호출마다 `EINTR`을 확인하고 루프를 도는 코드를 줄일 수 있다.

다만 `SA_RESTART`가 모든 시스템 콜에 적용되는 건 아니다. `select`, `poll`, `epoll_wait`처럼 타임아웃이 있는 대기 함수는 플랫폼에 따라 여전히 `EINTR`로 깨어날 수 있고, 이것이 오히려 이벤트 루프 입장에서는 바람직한 동작이다. 시그널이 왔다는 사실 자체가 "지금 깨어나서 상태를 확인하라"는 신호이기 때문이다. 그래서 이벤트 루프를 구성할 때는 `SA_RESTART`에 의존하지 말고, 대기 함수가 `EINTR`로 반환했을 때 이를 정상적인 "깨어남"으로 처리하는 코드를 항상 넣어야 한다.

```c
ssize_t n;
do {
    n = read(fd, buf, sizeof(buf));
} while (n == -1 && errno == EINTR);   // SA_RESTART가 없거나 적용 안 되는 콜 대비
```

## 시그널 마스크

시그널 마스크는 현재 실행 문맥에서 "차단(block)"되어 있는 시그널의 집합이다. 차단된 시그널은 무시되는 게 아니라 커널 안에 대기(pending) 상태로 쌓이고, 마스크가 풀리는 순간 전달된다. `sigprocmask(2)`(단일 스레드) 또는 `pthread_sigmask(3)`(멀티스레드)로 조작한다.

이벤트 루프 설계에서 시그널 마스크를 쓰는 전형적인 패턴은, self-pipe를 설정하기 전까지 관심 있는 시그널(`SIGCHLD`, `SIGTERM` 등)을 미리 차단해 두는 것이다. 이렇게 하면 "처리기를 등록하는 코드"와 "self-pipe를 만드는 코드" 사이의 짧은 틈에 시그널이 도착해서 유실되는 경쟁 조건을 막을 수 있다 (자세한 경쟁 조건은 아래 "이벤트 대기 직전의 경쟁 조건" 절에서 다룬다).

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGCHLD);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, NULL);
```

### 다중 스레드 프로그램

시그널 마스크는 프로세스 전체가 아니라 스레드마다 독립적으로 존재한다. 반면 처리기 자체(어떤 함수가 실행되는가)는 프로세스 전체에 공유된다. 즉 어느 스레드의 마스크가 열려 있느냐에 따라 커널이 그 스레드를 골라 처리기를 실행시킬 뿐, "이 시그널은 이 스레드 전용"이라는 개념은 없다.

이 때문에 멀티스레드 프로그램에서 흔히 쓰는 패턴은, 새 스레드를 만들기 전에 메인 스레드에서 관심 있는 시그널을 전부 차단해 두는 것이다. `pthread_create`로 만들어진 스레드는 생성 시점의 마스크를 상속받으므로, 이렇게 하면 모든 워커 스레드에서 해당 시그널이 차단된 채로 시작한다. 그리고 시그널을 실제로 처리하고 싶은 전용 스레드 하나만 `sigwait(3)`로 명시적으로 그 시그널을 기다리게 한다. 이 스레드는 시그널이 도착할 때까지 블록되어 있다가 `sigwait`가 반환하면 처리한다.

```c
pthread_t signal_thread;

void *signal_thread_main(void *arg) {
    sigset_t mask;
    sigemptyset(&mask);
    sigaddset(&mask, SIGTERM);
    sigaddset(&mask, SIGINT);

    int signo;
    for (;;) {
        if (sigwait(&mask, &signo) == 0) {
            // sigwait로 받은 시그널은 async-signal-safe 제약이 없
               일반 스레드 문맥에서 실행되므로 여기서는 자유롭게
               로그를 찍거나 정리 절차를 호출해도 된다 */
            handle_signal(signo);
        }
    }
    return NULL;
}
```

이 방식의 장점은 `sigaction` 처리기의 async-signal-safe 제약에서 완전히 벗어난다는 것이다. `sigwait`로 시그널을 받는 코드는 보통의 스레드 함수이므로 원하는 만큼 복잡한 일을 해도 안전하다. 대신 프로그램 시작 시점에 마스크 차단 순서를 정확히 지켜야 한다. 워커 스레드를 만들기 전에 마스크를 막지 않으면, 그 워커 스레드가 우연히 시그널을 받아버릴 수 있다.

## Self-pipe

처리기 안에서는 async-signal-safe 함수만 호출할 수 있다는 제약과, 이벤트 루프는 보통 `select`/`poll`/`epoll` 같은 파일 디스크립터 기반 대기 함수로 짜여 있다는 사실을 연결하는 기법이 self-pipe다. 아이디어는 단순하다: 파이프를 하나 만들어 두고, 시그널 처리기 안에서는 그 파이프의 쓰기 끝에 한 바이트를 쓰기만 한다. `write`는 async-signal-safe 함수이므로 이 동작은 안전하다. 이벤트 루프는 이 파이프의 읽기 끝을 다른 파일 디스크립터들과 함께 감시 대상에 넣어 두면, 시그널이 왔을 때 파이프가 읽기 가능(readable) 상태가 되면서 루프가 깨어난다.

```c
static int g_selfpipe[2];   // [0] = 읽기 끝, [1] = 쓰기 끝

static void on_signal(int signo) {
    int saved_errno = errno;
    unsigned char byte = (unsigned char)signo;
    ssize_t n = write(g_selfpipe[1], &byte, 1);
    (void)n;   // 실패해도(EAGAIN 포함) 처리기 안에서는 할 수 있는 일이 없다
    errno = saved_errno;
}

void setup_selfpipe(void) {
    if (pipe(g_selfpipe) == -1) { perror("pipe"); exit(1); }
    // 이후 두 끝을 각각 non-blocking으로 설정한다 (아래 두 절 참고)
}
```

이렇게 하면 "시그널이 도착했다"는 사실이 커널의 시그널 서브시스템에서 벗어나, 이벤트 루프가 이미 알고 있는 어휘(파일 디스크립터의 읽기 가능 여부)로 번역된다. `select`나 `epoll_wait`가 이 파이프를 다른 소켓, 타이머 fd와 완전히 동일한 방식으로 취급할 수 있으므로, 시그널 처리를 위해 이벤트 루프의 구조를 특별히 바꿀 필요가 없다.

## 대기하지 않는 쓰기 끝

self-pipe의 쓰기 끝을 blocking 모드로 두면 위험하다. 파이프 버퍼는 크기가 제한되어 있는데(보통 64KB 정도), 만약 이벤트 루프가 읽기 끝을 오랫동안 비우지 못하는 사이 같은 시그널이 아주 여러 번 몰아쳐 들어오면 버퍼가 가득 찰 수 있다. 이때 처리기 안의 `write`가 blocking 모드라면, 버퍼에 빈 공간이 생길 때까지 그 자리에서 멈춰버린다. 그런데 버퍼를 비워야 할 주체가 바로 지금 멈춰 있는 이 프로세스의 메인 루프이므로, 결과적으로 자기 자신과 데드락에 빠진다.

`O_NONBLOCK`을 쓰기 끝에 설정해 두면, 버퍼가 가득 찬 상황에서 `write`는 블록하는 대신 즉시 `-1`과 `EAGAIN`을 반환하고 처리기는 그대로 반환한다.

```c
#include <fcntl.h>

int flags = fcntl(g_selfpipe[1], F_GETFL);
fcntl(g_selfpipe[1], F_SETFL, flags | O_NONBLOCK);
```

이 상황에서 통지 바이트 하나가 유실되는 것은 괜찮다. self-pipe의 목적은 "적어도 한 번은 이벤트 루프를 깨운다"는 것이지, 시그널이 도착한 횟수를 정확히 세는 것이 아니다. 실제로 몇 번 발생했는지는 별도의 카운터나 pending 상태로 추적해야 한다("Pending 값을 안전하게 가져오기" 절 참고).

## 읽기 끝도 non-blocking으로 만드는 이유

읽기 끝 역시 non-blocking으로 설정해야 하는데, 이유는 쓰기 끝과는 다르다. 이벤트 루프가 `select`/`epoll_wait`에서 self-pipe의 읽기 끝이 readable하다는 결과를 받았다고 해도, 그 시점과 실제로 `read()`를 호출하는 시점 사이에 파이프에 쌓인 바이트 수가 바뀔 수 있다(예를 들어 처리기가 그 사이 한 번 더 실행돼 바이트를 하나 더 썼다면 상관없지만, 반대로 커널 버퍼링 방식에 따라 예상보다 적은 바이트만 남아 있을 수도 있다).

more importantly, 루프는 보통 파이프를 "비울 수 있을 때까지 반복해서 읽는" 방식으로 처리한다.

```c
for (;;) {
    unsigned char buf[64];
    ssize_t n = read(g_selfpipe[0], buf, sizeof(buf));
    if (n > 0) {
        continue;   // 더 읽을 게 있을 수 있으니 계속
    }
    if (n == -1 && errno == EAGAIN) {
        break;      // 파이프가 비었다: 정상 종료 조건
    }
    if (n == -1 && errno == EINTR) {
        continue;   // 재시도
    }
    break;          // n == 0 이거나 다른 오류
}
```

읽기 끝이 blocking 모드라면 파이프가 실제로 빈 순간 마지막 `read` 호출이 그 자리에서 멈춰버려 이벤트 루프 전체가 정지한다. non-blocking이면 파이프가 비었을 때 `EAGAIN`으로 즉시 반환되므로, 이를 "이제 다 비웠다"는 명확한 종료 조건으로 삼아 루프를 빠져나올 수 있다.

## 외부 프로그램 실행 시 닫기

self-pipe의 두 파일 디스크립터는 `fork()` 시점에 자식 프로세스로 그대로 복제된다. 만약 이 자식이 `exec()`로 외부 프로그램을 실행할 때 이 fd들을 닫지 않고 넘겨주면 두 가지 문제가 생긴다.

1. 자식(그리고 자식이 실행하는 외부 프로그램)이 부모의 self-pipe 쓰기 끝을 들고 있는 채로 오래 살아있으면, 부모가 의도한 "쓰기 끝을 가진 프로세스가 하나도 없어질 때 읽기 끝이 EOF를 본다"는 종료 감지 로직이 깨진다. 자식이 그 fd를 쥐고 있는 한 파이프가 완전히 닫히지 않는다.
2. 불필요하게 열린 fd가 새어나가면서, 완전히 무관한 외부 프로그램이 실수로(혹은 악의적으로) 그 fd에 쓰기를 하면 부모의 이벤트 루프가 엉뚱하게 깨어날 수 있다.

`pipe2(2)`로 파이프를 만들면서 `O_CLOEXEC` 플래그를 바로 지정하면, `exec` 호출 시 커널이 자동으로 해당 fd를 닫아준다. `pipe2`가 없는 플랫폼이라면 `fcntl(fd, F_SETFD, FD_CLOEXEC)`로 각 fd에 개별 설정한다.

```c
#include <fcntl.h>

if (pipe2(g_selfpipe, O_CLOEXEC | O_NONBLOCK) == -1) {
    perror("pipe2");
    exit(1);
}
```

`pipe2`는 `O_CLOEXEC`와 `O_NONBLOCK`을 한 번에 지정할 수 있어, `pipe()` + `fcntl()` 여러 번 호출보다 짧고 그 사이의 경쟁 조건도 없앤다.

## 표준 시그널은 횟수를 보장하지 않습니다

표준 시그널(POSIX 실시간 시그널이 아닌 `SIGTERM`, `SIGCHLD` 등)은 큐잉되지 않는다. 즉, 같은 시그널이 처리기가 아직 실행되기 전(또는 처리기가 아직 마스크로 차단된 상태)에 두 번, 세 번 도착해도 커널은 "대기 중"이라는 사실 하나만 기억할 뿐, 몇 번 도착했는지는 기억하지 않는다. 처리기가 실행되고 나면 그 시그널은 한 번만 전달된 것으로 처리되고, 나머지 발생 횟수는 그냥 사라진다.

이는 self-pipe 설계에도 그대로 영향을 준다. 시그널이 세 번 왔어도 처리기가 그 사이 한 번만 실행됐다면, self-pipe에는 (구현에 따라) 한 바이트만 쓰였을 수도 있다. 그래서 self-pipe로 받은 통지를 "시그널이 정확히 N번 왔다"는 신호로 해석해서는 안 된다. 대신 통지는 오직 "적어도 한 번, 관심 있는 시그널 중 무언가가 발생했으니 상태를 다시 확인하라"는 트리거로만 쓰고, 실제로 몇 개의 이벤트가 밀려 있는지는 그 상태 자체(예: 종료해야 할 자식 프로세스 목록을 `waitpid(WNOHANG)`으로 전부 소진할 때까지 반복하는 식)를 확인해서 알아내야 한다. 정확한 횟수가 꼭 필요하다면 POSIX 실시간 시그널(`SIGRTMIN`~`SIGRTMAX`, `sigqueue(3)`)을 검토할 수 있지만, 이는 이식성과 구현 복잡도 면에서 트레이드오프가 크다.

## Pending 값을 안전하게 가져오기

여러 개의 플래그나 카운터를 처리기와 메인 흐름이 공유해야 하는 경우, 이 값을 어떻게 읽고 쓰느냐가 중요하다. `volatile sig_atomic_t` 하나짜리 플래그(참/거짓 정도)는 안전하지만, 여러 필드로 이루어진 구조체나 카운터의 증가, 감소는 그 자체로 원자적이지 않을 수 있다.

가장 간단하고 이식성 있는 패턴은, 처리기가 값을 직접 조작하지 않고 항상 시그널을 차단한 상태에서 메인 흐름이 값을 읽고 초기화하는 것이다.

```c
static volatile sig_atomic_t g_sigchld_count = 0;

static void on_sigchld(int signo) {
    (void)signo;
    g_sigchld_count++;   // sig_atomic_t 하나에 대한 단순 증가는 안전
}

int fetch_and_reset_sigchld_count(void) {
    sigset_t mask, old;
    sigemptyset(&mask);
    sigaddset(&mask, SIGCHLD);
    sigprocmask(SIG_BLOCK, &mask, &old);   // 처리기가 끼어들 수 없게 잠깐 막는다

    int count = g_sigchld_count;
    g_sigchld_count = 0;

    sigprocmask(SIG_SETMASK, &old, NULL);  // 원래 마스크로 복원
    return count;
}
```

`sigprocmask`로 잠깐 차단해 두는 구간 동안은 처리기가 절대 끼어들 수 없으므로, 그 사이의 읽기-초기화는 "읽으면서 동시에 갱신되는" 경쟁 조건 없이 안전하게 이루어진다. 멀티스레드 환경이라면 `pthread_sigmask` 대신 스레드 간 공유에는 `atomic_int`(C11 `<stdatomic.h>`) 같은 원자적 타입을 함께 고려해야 한다. 시그널 마스크는 시그널 처리기와의 경쟁만 막아줄 뿐, 다른 스레드와의 경쟁까지 막아주지는 않는다.

## 이벤트 대기 직전의 경쟁 조건

self-pipe와 이벤트 루프를 조합할 때 가장 미묘한 버그는 다음 순서로 발생한다.

1. 메인 루프가 "종료 플래그가 섰는지" 확인한다 → 아직 안 섰다.
2. 바로 그 직후, `select`/`epoll_wait` 호출 전에 시그널이 도착해서 처리기가 실행되고 플래그를 세운다.
3. 메인 루프가 `select`를 호출해 블록한다. 그런데 self-pipe에 이미 통지가 쓰여 있었다면 문제없이 곧바로 깨어나지만, 만약 self-pipe 설정 자체가 아직 안 된 초기화 단계였다거나, 확인과 대기 사이의 그 짧은 틈에 발생한 이벤트가 self-pipe를 거치지 않는 종류였다면 루프는 이미 일어난 사건을 놓친 채 다음 이벤트가 올 때까지 무한정 블록해버릴 수 있다.

이것이 "확인(check)과 대기(wait) 사이의 경쟁 조건"이다. self-pipe 자체는 이 문제를 대부분 해결해 준다. 시그널이 언제 도착하든 self-pipe 쓰기는 그 즉시 이루어지고, 그 바이트는 파이프 버퍼에 남아있으므로 이후에 `select`를 호출하면 곧바로 readable 상태로 반환되기 때문이다(설령 시그널이 `select` 호출 *직전*에 왔더라도, 파이프에 남은 바이트가 있으므로 `select`는 블록하지 않고 즉시 리턴한다). 이 성질이 self-pipe 기법의 핵심이다: "플래그 확인"과 "대기 시작" 사이에 원자성이 없어도, 이벤트가 파일 디스크립터에 영속적으로 남아 있기 때문에 경쟁 조건이 사라진다.

반대로 self-pipe 없이 순수 플래그 변수만으로 "확인 후 대기"를 구현하면(`pause(2)`를 쓰는 전통적인 방식 등) 이 경쟁을 피하기 위해 `sigprocmask`로 차단 → 플래그 확인 → `sigsuspend(2)`로 마스크를 원자적으로 복원하면서 대기, 라는 조합이 필요하다. self-pipe 방식이 여러 이벤트 소스를 다뤄야 하는 이벤트 루프에서 더 널리 쓰이는 이유가 여기에 있다. `sigsuspend`는 시그널 하나를 기다리는 데는 적합하지만 소켓 fd 여러 개와 함께 다루기 어렵다.

## 이벤트 루프의 처리 순서

이벤트 루프 한 바퀴에서 self-pipe가 readable로 나타났을 때, 처리 순서를 다음과 같이 고정해 두면 이후 절들(종료 처리, 정리 순서)과 일관성이 맞는다.

1. self-pipe 읽기 끝을 `EAGAIN`이 나올 때까지 전부 비운다 ("읽기 끝도 non-blocking으로 만드는 이유" 절 참고).
2. 대기 중인 상태를 나타내는 플래그/카운터들을 확인한다 (예: 종료 플래그, `SIGCHLD` 카운트).
3. 종료 플래그가 서 있다면 "종료 사건 처리" 절의 순서로 넘어가고, 그렇지 않다면 개별 이벤트(예: `waitpid(WNOHANG)`로 종료된 자식들을 전부 회수)를 처리한 뒤 평소처럼 다음 바퀴로 돈다.

self-pipe를 비우는 일을 다른 소켓 fd를 처리하기 *전에* 하는 이유는, self-pipe에 남아있는 통지가 다음 `select` 호출에서도 계속 readable 상태를 유발해 루프가 불필요하게 바쁘게 도는(busy loop) 것을 막기 위해서다.

## 종료 사건 처리

`SIGTERM`이나 `SIGINT` 같은 종료 요청은 대부분의 다른 이벤트와 달리, 받자마자 그 자리에서 프로세스를 끝내면 안 된다. 진행 중인 요청을 끊거나 파일을 반쯤 쓴 채로 종료하면 상태가 깨진다. 그래서 처리기는 (이 문서의 다른 시그널과 마찬가지로) 플래그만 세우고, 이벤트 루프가 다음 바퀴에서 이를 확인해 "정상 종료(graceful shutdown)" 절차를 시작하는 방식이 일반적이다.

```c
if (g_shutdown_requested) {
    stop_accepting_new_connections();   // 새 연결/작업을 더 받지 않는다
    drain_in_flight_work();             // 이미 시작된 작업은 완료시키거나 취소한다
    // 이 단계가 끝난 뒤에야 "정리 순서" 절의 절차로 넘어간다
}
```

여기서 중요한 점은, 종료 요청이 들어왔다고 이벤트 루프 자체를 즉시 멈추는 게 아니라 "새 이벤트 루프 반복에서 종료 절차로 분기한다"는 것이다. 이렇게 하면 종료 처리 코드도 다른 이벤트 처리 코드와 마찬가지로 일반적인 실행 문맥에서 돌기 때문에, async-signal-safe 제약 없이 자유롭게 로그를 남기고 자원을 정리할 수 있다.

## 정리 순서

프로세스가 실제로 종료하기 직전에는 열어둔 자원들을 역순으로(대략 초기화의 반대 순서로) 정리하는 것이 안전하다. self-pipe와 관련해서는 다음을 신경 써야 한다.

- self-pipe의 읽기 끝, 쓰기 끝 fd를 닫는다.
- 만약 여러 시그널에 대해 처리기를 등록했다면, 종료 처리 도중에는 굳이 `sigaction`을 기본값으로 되돌릴 필요는 없다. 프로세스가 곧 사라질 것이기 때문이다. 다만 데몬처럼 재시작을 반복하거나, 자식 프로세스를 새로 `fork`해서 계속 띄우는 구조라면 정리 시점에 마스크와 처리기를 원상 복구해 두는 편이 다음 생애주기에 영향을 주지 않는다.
- 소켓, 파일, 락 파일 같은 다른 자원은 self-pipe보다 먼저 열렸다면 self-pipe보다 나중에 닫는 게 자연스럽다. "나중에 연 것을 먼저 닫는다"는 일반적인 자원 해제 원칙을 여기서도 따른다.

정리 코드 자체는 이미 시그널 마스크나 처리기와 무관한, 평범한 함수 호출 순서로 실행되므로 특별한 제약은 없다. 다만 정리 도중 다시 시그널이 들어오는 상황(예: 사용자가 종료 신호를 두 번 보내는 경우)까지 고려한다면, 정리 절차 진입 시점에 해당 시그널들을 다시 한 번 차단해 정리 로직이 재진입되지 않도록 하는 것도 방법이다.

## 초기화 실패 시 되돌리기

`setup_selfpipe`처럼 여러 시스템 콜(파이프 생성, `O_NONBLOCK`/`O_CLOEXEC` 설정, `sigaction` 등록, 시그널 마스크 조작)을 순서대로 호출하는 초기화 코드는 중간 단계에서 실패할 수 있다. 이때 이미 성공한 앞 단계들을 그대로 방치하면, 예를 들어 파이프는 만들어졌는데 처리기 등록에 실패한 상태로 프로그램이 계속 진행되어 나중에 예상치 못한 동작(파이프에 아무도 쓰지 않는데 fd만 열려 있는 등)을 유발할 수 있다.

초기화 함수는 실패한 지점까지 만들어진 자원을 역순으로 되돌리고 나서 오류를 반환하도록 짜는 것이 안전하다.

```c
int setup_selfpipe(void) {
    if (pipe2(g_selfpipe, O_CLOEXEC | O_NONBLOCK) == -1) {
        return -1;   // 아무것도 안 만들어졌으니 되돌릴 것도 없다
    }

    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = on_signal;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;

    if (sigaction(SIGTERM, &sa, NULL) == -1) {
        close(g_selfpipe[0]);   // 앞서 만든 파이프를 되돌린다
        close(g_selfpipe[1]);
        return -1;
    }

    if (sigaction(SIGCHLD, &sa, NULL) == -1) {
        signal(SIGTERM, SIG_DFL);   // 앞서 등록한 SIGTERM 처리기를 되돌린다
        close(g_selfpipe[0]);
        close(g_selfpipe[1]);
        return -1;
    }

    return 0;
}
```

초기화 실패는 보통 프로그램 시작 단계에서 일어나므로 async-signal-safe 제약 없이 일반적인 오류 처리(로그, `errno` 확인, 상위 호출자에게 실패 전파)를 그대로 적용할 수 있다. 다만 "부분적으로 설정된 상태"를 남기지 않는다는 원칙만은 지켜야, 이후 이 프로세스가 시그널을 받았을 때 절반만 설정된 self-pipe나 처리기 때문에 이상 동작하는 것을 막을 수 있다.

## 테스트할 내용

시그널 처리 코드는 타이밍에 의존하는 경쟁 조건이 핵심이라 일반적인 단위 테스트로는 잡히지 않는 경우가 많다. 다음 항목들을 각각 별도로 확인하는 것이 좋다.

- **기본 동작**: 시그널을 보냈을 때(`kill(getpid(), SIGTERM)` 등) 실제로 self-pipe가 readable해지고 이벤트 루프가 깨어나는지.
- **폭주 상황**: 같은 시그널을 아주 짧은 시간 안에 여러 번 연속으로 보냈을 때 self-pipe 버퍼가 가득 차더라도(non-blocking write가 `EAGAIN`을 반환하더라도) 프로세스가 멈추거나 죽지 않는지, 그리고 최소 한 번은 이벤트 루프가 깨어나는지.
- **확인-대기 경쟁**: 플래그를 확인하는 시점과 `select`/`epoll_wait` 호출 시점 사이에 의도적으로 지연을 넣어(테스트 전용 빌드에서 `usleep` 삽입 등) 그 틈에 시그널을 보내도 이벤트가 유실되지 않는지.
- **`EINTR` 처리**: `SA_RESTART`가 적용되지 않는 시스템 콜(특히 대기 함수)에서 시그널이 도착했을 때 `EINTR`을 제대로 처리하고 있는지, 재시작 루프를 빼먹으면 특정 타이밍에서만 실패하는 산발적 버그가 된다.
- **`errno` 오염**: 처리기가 실행되는 도중 메인 흐름이 `errno`를 확인하려던 시나리오를 재현해, 처리기가 `errno`를 복원하지 않았을 때 발생하는 증상과 비교해 본다.
- **cloexec 확인**: self-pipe fd를 쥔 채로 자식 프로세스를 `fork`+`exec`한 뒤, `/proc/<pid>/fd`(리눅스 기준)를 확인해 자식이 그 fd를 물려받지 않았는지.
- **정리 순서**: 정상 종료 경로와, 초기화 중간에 실패를 주입한 경로 양쪽에서 fd 누수가 없는지(`lsof`나 `/proc/<pid>/fd` 개수 비교로 확인 가능).
- **멀티스레드 마스크 상속**: (다중 스레드 절이 적용되는 경우) 워커 스레드 생성 순서를 바꿔가며, 의도한 시그널 처리 스레드가 아닌 다른 스레드가 시그널을 가로채지 않는지.
