# 프로세스, 파일 디스크립터, 파이프

유닉스 계열 시스템에서 셸이 명령을 실행하고, 파이프로 명령을 연결하고, 자식 프로세스의 종료를 기다리는 전체 흐름은 결국 `fork`, `exec`, `pipe`, `dup2`, `waitpid` 다섯 개의 시스템콜 조합으로 귀결된다. 이 문서는 이 조합이 왜 그런 순서로 필요한지, 그리고 실전에서 자주 틀리는 지점(FD 누수, 부분 실패, EOF 조건)을 짚는다.

## `fork`

`fork()`는 호출한 프로세스를 복제해 부모와 자식, 두 개의 독립된 프로세스를 만들고 반환값으로 두 프로세스를 구분한다: 부모에서는 자식의 PID(양수)가, 자식에서는 `0`이, 실패 시에는 `-1`이 반환된다. 복제되는 시점의 메모리 이미지(힙, 스택, 전역 변수)는 논리적으로 동일하지만 물리적으로는 copy-on-write로 공유되다가 한쪽이 쓰기를 시도할 때 실제로 분리된다.

파일 디스크립터 테이블도 복제 대상이다. 부모가 `fork` 직전에 열어 둔 FD는 자식도 그대로 이어받는다. 단, 테이블 항목(정수 번호와 플래그)만 복제되고, 커널의 "열린 파일 설명(open file description)"은 부모, 자식이 공유한다. 그래서 **자식이 그 FD로 `read`해서 파일 오프셋을 옮기면 부모가 같은 FD로 다음 `read`를 할 때도 그 옮겨진 오프셋부터 읽힌다. 이 공유 여부가 파이프를 이용한 프로세스 간 통신의 전제**가 된다.

```c
pid_t pid = fork();
if (pid < 0) {
    perror("fork");
    exit(1);
} else if (pid == 0) {
    // 자식 프로세스
    execlp("ls", "ls", "-l", NULL);
    perror("execlp");   // exec가 성공하면 이 줄은 절대 실행되지 않는다
    _exit(127);
} else {
    // 부모 프로세스
    int status;
    waitpid(pid, &status, 0);
}
```

자식 쪽에서 `perror`나 표준 `exit()`를 쓰지 않고 `_exit()`를 쓰는 이유는 뒤에서 다룬다.

## `exec`

`fork`는 프로세스를 복제할 뿐 새 프로그램을 실행하지는 않는다. 복제된 자식이 실제로 다른 프로그램(`ls`, `grep` 같은)을 실행하려면 `exec` 계열 함수(`execve`, `execlp`, `execvp` 등)를 호출해야 한다. `exec`는 현재 프로세스의 텍스트, 데이터, 스택을 새 프로그램의 이미지로 완전히 덮어쓴다. 새 프로세스가 생기는 게 아니라 같은 PID를 유지한 채 프로그램만 바뀐다. 그래서 `exec`가 성공하면 그 호출 이후의 코드는 절대 실행되지 않는다. `execlp` 다음 줄이 실행됐다는 것 자체가 `exec`가 실패했다는 증거다.

### `exec`와 열린 FD

`exec`로 프로그램 이미지가 통째로 바뀌어도 열려 있는 파일 디스크립터는 기본적으로 그대로 유지된다. 이것이 리다이렉션과 파이프 구현의 핵심 전제다: `dup2`로 표준입출력을 원하는 FD에 연결해 두고 `exec`를 호출하면, 새로 실행되는 프로그램은 그 사실을 전혀 모른 채 `stdin`/`stdout`을 정상적으로 쓸 수 있다.

단, `FD_CLOEXEC` 플래그(`fcntl(fd, F_SETFD, FD_CLOEXEC)`)가 걸린 FD는 예외다. 이 플래그가 설정된 FD는 `exec` 시점에 커널이 자동으로 닫는다. 셸 구현에서 파이프의 읽기/쓰기 끝을 만들 때 이 플래그를 실수로 걸어 두면, 정작 자식이 `exec` 직전에 `dup2`로 복제해 둔 FD는 살아있어도 원본 FD가 사라져 있는 경우가 생길 수 있으니 순서에 주의해야 한다.

### `argv` 계약

`exec` 계열 함수에 넘기는 `argv` 배열은 반드시 `NULL`로 끝나야 한다. `execlp("ls", "ls", "-l", NULL)`에서 첫 번째 `"ls"`는 실행할 프로그램 경로(PATH 탐색용 이름), 두 번째 `"ls"`부터는 그 프로그램이 자기 `argv[0]`으로 받게 될 값이다. 관례상 `argv[0]`은 프로그램 이름 자체를 넣지만, 커널은 이를 강제하지 않으므로 `argv[0]`에 아무 문자열이나 넣어도 실행 자체는 된다. 다만 `NULL` 종료자를 빠뜨리면 `exec`는 스택 너머의 쓰레기 값을 인자로 읽어 들이므로 반드시 넣어야 한다.

### `126`과 `127`

셸은 명령 실행 실패를 관례적인 종료 코드로 구분해 알린다. `127`은 명령을 찾지 못했을 때(`execvp`가 `ENOENT`로 실패), `126`은 명령은 찾았지만 실행 권한이 없거나 실행 불가능한 형식일 때(`EACCES`, `ENOEXEC` 등) 쓰는 관례다. 이 값은 커널이 강제하는 게 아니라 `sh`/`bash` 등 셸 구현이 약속한 것이므로, 직접 셸을 구현한다면 `exec`가 실패했을 때 `errno`를 보고 이 관례를 따라 `_exit(126)` 또는 `_exit(127)`을 호출해 주는 게 좋다.

## `waitpid`

`fork`로 만든 자식이 종료해도 부모가 그 종료 상태를 회수(`wait` 계열 호출)하기 전까지 자식은 좀비(zombie) 상태로 프로세스 테이블에 남는다. `waitpid(pid, &status, options)`는 특정 PID(또는 `-1`로 아무 자식)의 종료를 기다리고 `status`에 결과를 채운다. `status`는 비트 레이아웃이 플랫폼별로 다를 수 있기 때문에 직접 해석하지 않고 `WIFEXITED(status)` / `WEXITSTATUS(status)` / `WIFSIGNALED(status)` / `WTERMSIG(status)` 같은 매크로로 해석해야 한다.

```c
int status;
pid_t w = waitpid(pid, &status, 0);
if (w < 0) {
    perror("waitpid");
} else if (WIFEXITED(status)) {
    printf("종료 코드: %d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("시그널 %d로 종료됨\n", WTERMSIG(status));
}
```

`waitpid`를 호출하지 않고 부모가 계속 살아있으면 자식은 좀비로 남아 `ps`에 `<defunct>`로 보인다. 좀비 자체는 커널 자원(프로세스 테이블 슬롯 하나)만 차지하므로 심각한 누수는 아니지만, 장수 프로세스(셸, 데몬)가 자식을 계속 회수하지 않으면 결국 프로세스 테이블이 고갈될 수 있다.

## `pipe`

`pipe(int fds[2])`는 커널 버퍼 하나를 두 개의 FD로 노출하는 단방향 통신 채널을 만든다. `fds[0]`은 읽기 전용 끝, `fds[1]`은 쓰기 전용 끝이다. 이 두 FD는 `fork` 전에 만들어야 의미가 있다. `fork`로 FD 테이블이 복제되면서 부모와 자식이 같은 파이프의 양 끝을 나눠 갖게 되고, 그 뒤 각자 안 쓰는 쪽을 `close`하는 방식으로 단방향 통신을 구성한다.

```c
int fds[2];
if (pipe(fds) < 0) { perror("pipe"); exit(1); }

pid_t pid = fork();
if (pid == 0) {
    close(fds[0]);  // 자식은 쓰기만 함
    dup2(fds[1], STDOUT_FILENO);
    close(fds[1]);
    execlp("ls", "ls", NULL);
    _exit(127);
} else {
    close(fds[1]);  // 부모는 읽기만 함
    char buf[256];
    ssize_t n;
    while ((n = read(fds[0], buf, sizeof(buf))) > 0) {
        write(STDOUT_FILENO, buf, n);
    }
    close(fds[0]);
    waitpid(pid, NULL, 0);
}
```

### 파이프의 EOF 조건

파이프의 읽기 쪽에서 `read`가 `0`을 반환(EOF)하는 조건은 "쓰기 쪽 FD를 참조하는 열린 파일 설명이 하나도 남지 않았을 때"다. 여기서 핵심은 FD 개수가 아니라 참조 개수라는 점이다. 부모가 `fds[1]`을 열어 둔 채로 자식만 종료해도, 부모 쪽에 쓰기 끝이 여전히 열려 있으므로 읽기 쪽은 EOF를 받지 못하고 무한정 블록된다. 그래서 각 프로세스가 자기가 쓰지 않는 끝을 반드시 명시적으로 `close`해야 한다: 부모는 `fds[1]`을, 자식은 `fds[0]`을 닫아야 나머지 한쪽이 마지막 참조가 되고, 그 참조마저 닫힐 때 비로소 EOF가 발생한다. 두 자식을 파이프로 연결하는 경우처럼 참여자가 여러 개면 이 닫기 규율은 더 엄격해진다. 하나라도 안 쓰는 끝을 들고 있으면 전체 파이프라인이 멈춘다.

## `dup2`

`dup2(oldfd, newfd)`는 `newfd`가 `oldfd`와 같은 열린 파일 설명을 가리키도록 만든다. 이때 `newfd`가 이미 열려 있었다면 원자적으로 먼저 닫고 재사용한다. `close(newfd); dup(oldfd)`를 따로 호출하는 것과 달리, 그 사이에 다른 스레드나 시그널 핸들러가 끼어들어 `newfd` 번호를 가로챌 여지가 없다. 리다이렉션 구현의 표준 패턴은 다음과 같다: 원하는 FD(파일이든 파이프든)를 열고, `dup2(fd, STDOUT_FILENO)`로 표준출력 자리에 복제한 뒤, 더 이상 필요 없는 원본 `fd`를 닫는다.

```c
int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(fd, STDOUT_FILENO);
close(fd);
execlp("ls", "ls", NULL);
```

### `source == destination`

`dup2(fd, fd)`처럼 `oldfd`와 `newfd`가 같은 값이면 POSIX 규격상 아무 동작도 하지 않고 성공을 반환한다. 특히 `close-on-exec` 플래그를 건드리지 않는다는 점이 중요하다. 파이프라인 구현에서 이 경우를 특별 취급하지 않고 무심코 `close(oldfd)`를 뒤따라 호출하면, `newfd`와 `oldfd`가 사실 같은 FD였으므로 정작 필요한 FD를 자기 손으로 닫아버리는 버그가 된다. 예를 들어 파이프의 쓰기 끝이 우연히 이미 `STDOUT_FILENO` 번호를 갖고 있는 경우(FD 재사용으로 흔히 발생) `dup2(fds[1], STDOUT_FILENO)` 다음에 오는 `close(fds[1])`이 표준출력 자체를 닫아버릴 수 있다. 이런 케이스는 `oldfd == newfd`를 먼저 검사해 `close`를 건너뛰는 방식으로 방어해야 한다.

## 두 명령 연결

`cmd1 | cmd2` 형태의 파이프라인은 파이프 하나, 자식 프로세스 둘, 그리고 부모의 FD 정리로 구성된다. 파이프는 반드시 두 `fork` 이전에 만들어 둬야 양쪽 자식이 같은 파이프를 상속받는다.

```c
int fds[2];
pipe(fds);

pid_t left = fork();
if (left == 0) {
    close(fds[0]);
    dup2(fds[1], STDOUT_FILENO);
    close(fds[1]);
    execlp("cmd1", "cmd1", NULL);
    _exit(127);
}

pid_t right = fork();
if (right == 0) {
    close(fds[1]);
    dup2(fds[0], STDIN_FILENO);
    close(fds[0]);
    execlp("cmd2", "cmd2", NULL);
    _exit(127);
}

close(fds[0]);
close(fds[1]);
waitpid(left, NULL, 0);
waitpid(right, NULL, 0);
```

### 왼쪽 자식

왼쪽 자식(`cmd1`)은 파이프의 쓰기 끝만 필요하다. 읽기 끝(`fds[0]`)을 즉시 닫고, 쓰기 끝(`fds[1]`)을 `STDOUT_FILENO`로 `dup2`한 뒤 원본 `fds[1]`도 닫는다. 이렇게 해야 `cmd1`이 표준출력에 쓰는 모든 내용이 파이프로 들어가고, 동시에 이 자식이 들고 있는 파이프 참조가 정확히 하나(복제된 FD 1번)만 남는다.

### 오른쪽 자식

오른쪽 자식(`cmd2`)은 대칭적으로 읽기 끝만 필요하다. 쓰기 끝(`fds[1]`)을 즉시 닫고, 읽기 끝(`fds[0]`)을 `STDIN_FILENO`로 `dup2`한 뒤 원본을 닫는다. 여기서 왼쪽 자식이 아직 파이프에 아무것도 안 썼더라도, `dup2`와 `exec`는 블로킹되지 않는다. 실제로 `read`가 블록되는 시점은 `cmd2`가 표준입력을 읽기 시작할 때이며, 그건 두 프로세스가 이미 각자 병렬로 실행되기 시작한 뒤다.

### 부모

부모는 파이프의 어느 쪽도 데이터를 주고받는 데 쓰지 않으므로 `fork` 직후 양쪽 FD를 전부 닫아야 한다. 이걸 빠뜨리면 부모가 쓰기 끝을 들고 있는 채로 남아, `cmd1`이 종료돼도 EOF 조건이 충족되지 않아 `cmd2`가 영원히 입력을 기다리는 상태로 멈춘다. 부모의 역할은 파이프를 만들고, 두 자식에게 나눠주고, 자기 몫은 즉시 반납한 뒤 종료를 기다리는 것뿐이다.

## 두 자식을 시작한 뒤 기다리기

두 `fork`를 먼저 순서대로 다 해놓고, `waitpid`는 그 다음에 몰아서 호출하는 순서가 중요하다. 만약 왼쪽 자식을 `fork`한 직후 바로 `waitpid(left, ...)`로 블록해 버리면, 오른쪽 자식이 아직 시작되지 않은 상태에서 왼쪽 자식이 파이프 버퍼(보통 64KB)를 가득 채우고 블록될 경우 데드락에 빠진다. 왼쪽은 버퍼가 빌 때까지 `write`에서 멈춰 있고, 그걸 비워줄 오른쪽은 아직 존재하지도 않기 때문이다. 그래서 반드시 필요한 자식을 모두 `fork`하고 부모가 자기 FD를 정리한 뒤에야 `waitpid`를 호출해야 하며, 두 개 이상을 기다릴 때는 순서(`left` 먼저 또는 `right` 먼저)는 상관없다. 어느 쪽이 먼저 끝나든 `waitpid`는 해당 PID가 종료할 때까지만 블록되고 다른 자식은 그동안 백그라운드에서 계속 실행된다.

## 부분 `fork` 실패

파이프라인의 자식이 셋 이상이거나 `fork`를 반복 호출하는 구조에서는, 앞선 `fork` 몇 개는 성공하고 중간의 `fork` 하나가 자원 부족(`EAGAIN`, `ENOMEM`)으로 실패하는 상황을 반드시 고려해야 한다. 이 경우 이미 만들어진 자식들은 그대로 살아서 실행 중이므로, 부모는 그 자식들을 고아로 방치하지 말고 신호(`SIGTERM`)를 보내 정리하거나 최소한 `waitpid`로 회수해야 한다. 흔한 실수는 `fork` 실패를 감지한 즉시 부모가 `exit()`해 버리는 것, 이미 실행 중인 자식들이 파이프의 다른 쪽을 기다리며 좀비 혹은 무한 블록 상태로 남는다.

```c
pid_t pids[N];
int ok = 1;
for (int i = 0; i < N && ok; i++) {
    pids[i] = fork();
    if (pids[i] < 0) {
        perror("fork");
        ok = 0;
        for (int j = 0; j < i; j++) kill(pids[j], SIGTERM);
    } else if (pids[i] == 0) {
        // ... exec ...
    }
}
for (int i = 0; i < N; i++) {
    if (pids[i] > 0) waitpid(pids[i], NULL, 0);
}
```

## 오류 경로에서도 FD를 닫기

`open`, `pipe`, `dup2` 같은 호출이 성공 경로에서만 FD를 닫도록 짜여 있으면, 그 사이에 다른 호출이 실패해 함수를 일찍 빠져나가는 오류 경로에서 FD가 그대로 새어 나간다. 특히 `exec` 실패 후 자식에서 `_exit`하기 전에 열어 둔 FD들을 정리하지 않고 그냥 종료하는 경우가 많은데, 프로세스가 종료되면 커널이 어차피 모든 FD를 회수하므로 이 특정 경우엔 실질적 문제는 없다. 진짜 위험한 쪽은 부모(또는 장수 프로세스) 안에서 함수 단위로 파이프나 파일을 여닫는 헬퍼를 여러 번 호출하는 구조다. 한 번의 실패 경로에서 `close`를 빠뜨리면 그 프로세스가 살아있는 한 FD 하나가 계속 누적되고, 수천 번 반복되면 `EMFILE`("too many open files")로 이어진다. 규칙은 단순하다: 함수 안에서 연 FD는 성공/실패 관계없이 모든 반환 경로에서 닫는다.

## 파일 디스크립터 누수 확인

실행 중인 프로세스가 FD를 얼마나 들고 있는지는 `/proc/<pid>/fd/` 디렉터리를 나열해 확인할 수 있다. 각 항목은 해당 FD가 가리키는 대상(파일, 파이프, 소켓)으로의 심볼릭 링크다.

```sh
ls -l /proc/$PID/fd
```

파이프라인 코드를 고친 뒤에는 반복 실행 전후로 이 목록의 항목 수가 늘어나는지 비교하는 것이 가장 직접적인 검증 방법이다. `lsof -p <pid>`도 같은 정보를 더 읽기 쉬운 형태로 보여준다. 장기 실행 서버라면 주기적으로 열린 FD 개수를 로깅해 두면 서서히 늘어나는 누수를 조기에 잡아낼 수 있다.

## 프로세스 그룹

셸이 하나의 파이프라인(`cmd1 | cmd2 | cmd3`)을 실행할 때, 그 파이프라인에 속한 모든 자식은 보통 같은 프로세스 그룹으로 묶는다. `setpgid(pid, pgid)`를 각 자식에서(또는 부모에서 각 자식에 대해 경쟁 없이) 호출해, 파이프라인의 첫 자식이 그룹 리더(`pgid == pid`)가 되고 나머지는 그 그룹에 합류하도록 만든다. 이렇게 묶어 두면 터미널에서 Ctrl+C(`SIGINT`)를 눌렀을 때 그 시그널이 포그라운드 프로세스 그룹 전체에 전달되어, 파이프라인 중 하나만이 아니라 `cmd1`, `cmd2`, `cmd3` 전부가 함께 종료된다. 프로세스 그룹을 나누지 않으면 파이프 중간의 한 명령만 죽고 나머지는 좀비 상태로 파이프의 반대쪽을 기다리며 남을 수 있다. 대화형 셸을 구현한다면 여기에 더해 `tcsetpgrp()`로 터미널의 포그라운드 프로세스 그룹을 그 파이프라인 그룹으로 넘겨줘야 키보드 시그널과 터미널 입력이 올바르게 전달된다.

## 테스트할 내용

- `fork` 실패(`ulimit -u`로 프로세스 수를 낮춰 강제로 `EAGAIN` 재현)를 부모가 감지하고, 이미 시작된 자식들을 정리하는지
- `exec` 대상이 존재하지 않을 때 자식이 `127`로, 실행 권한이 없을 때 `126`으로 종료하는지
- 파이프의 양쪽 끝을 각 프로세스가 정확히 하나씩만 들고 있는지 (`/proc/<pid>/fd`로 확인), 특히 부모가 `fork` 직후 두 끝을 모두 닫는지
- `cmd1`이 아무 출력도 하지 않고 즉시 종료할 때 `cmd2`가 정상적으로 EOF를 받고 종료하는지 (파이프 끝을 안 닫으면 여기서 무한 블록됨을 재현해 보는 것도 유용하다)
- 파이프 버퍼 크기(리눅스 기본 64KB)보다 큰 데이터를 흘려보내 `left`를 먼저 `waitpid`하지 않는 순서가 실제로 데드락을 막는지
- `dup2(fd, fd)` 케이스를 의도적으로 만들어(파이프 FD 번호가 우연히 `STDOUT_FILENO`와 같아지도록 FD를 미리 소진시켜서) 뒤따르는 `close`가 표준출력을 실수로 닫지 않는지
- Ctrl+C를 눌렀을 때 파이프라인의 모든 프로세스가 함께 종료되는지, 프로세스 그룹을 안 나눈 버전과 비교
