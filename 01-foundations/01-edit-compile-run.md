# 편집, 컴파일, 실행

C로 뭔가를 만든다는 건 "코드를 쓴다"가 아니라 "코드를 쓰고 → 그걸 실행 가능한 형태로 바꾸고 → 그 결과를 확인한다"라는 세 단계를 오가는 일이다. 다른 언어(파이썬, JS)에 익숙하다면 이 세 단계가 "저장하면 끝"이 아니라는 점부터 낯설 수 있다. 이 문서는 그 순환(편집기에서 코드를 고치고, 컴파일러로 그걸 기계어로 바꾸고, 나온 결과물을 실행해 확인하는 순서)을 손에 붙이는 것부터 시작한다.

## 가장 작은 프로그램

C 프로그램이 성립하려면 최소한 `main` 함수 하나가 있어야 한다. 프로그램이 시작될 때 운영체제가 제일 먼저 호출하는 함수가 `main`이기 때문에, 이게 없으면 링커가 시작 지점을 찾지 못해 빌드 자체가 실패한다.

```c
int main(void) {
    return 0;
}
```

이 네 줄이 컴파일되고 실행되는 가장 작은 C 프로그램이다. `int`는 이 함수가 정수를 돌려준다는 뜻이고, `void`는 인자를 받지 않는다는 뜻이며, `return 0`은 "정상 종료"를 운영체제에 알리는 값이다. 아무 일도 하지 않지만, 편집 → 컴파일 → 실행이라는 사이클 전체를 통과시켜 볼 수 있는 최소 단위라는 점에서 의미가 있다.

흔한 실수로 `main`에 `return`을 아예 생략하는 경우가 있다. C99 이후 표준에서는 `main`의 끝에 도달하면 `return 0;`이 생략된 것처럼 처리해 주지만, 이 동작에 기대지 않고 명시적으로 적어 두는 편이 이후 "종료 상태 확인하기"에서 다룰 문제를 피하기 쉽다.

## 컴파일 명령 읽기

소스 파일 `hello.c`를 실행 파일로 만들려면 컴파일러를 호출해야 한다. gcc를 기준으로 가장 기본적인 형태는 이렇다.

```sh
gcc hello.c -o hello
```

이 한 줄 안에 세 가지 정보가 들어 있다. `gcc`는 사용할 컴파일러, `hello.c`는 입력이 되는 소스 파일, `-o hello`는 "출력 파일 이름을 hello로 하라"는 지시다. `-o` 옵션을 빼면 컴파일러는 관례적으로 `a.out`이라는 이름으로 실행 파일을 만든다(이름이 `a.out`인 이유는 초기 유닉스 컴파일러의 기본 출력 이름이 그대로 관례로 남았기 때문이다).

옵션은 순서를 크게 가리지 않지만, `-o` 뒤에는 반드시 파일 이름이 와야 한다는 점만 기억하면 된다. 자주 같이 쓰게 될 옵션 몇 가지도 미리 봐 두면 좋다.

```sh
gcc -Wall -Wextra -std=c11 hello.c -o hello
```

`-Wall -Wextra`는 경고를 최대한 많이 켜라는 뜻이고, `-std=c11`은 어떤 C 표준을 기준으로 컴파일할지 지정한다. 경고는 무시해도 컴파일은 되는 경우가 많지만, 대부분의 버그가 경고 단계에서 먼저 신호를 보낸다는 점에서 처음부터 켜 두는 습관을 들이는 게 낫다.

## 소스 파일과 실행 파일은 별개다

`hello.c`를 수정한 뒤 곧바로 `./hello`를 실행해서 "왜 바뀐 게 반영이 안 되지"라고 당황하는 건 초보자가 가장 흔하게 겪는 일이다. 이유는 단순하다. 컴파일은 소스 코드를 실행 파일로 "번역"하는 별도의 단계이고, 이 번역은 자동으로 다시 일어나지 않는다. `hello.c`를 고쳤다면, 그 변경은 `gcc hello.c -o hello`를 다시 실행해서 `hello`라는 실행 파일을 새로 만들어야만 반영된다.

```sh
# 1. 소스 수정
vim hello.c

# 2. 다시 컴파일 (수정 반영은 여기서 일어난다)
gcc hello.c -o hello

# 3. 실행 (컴파일 시점의 코드가 실행된다)
./hello
```

`./hello`처럼 앞에 `./`를 붙이는 이유도 여기서 짚고 넘어갈 만하다. 셸은 기본적으로 현재 디렉터리를 실행 파일 탐색 경로(`PATH`)에 포함하지 않는다. `./`는 "현재 디렉터리에 있는 이 파일을 실행하라"는 명시적인 지시이며, 이게 없으면 셸은 `PATH`에 등록된 디렉터리들만 뒤지다가 "명령을 찾을 수 없다"는 오류를 낸다.

소스 파일(`.c`)과 실행 파일(`hello`)은 저장된 형식도, 다루는 방식도 완전히 다른 별개의 파일이라는 점을 기억해 두면, 이후 "소스 파일은 고쳤는데 결과가 안 바뀐다" 같은 혼란을 스스로 진단할 수 있게 된다.

## 종료 상태 확인하기

프로그램이 끝나면 운영체제에 정수 하나를 돌려준다. 이걸 종료 상태(exit status)라고 부르며, 관례상 `0`은 성공, `0`이 아닌 값은 실패나 특정 오류 상황을 뜻한다. 셸에서는 직전 명령의 종료 상태를 `$?`로 바로 확인할 수 있다.

```sh
./hello
echo $?    # 방금 실행한 hello의 종료 상태 출력
```

이게 왜 중요한가 하면, 화면에 아무 출력도 없는 프로그램이 "성공적으로 아무것도 안 한 것"인지 "뭔가 실패해서 조용히 죽은 것"인지는 종료 상태를 보지 않으면 구분할 수 없기 때문이다. 셸 스크립트에서 `&&`나 `||`로 명령을 이어 붙이는 것도 이 종료 상태를 기준으로 동작한다.

```c
int main(void) {
    return 1;  // 실패를 나타내는 관례적인 값
}
```

흔한 함정은 `main` 안에서 `exit(1)`을 호출하는 것과 `return 1`을 혼동해서, 함수 중간에 있는 `exit()` 호출이 그 뒤의 정리 코드(가령 열어 둔 파일을 닫는 코드)를 건너뛴다는 사실을 잊는 것이다. `exit()`는 그 자리에서 즉시 프로그램을 끝내지만, `return`은 `main`이라는 함수 하나를 정상적으로 빠져나가는 것이라는 차이가 있다.

## `stdout`과 `stderr`

C 프로그램이 화면에 뭔가를 출력할 때 사실은 두 개의 서로 다른 통로를 쓸 수 있다. `printf`로 내보내는 일반 출력은 표준 출력(`stdout`)으로 가고, 오류 메시지를 위한 표준 오류(`stderr`)라는 별도의 통로도 있다.

```c
#include <stdio.h>

int main(void) {
    printf("정상 출력입니다\n");            // stdout
    fprintf(stderr, "오류 메시지입니다\n"); // stderr
    return 0;
}
```

터미널에서 그냥 실행하면 둘 다 화면에 뒤섞여 보이기 때문에 차이가 잘 안 느껴진다. 이 둘이 나뉘어 있는 이유는, 프로그램의 "진짜 결과"와 "진행 상황이나 오류 알림"을 분리해서 각각 다른 곳으로 보낼 수 있게 하기 위해서다. 예를 들어 결과만 파일에 저장하고 오류 메시지는 화면에서 계속 보고 싶을 때 이 구분이 필요해진다.

### `stdout`과 `stderr`를 따로 저장하기

셸의 리다이렉션 기호로 두 통로를 각각 다른 곳으로 보낼 수 있다.

```sh
./hello > output.txt 2> error.txt
```

`>`는 `stdout`을 `output.txt`로, `2>`는 `stderr`를 `error.txt`로 보낸다. 여기서 `2`는 파일 디스크립터 번호로, 관례상 `0`은 표준 입력(`stdin`), `1`은 `stdout`, `2`는 `stderr`를 가리킨다. 둘 다 화면에는 안 보이게 하고 로그 파일만 남기고 싶다면 이렇게 쓴다.

```sh
./hello > output.txt 2> error.txt
./hello > all.txt 2>&1  # stdout과 stderr를 같은 파일로 합치기
```

`2>&1`은 "`stderr`를 `stdout`이 가리키는 곳과 같은 곳으로 보내라"는 뜻이다. 순서가 중요해서, `./hello 2>&1 > all.txt`처럼 순서를 바꾸면 의도와 다르게 동작한다. 셸은 리다이렉션을 왼쪽에서 오른쪽으로 순서대로 처리하기 때문에, **`2>&1`이 먼저 오면 그 시점의 `stdout`(화면)으로 `stderr`를 보내고, 그 다음에야 `stdout`을 파일로 바꾸게 되어 `stderr`는 여전히 화면에 남는다.**

## 오류가 난 뒤 부분 결과를 남기지 않기

프로그램이 파일을 만들거나 데이터를 처리하는 도중 오류를 만나면, 이미 반쯤 써 놓은 결과를 그대로 둔 채 끝나 버리는 경우가 있다. 이렇게 되면 다음 실행에서 그 어중간한 파일을 "완성된 결과"로 착각하고 읽어 들이는 사고로 이어질 수 있다.

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    FILE *fp = fopen("result.txt", "w");
    if (fp == NULL) {
        fprintf(stderr, "파일을 열 수 없습니다\n");
        return 1;
    }

    if (fprintf(fp, "일부 결과\n") < 0) {
        fprintf(stderr, "쓰기 실패\n");
        fclose(fp);
        remove("result.txt");  // 반쯤 쓰인 파일을 남기지 않는다
        return 1;
    }

    fclose(fp);
    return 0;
}
```

원칙은 간단하다. 오류가 발생한 시점에 이미 만들어 둔 파일이나 자원이 있다면, 실패 경로에서 그걸 정리(닫기, 지우기, 되돌리기)한 다음에 종료해야 한다는 것이다. 임시 파일에 먼저 쓰고 전부 성공했을 때만 최종 이름으로 옮기는 방식(원자적 쓰기)도 같은 문제의식에서 나온 패턴이다.

## 셸 인자와 `argc`, `argv`

터미널에서 `./program arg1 arg2`처럼 프로그램 이름 뒤에 붙이는 값들을 명령줄 인자라고 부른다. C에서는 이 값들을 `main` 함수의 두 매개변수로 받는다.

```c
#include <stdio.h>

int main(int argc, char *argv[]) {
    for (int i = 0; i < argc; i++) {
        printf("argv[%d] = %s\n", i, argv[i]);
    }
    return 0;
}
```

```sh
gcc args.c -o args
./args hello world
# argv[0] = ./args
# argv[1] = hello
# argv[2] = world
```

### `argc`

`argc`(argument count)는 `argv` 배열에 담긴 문자열의 개수다. 여기에는 프로그램 이름 자체도 포함되기 때문에, "인자를 하나도 안 줬을 때"도 `argc`는 최소 1이다. 인자 개수를 검사할 때 이 점을 놓치고 `argc == 0`을 조건으로 쓰면 절대 참이 되지 않는 죽은 코드를 만들게 된다.

```c
if (argc < 2) {
    fprintf(stderr, "사용법: %s <파일이름>\n", argv[0]);
    return 1;
}
```

### `argv`

`argv`(argument vector)는 문자열 포인터의 배열이며, 마지막 원소 `argv[argc]`는 항상 `NULL`로 채워진다는 것이 표준에서 보장하는 규약이다. 이 덕분에 `argc` 없이도 `argv`만 순회하며 `NULL`을 만날 때까지 반복하는 코드가 가능하다.

```c
for (int i = 0; argv[i] != NULL; i++) {
    printf("%s\n", argv[i]);
}
```

`argv[0]`은 관례상 프로그램 자신이 어떻게 호출됐는지를 담고 있지만, 이건 셸이 넘겨주는 값일 뿐 프로그램이 강제할 수 있는 게 아니라서 전적으로 신뢰할 수는 없다.

### 따옴표는 왜 사라지는가

```sh
./args "hello world"
# argv[0] = ./args
# argv[1] = hello world
```

여기서 `argv[1]`에는 따옴표 없이 `hello world`라는 문자열 하나가 들어온다. 따옴표는 프로그램에 전달되는 데이터가 아니라, 셸이 인자를 몇 개로 쪼갤지 판단하는 데 쓰는 구분 기호이기 때문이다. 따옴표가 없었다면 셸은 공백을 기준으로 `hello`와 `world`를 서로 다른 두 개의 인자로 나눠 넘겼을 것이다.

```sh
./args hello world       # argc == 3, argv[1]="hello", argv[2]="world"
./args "hello world"     # argc == 2, argv[1]="hello world"
```

이 구분이 왜 필요한가 하면, 프로그램 입장에서는 "공백이 포함된 값 하나"와 "공백으로 나뉜 값 두 개"가 완전히 다른 의미일 수 있기 때문이다. 파일 이름에 공백이 들어 있는 경우가 대표적인 예로, 따옴표를 빠뜨리면 하나의 파일 이름이 서로 다른 두 인자로 쪼개져 프로그램이 엉뚱하게 동작한다.

## 수정과 실행 사이의 확인 순서

코드를 고치고 바로 결과부터 보려 하면, 정작 어느 단계에서 문제가 생겼는지 나중에 되짚기 어려워진다. 매번 다음 순서를 지키는 습관을 들이면 문제가 생겼을 때 원인의 범위를 빠르게 좁힐 수 있다.

1. 소스를 수정한다.
2. 컴파일한다. 이 단계에서 실패하면 실행 파일 자체가 갱신되지 않았다는 뜻이므로, 방금 실행한 건 이전 버전의 코드다.
3. 컴파일 경고를 훑는다. 경고가 있다는 건 컴파일러가 의심스러운 지점을 이미 짚어 준 것이다.
4. 실행한다.
5. 종료 상태(`$?`)와 출력(`stdout`, `stderr`)을 확인한다.

이 순서를 건너뛰고 곧장 실행 결과만 보는 습관이 붙으면, "코드는 고쳤는데 결과가 그대로"인 상황(재컴파일을 안 해서)과 "코드에 진짜 버그가 있는" 상황을 구분하지 못한 채 시간을 낭비하게 된다.

## 프로그램이 만들어지는 단계

`gcc hello.c -o hello`라는 한 줄의 명령은 사실 겉으로 보이지 않는 네 단계를 순서대로 거친다. 전처리 → 컴파일 → 어셈블 → 링크. 컴파일러는 이 네 단계를 자동으로 연결해서 실행해 주지만, 각 단계가 무슨 일을 하는지 알아야 나중에 나오는 오류 메시지가 어느 단계에서 온 것인지 구분할 수 있다.

### 전처리

전처리기는 `#include`, `#define` 같은 `#`으로 시작하는 지시문을 처리해 소스 코드를 확장한다. `#include <stdio.h>`는 이 시점에 `stdio.h` 파일의 내용을 그 자리에 그대로 갖다 붙이는 것이고, `#define` 매크로는 이 시점에 텍스트가 그대로 치환된다. 이 결과물을 직접 눈으로 보고 싶다면 `-E` 옵션을 쓴다.

```sh
gcc -E hello.c -o hello.i
```

### 컴파일

컴파일 단계(좁은 의미의)는 전처리를 마친 C 코드를 어셈블리어로 바꾼다. 이 시점에 문법 오류, 타입 오류처럼 C 언어 규칙에 어긋나는 문제들이 걸러진다. `-S` 옵션으로 이 단계까지의 결과물을 확인할 수 있다.

```sh
gcc -S hello.c -o hello.s
```

### 어셈블

어셈블러가 어셈블리어 코드를 기계어로 이루어진 목적 파일(object file, `.o`)로 바꾼다. 이 목적 파일은 아직 실행할 수 없다. 다른 목적 파일이나 라이브러리와 연결되지 않은, 조각난 상태이기 때문이다.

```sh
gcc -c hello.c -o hello.o
```

### 링크

링커는 하나 이상의 목적 파일과 필요한 라이브러리들을 하나로 엮어 최종 실행 파일을 만든다. `printf` 같은 표준 라이브러리 함수를 호출하는 코드가 실제 `printf` 구현과 연결되는 것도 이 단계에서 일어난다.

```sh
gcc hello.o -o hello
```

네 단계를 하나씩 실행하면 결과적으로 처음에 봤던 `gcc hello.c -o hello`와 같은 실행 파일이 만들어진다.

```sh
gcc -E hello.c -o hello.i
gcc -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello
```

## 실패 단계 구분하기

컴파일 명령이 실패했을 때 오류 메시지를 보면 이 네 단계 중 어디서 멈췄는지 알 수 있다. 어느 단계인지를 먼저 파악하면, 원인을 찾을 범위가 확 줄어든다.

### 전처리 오류

`#include` 대상 파일을 찾지 못하거나 매크로 문법이 잘못됐을 때 발생한다.

```
hello.c:1:10: fatal error: stdioo.h: No such file or directory
    1 | #include <stdioo.h>
```

`fatal error`와 함께 특정 헤더 파일을 찾을 수 없다는 메시지가 뜨면, 대부분 헤더 이름 오타이거나 `-I` 옵션으로 헤더 검색 경로를 추가해 줘야 하는 상황이다.

### 컴파일 오류

문법 오류, 선언되지 않은 변수 사용, 타입 불일치 등 C 언어 규칙 위반이 여기서 걸린다.

```
hello.c:3:5: error: expected ';' before 'return'
    2 |     int x = 5
    3 |     return 0;
```

메시지에 파일 이름과 줄 번호가 정확히 나오기 때문에, 대부분 그 줄이나 바로 앞 줄을 보면 원인을 찾을 수 있다. 세미콜론 누락처럼 실제 오류 지점보다 한 줄 앞에서 문제가 시작되는 경우도 흔하다.

### 링크 오류

목적 파일들을 하나로 묶는 과정에서 함수나 변수의 정의를 찾지 못할 때 발생한다. 흔히 "undefined reference" 형태로 나타난다.

```
/usr/bin/ld: hello.o: in function `main':
hello.c:(.text+0x1a): undefined reference to `foo'
```

이 오류는 문법상 문제가 없는데도 발생할 수 있다는 점이 컴파일 오류와 다르다. 함수를 선언만 하고 정의(구현)를 빠뜨렸거나, 필요한 라이브러리(예: 수학 함수를 쓰면서 `-lm`을 빠뜨리는 경우)를 링크 명령에 포함하지 않았을 때 흔히 발생한다.

```sh
gcc hello.c -o hello -lm   # 수학 라이브러리(libm) 링크
```

### 실행 오류

컴파일과 링크는 모두 성공했지만, 프로그램을 실행하는 도중 문제가 생기는 경우다. 배열 범위를 벗어난 접근, 널 포인터 역참조 같은 문제가 대표적이며, 셸에서는 보통 "Segmentation fault"로 나타난다.

```
Segmentation fault (core dumped)
```

컴파일러가 이런 오류를 미리 걸러내지 못하는 이유는, C가 배열 경계나 포인터 유효성을 실행 시점에 검사하지 않는 언어이기 때문이다. 이런 오류는 메시지만으로는 원인 위치를 알기 어려워서, 이후 디버거를 이용한 진단이 별도로 필요해진다.

## 오류 메시지를 읽는 기본 순서

컴파일이든 실행이든 오류가 나면 다음 순서로 읽는 습관을 들이면 좋다.

1. **가장 먼저 뜬 오류부터 본다**: 하나의 오류가 뒤이은 여러 줄의 오류를 연쇄적으로 유발하는 경우가 많아서, 마지막 줄이 아니라 맨 처음 오류가 진짜 원인인 경우가 대부분이다.
2. **파일 이름과 줄 번호를 확인한다**: 대부분의 오류 메시지는 `파일:줄:열` 형식으로 위치를 알려준다.
3. **어느 단계의 오류인지 구분한다**: 전처리, 컴파일, 링크, 실행 중 어디서 났는지에 따라 원인을 찾는 방향이 완전히 달라진다(앞 절 참고).
4. **메시지를 그대로 읽는다**: 컴파일러 오류 메시지는 대개 무엇이 왜 문제인지를 상당히 정확하게 설명해 준다. 메시지를 건너뛰고 코드부터 훑기보다, 먼저 메시지 자체를 문장으로 읽는 편이 빠르다.

## 기본 개발 습관

지금까지 다룬 내용을 하나의 흐름으로 묶으면 다음과 같다.

- 소스를 고칠 때마다 반드시 다시 컴파일한다. 실행 파일은 자동으로 갱신되지 않는다.
- 경고를 최대한 켠 채(`-Wall -Wextra`) 컴파일하고, 뜨는 경고를 무시하지 않는다.
- 실행 후에는 눈에 보이는 출력만이 아니라 종료 상태(`$?`)까지 확인한다.
- 오류가 나면 어느 단계(전처리/컴파일/링크/실행)인지부터 구분하고, 그 범위 안에서 원인을 찾는다.
- 오류가 발생한 실행 도중에 이미 만들어진 파일이나 자원이 있다면, 실패 경로에서 정리하고 끝낸다.

이 습관들은 개별로는 사소해 보이지만, 프로그램이 커지고 여러 파일로 나뉘면서 빌드 자체가 복잡해질수록(특히 이후 다룰 Makefile이나 여러 목적 파일을 엮는 빌드 과정에서) 문제를 빠르게 좁혀 나가는 데 그대로 이어진다.
