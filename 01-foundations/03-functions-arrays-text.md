# 함수, 배열, 문자열

## 함수 선언과 호출

C에서 함수를 쓰려면 컴파일러가 그 함수의 반환형과 매개변수 타입을 미리 알아야 한다. 함수를 호출하는 코드보다 먼저(또는 같은 번역 단위 어딘가에) 함수의 존재가 알려져 있지 않으면, 컴파일러는 암묵적으로 `int`를 반환하는 함수라고 가정하거나(오래된 C 표준) 아예 에러를 낸다.

```c
#include <stdio.h>

int add(int a, int b);   // 선언: "이런 함수가 존재한다"

int main(void) {
    int result = add(3, 4);   // 호출
    printf("%d\n", result);
    return 0;
}

int add(int a, int b) {   // 정의: 실제 몸체
    return a + b;
}
```

호출은 함수 이름 뒤에 괄호와 인자를 쓰는 문법이며, 인자의 개수와 타입은 선언과 일치해야 한다. 헤더 파일(`.h`)에 선언을 모아두고 여러 `.c` 파일에서 `#include`하는 것이 일반적인 구조다.

## 선언과 정의

선언(declaration)은 컴파일러에게 "이런 이름과 타입을 가진 것이 어딘가에 존재한다"고 알려주는 것이고, 정의(definition)는 실제로 메모리를 차지하거나 몸체를 갖는 실체를 만드는 것이다. 함수는 선언만 여러 번 반복해도 되지만 정의는 프로그램 전체에서 딱 한 번만 있어야 한다(One Definition Rule).

```c
// 선언: 여러 .c 파일에서 반복 가능
int square(int x);

// 정의: 링크되는 전체 프로그램에서 단 하나
int square(int x) {
    return x * x;
}
```

이 구분이 흐려지면 링크 단계에서 "multiple definition" 또는 "undefined reference" 에러를 만나게 된다. 헤더 파일에는 선언만 넣고, 정의는 `.c` 파일에 두는 관례가 여기서 나온다. 헤더가 여러 곳에서 `#include`되어도 정의가 중복되지 않도록 하기 위해서다.

## 값 전달과 포인터 전달

C는 함수 인자를 항상 값으로 전달(pass by value)한다. 함수 안에서 매개변수를 바꿔도 호출한 쪽의 원본 변수는 전혀 영향을 받지 않는다.

```c
void increment(int x) {
    x = x + 1;   // 지역 복사본만 바뀐다
}

int main(void) {
    int n = 5;
    increment(n);
    printf("%d\n", n);   // 여전히 5
}
```

호출한 쪽의 값을 실제로 바꾸고 싶다면, 그 변수의 주소를 넘기고 함수 안에서 포인터를 역참조해야 한다.

```c
void increment(int *x) {
    *x = *x + 1;   // 포인터가 가리키는 원본을 수정
}

int main(void) {
    int n = 5;
    increment(&n);
    printf("%d\n", n);   // 6
}
```

### 포인터도 값으로 전달된다

포인터를 넘긴다고 해서 전달 방식 자체가 달라지는 것은 아니다. 포인터 역시 하나의 값이고, 그 값(주소)이 복사되어 함수 안으로 들어간다. 함수 안에서 포인터 매개변수 자체를 다른 곳을 가리키게 바꿔도, 호출한 쪽이 들고 있던 포인터 변수는 바뀌지 않는다.

```c
void reassign(int *p) {
    int local = 100;
    p = &local;   // 이 함수 안의 지역 포인터 복사본만 바뀜
}

int main(void) {
    int a = 1;
    int *ptr = &a;
    reassign(ptr);
    // ptr은 여전히 &a를 가리킨다
}
```

포인터가 가리키는 대상을 바꾸고 싶은 게 아니라 포인터 자체(즉 그 포인터가 무엇을 가리키는지)를 바꾸고 싶다면, 포인터의 포인터(`int **`)를 넘겨야 한다. 이 구분을 헷갈리면 "함수에 포인터를 넘겼는데 왜 호출부의 포인터가 안 바뀌지"라는 흔한 혼란에 빠진다.

## 포인터와 소유권

포인터는 그 자체로는 "누가 이 메모리를 해제할 책임이 있는가"를 말해주지 않는다. C에는 소유권을 강제하는 언어 차원의 장치가 없으므로, 이는 순전히 코드를 작성하는 사람들 사이의 약속(convention)과 문서화로 유지된다.

```c
char *make_greeting(const char *name) {
    char *buf = malloc(strlen(name) + 8);
    if (!buf) return NULL;
    sprintf(buf, "Hello, %s", name);
    return buf;   // 호출자가 이 메모리의 소유자가 된다
}

int main(void) {
    char *msg = make_greeting("World");
    printf("%s\n", msg);
    free(msg);   // 소유자가 해제할 책임을 진다
}
```

여기서 `make_greeting`이 반환한 포인터는 힙에 할당된 메모리를 가리키고, 그 소유권은 호출자로 넘어간다는 것이 함수 이름이나 주석, 프로젝트의 관례로 전달되어야 한다. 이 약속이 문서화되지 않으면 두 곳에서 동시에 `free`를 호출하는 이중 해제(double free)나, 아무도 해제하지 않는 메모리 누수(leak)로 이어진다.

## 배열과 길이

C의 배열은 자기 길이를 스스로 기억하지 않는다. `int arr[10]`은 그냥 `int` 10개가 연속으로 놓인 메모리 블록일 뿐이고, "이 배열의 길이는 10이다"라는 정보는 컴파일 시점에 그 배열이 선언된 스코프에서만 알 수 있다.

```c
int arr[10];
size_t len = sizeof(arr) / sizeof(arr[0]);   // 10, 컴파일 타임에 계산됨
```

이 계산이 성립하는 이유는 `arr`가 아직 배열 타입 그대로 존재하는 스코프에 있기 때문이다. 배열이 함수의 매개변수로 넘어가는 순간 이 정보는 사라진다(다음 절 참고).

### `sizeof`로 함수 안에서 배열 길이를 구할 수 없는 이유

배열을 함수 매개변수로 선언하면, 컴파일러는 그것을 배열이 아니라 첫 원소를 가리키는 포인터로 취급한다(배열-포인터 decay). 따라서 함수 안에서 `sizeof`를 적용하면 배열 전체 크기가 아니라 포인터 하나의 크기(보통 8바이트)가 나온다.

```c
void print_len(int arr[10]) {
    printf("%zu\n", sizeof(arr));   // 8 (포인터 크기), 10 * sizeof(int)가 아니다!
}

int main(void) {
    int nums[10] = {0};
    printf("%zu\n", sizeof(nums));   // 40, 여기서는 진짜 배열이므로 다르다
    print_len(nums);
}
```

이 때문에 배열을 함수에 넘길 때는 길이를 별도의 매개변수로 항상 같이 넘겨야 한다.

```c
void process(int *arr, size_t len) {
    for (size_t i = 0; i < len; i++) {
        arr[i] *= 2;
    }
}
```

## 배열 인덱스의 유효 범위

`int arr[N]`의 유효한 인덱스는 `0`부터 `N - 1`까지다. `arr[N]`에 접근하는 것은 배열 경계를 벗어난 접근(out-of-bounds access)이며, C는 이를 컴파일 타임에도 런타임에도 자동으로 막아주지 않는다.

```c
int arr[5] = {1, 2, 3, 4, 5};
arr[5] = 100;   // 정의되지 않은 동작(undefined behavior), 컴파일은 되지만 위험하다
```

이런 접근은 크래시로 바로 드러날 수도 있고, 운 나쁘게 인접한 다른 변수의 메모리를 조용히 덮어써서 훨씬 나중에, 전혀 관계없어 보이는 곳에서 버그로 나타날 수도 있다. 반복문에서 `<=` 대신 `<`를 쓰는 습관, 그리고 길이를 넘길 때 정확한 값을 유지하는 것이 이 문제를 막는 기본 방어선이다.

## 문자열은 NUL로 끝나는 `char` 배열

C에는 별도의 문자열 타입이 없다. "문자열"이라고 부르는 것은 단지 `char` 배열이며, 그 끝을 표시하기 위해 값이 0인 바이트(`'\0'`, NUL 문자)를 마지막에 두는 관례를 따를 뿐이다.

```c
char s[6] = {'H', 'e', 'l', 'l', 'o', '\0'};
// 또는 더 흔하게:
char s2[] = "Hello";   // 컴파일러가 자동으로 '\0'을 붙여 길이 6짜리 배열을 만든다
```

`printf("%s", s)` 같은 문자열 관련 함수들은 모두 이 NUL 바이트를 만날 때까지 메모리를 읽어나가는 방식으로 동작한다. NUL이 없으면 그 함수는 배열의 끝을 넘어서까지 계속 읽어나가며, 이 역시 정의되지 않은 동작이다.

## `strlen`이 요구하는 전제

`strlen(s)`은 `s`가 가리키는 위치부터 시작해서 처음 만나는 `'\0'` 바이트까지의 거리를 센다. 이 함수는 `s`가 유효한 NUL 종료 문자열을 가리킨다는 것을 절대적으로 전제하며, 그 전제가 깨지면 함수는 배열 경계를 한참 넘어서까지 계속 읽어나간다.

```c
char buf[5] = {'a', 'b', 'c', 'd', 'e'};   // NUL이 없다!
size_t len = strlen(buf);   // 정의되지 않은 동작, buf 뒤 메모리를 계속 읽는다
```

이런 이유로 고정 크기 배열에 `strncpy`나 `snprintf` 같은 함수로 문자열을 채울 때는, 항상 마지막에 NUL이 실제로 들어갔는지 스스로 확인하는 습관이 필요하다. `strncpy`는 소스가 길면 NUL을 아예 안 붙이는 함정으로 유명하다.

## 문자열 공간과 마지막 NUL 바이트

`char` 배열에 길이 N인 문자열을 담으려면 배열 크기는 최소 N + 1이어야 한다. 문자 N개에 더해 NUL 바이트 하나가 추가로 필요하기 때문이다.

```c
char name[5];
strcpy(name, "Alice");   // "Alice"는 5글자 + NUL = 6바이트 필요, name은 5바이트뿐(버퍼 오버플로우)
```

```c
char name[6];
strcpy(name, "Alice");   // 정확히 맞다: A,l,i,c,e,\0
```

이 "+1을 잊는 실수"는 C에서 가장 흔한 버그 중 하나이며, 버퍼 오버플로우로 이어져 보안 취약점의 단골 원인이 된다. 배열을 선언할 때는 항상 "담을 문자 수 + 1"을 기준으로 크기를 잡아야 한다.

## 문자열 리터럴과 수정 가능 여부

`"Hello"`처럼 큰따옴표로 감싼 문자열 리터럴은 프로그램의 읽기 전용 메모리 영역에 저장된다. 이 리터럴을 `char *`로 받아서 수정하려고 하면 정의되지 않은 동작이 발생하며, 많은 환경에서 세그멘테이션 폴트로 즉시 드러난다.

```c
char *p = "Hello";
p[0] = 'h';   // 정의되지 않은 동작, 리터럴은 읽기 전용

char arr[] = "Hello";   // 이건 다르다, 스택에 만들어진 별개의 복사본(배열)
arr[0] = 'h';           // 안전하다
```

`char *p = "Hello"`와 `char arr[] = "Hello"`는 겉보기엔 비슷해 보여도 근본적으로 다르다. 전자는 리터럴을 가리키는 포인터이고, 후자는 리터럴의 내용을 복사해 만든 독립적인 배열이다. 리터럴을 수정할 계획이 있다면 반드시 배열 형태로 선언해야 한다.

## 배열과 포인터는 완전히 같은 것이 아니다

배열 이름은 대부분의 문맥에서 첫 원소를 가리키는 포인터로 "붕괴(decay)"하지만, 배열과 포인터는 같은 타입이 아니다. 가장 분명한 차이는 `sizeof`와 대입 가능 여부에서 드러난다.

```c
int arr[10];
int *p = arr; // 배열이 포인터로 decay하며 대입됨, 허용

sizeof(arr);  // 40 (int 10개)
sizeof(p);    // 8 (포인터 크기)

arr = p;      // 컴파일 에러! 배열 이름은 값처럼 대입할 수 없다(수정 불가능한 lvalue)
arr++;        // 이것도 컴파일 에러
```

배열은 스스로 메모리를 소유한 고정된 실체이고, 포인터는 어딘가를 가리키는 값일 뿐이라서 다른 곳을 가리키도록 재대입할 수 있다. "배열은 포인터와 같다"는 단순화된 설명은 함수 인자로 넘어갈 때의 decay 동작에만 해당하며, 배열 자체의 정체성까지 포인터와 같아지는 것은 아니다.

## `ctype` 함수와 음수 `char`

`<ctype.h>`의 `isalpha`, `isdigit`, `toupper` 같은 함수들은 인자로 `int` 값을 받는데, 이 값은 `unsigned char`로 표현 가능한 범위이거나 `EOF`여야 한다는 전제가 있다. 그런데 대부분의 플랫폼에서 `char`는 부호 있는(signed) 타입이므로, 8비트 중 최상위 비트가 켜진 문자(예: 확장 ASCII, 비 ASCII 바이트)는 음수 값으로 변환되어 이 전제를 깨뜨린다.

```c
char c = (char)200;         // 이 플랫폼에서 char가 signed라면 음수 값
if (isalpha(c)) { ... }     // 정의되지 않은 동작, 음수를 int로 넘김
```

안전하게 쓰려면 `char`를 `unsigned char`로 캐스팅한 뒤 `int`로 넘겨야 한다.

```c
if (isalpha((unsigned char)c)) { ... }   // 안전
```

이 문제는 ASCII 범위(0~127)의 문자만 다룰 때는 드러나지 않다가, 파일에서 읽은 바이트나 다국어 텍스트를 처리할 때 예상치 못한 크래시나 이상 동작으로 나타나는 경우가 많다.

## `struct`로 함께 변하는 값 묶기

여러 변수가 항상 함께 만들어지고, 함께 전달되고, 함께 의미를 이루는 경우 이를 개별 변수로 흩어놓기보다 `struct`로 묶으면 관계가 코드에 드러나고 실수로 하나만 넘기는 실수를 줄일 수 있다.

```c
// 흩어진 버전, point의 x, y가 항상 같이 다녀야 한다는 사실이 코드에 드러나지 않는다
void move(int x, int y, int dx, int dy);

// 묶은 버전
typedef struct {
    int x;
    int y;
} Point;

void move(Point *p, int dx, int dy) {
    p->x += dx;
    p->y += dy;
}
```

구조체로 묶으면 함수 시그니처가 짧아질 뿐 아니라, 이 값들이 개념적으로 하나의 단위라는 사실이 타입 시스템에 명시적으로 드러난다.

## 구조체 불변식은 자동으로 지켜지지 않는다

구조체의 필드들 사이에 "항상 성립해야 하는 관계"(불변식, invariant)가 있다면, C는 그것을 강제해주지 않는다. 구조체는 필드들의 단순한 묶음일 뿐이므로, 누구든 필드에 직접 접근해 불변식을 깨뜨릴 수 있다.

```c
typedef struct {
    int *data;
    size_t len;       // data가 가리키는 유효한 원소 개수, len과 실제 할당 크기가 항상 일치해야 한다
    size_t capacity;
} DynArray;

DynArray a = make_array(10);
a.len = 100;   // capacity를 넘어서는 값을 그냥 대입할 수 있다, 불변식이 깨졌지만 컴파일러는 모른다
```

이런 불변식을 지키려면, 필드를 직접 건드리지 않고 반드시 정해진 함수(생성자/접근자/수정자 역할을 하는 함수들)를 통해서만 구조체를 조작하도록 관례를 정하고, 그 함수들 내부에서 불변식이 깨지지 않는지 검사해야 한다. C++의 접근 제어자 같은 언어 차원의 강제가 없는 만큼, 이 규율은 전적으로 코드를 쓰는 사람의 몫이다.

## 함수 이름은 실제 동작을 드러내기

함수 이름은 그 함수가 무엇을 하는지, 특히 부수 효과(원본을 수정하는지, 메모리를 할당하는지, 실패할 수 있는지)를 최대한 정직하게 드러내야 한다. `get_name()`처럼 단순 조회처럼 보이는 이름이 실제로는 매번 새로 메모리를 할당한다면, 호출하는 쪽은 그 사실을 모른 채 반환값을 해제하지 않아 메모리 누수를 만들기 쉽다.

```c
// 오해를 부르는 이름, "get"은 보통 그냥 읽기만 한다는 인상을 준다
char *get_name(void) {
    char *buf = malloc(64);
    strcpy(buf, "Alice");
    return buf;   // 실제로는 할당까지 한다
}

// 더 정직한 이름
char *create_name_copy(void) { ... }
```

마찬가지로 정렬 함수가 원본 배열을 제자리에서(in-place) 바꾸는지, 아니면 정렬된 새 배열을 만들어 반환하는지도 이름에서 드러나야 한다(`sort_in_place` vs `sorted_copy`). 이름이 동작을 정확히 반영하지 않으면, 코드를 읽는 사람은 함수 몸체를 매번 열어봐야만 안전하게 쓸 수 있다.

## 반환값과 출력 매개변수

함수가 호출자에게 결과를 돌려주는 방법은 크게 두 가지다. 하나는 `return`으로 값을 하나 돌려주는 것이고, 다른 하나는 포인터 매개변수를 받아서 그 포인터가 가리키는 위치에 결과를 써넣는 것(출력 매개변수, output parameter)이다.

```c
// 반환값 방식: 결과가 하나뿐일 때 자연스럽다
int square(int x) {
    return x * x;
}

// 출력 매개변수 방식: 결과를 여러 개 돌려주거나, 실패 여부도 함께 알려야 할 때
bool divide(int a, int b, int *result) {
    if (b == 0) return false;
    *result = a / b;
    return true;
}
```

반환값은 하나만 돌려줄 수 있으므로, 결과가 여러 개이거나 "성공했는지 여부"와 "실제 값"을 동시에 전달해야 할 때는 출력 매개변수를 쓰고 반환값은 성공/실패 표시에 쓰는 패턴이 흔하다.

## 출력 매개변수 패턴을 호출하는 방법

출력 매개변수를 받는 함수를 호출할 때는, 결과를 담을 변수를 먼저 준비하고 그 변수의 주소를 넘긴다.

```c
int result;
if (divide(10, 2, &result)) {
    printf("%d\n", result);   // 5
} else {
    printf("division by zero\n");
}
```

여기서 흔한 실수는 초기화되지 않은 포인터를 넘기거나(`int *result;` 뒤 `divide(10, 2, result)`처럼 주소가 아니라 쓰레기 값을 넘기는 것), 함수가 실패를 반환했는데도 출력 매개변수의 값을 그대로 신뢰해버리는 것이다. 반환값으로 성공 여부를 반드시 먼저 확인한 뒤에 출력 매개변수를 읽어야 한다.

## `const`가 의미하는 것

매개변수나 포인터 선언에 붙은 `const`는 "이 값(또는 이 포인터가 가리키는 대상)을 통해서는 수정하지 않겠다"는 약속을 컴파일러가 강제하도록 만든다. `const char *p`는 "`p`를 통해 가리키는 문자를 바꾸지 않겠다"는 뜻이고, `char *const p`는 "`p` 자체가 다른 곳을 가리키도록 바뀌지 않겠다"는 뜻으로, 이 둘은 다르다.

```c
void print(const char *s) {   // s가 가리키는 내용을 읽기만 하겠다는 신호
    printf("%s\n", s);
}

void bad(const char *s) {
    s[0] = 'X';   // 컴파일 에러, const를 어기는 시도를 컴파일러가 잡아준다
}
```

함수 시그니처에 `const`를 붙이는 것은 단순한 습관이 아니라, 그 함수가 인자를 읽기만 할 뿐 수정하지 않는다는 것을 호출하는 쪽에게 컴파일 타임에 보장해주는 문서화 수단이다. 문자열 리터럴을 받을 매개변수는 특히 `const char *`로 선언하는 것이 관례다. 리터럴 자체가 원래 수정 불가능하기 때문이다.

## 함수 인터페이스를 읽는 순서

낯선 함수 시그니처를 처음 마주쳤을 때, 아래 순서로 훑으면 그 함수를 안전하게 쓰기 위해 필요한 정보를 빠짐없이 파악할 수 있다.

### 반환형 확인

먼저 반환형이 무엇인지, 그리고 그것이 실제 결과 값인지 아니면 단순히 성공/실패를 나타내는 상태 코드인지를 구분한다. `int`를 반환하는 함수가 실제 계산 결과를 돌려주는지, 아니면 0/음수로 성공/실패만 알려주는지는 함수마다 다르다.

### 입력 매개변수 확인

각 매개변수가 함수 안에서 읽히기만 하는지(`const`가 붙어 있는지) 확인한다. `const`가 없는 포인터 매개변수는 함수가 그 내용을 바꿀 수도 있다는 신호이므로 더 주의해서 봐야 한다.

### 출력 매개변수 확인

`const`가 붙지 않은 포인터 매개변수 중, 함수가 값을 써넣도록 의도된 것이 있는지 찾는다. 보통 이름(`out_`, `result` 등)이나 문서 주석에서 힌트를 얻을 수 있다.

### `NULL` 허용 여부 확인

각 포인터 매개변수에 `NULL`을 넘겨도 되는지, 아니면 반드시 유효한 주소여야 하는지 확인한다. 이는 함수 문서나 구현을 보지 않으면 시그니처만으로는 알 수 없는 경우가 많으므로, 문서화되어 있지 않다면 보수적으로 `NULL`을 넘기지 않는 쪽을 기본으로 삼는다.

### 실패 시 상태 확인

함수가 실패했을 때(`false`나 `NULL`, 음수 등을 반환했을 때) 출력 매개변수나 다른 부수 효과가 어떤 상태에 놓이는지 확인한다. 실패 시 출력 매개변수가 미정의 상태로 남는 함수도 있고, 항상 안전한 기본값으로 초기화해주는 함수도 있다. 이 차이를 모르고 실패 케이스에서도 결과를 읽으면 정의되지 않은 값을 쓰게 된다.

### 소유권 확인

함수가 포인터를 반환하거나 포인터 매개변수를 통해 무언가를 건네줄 때, 그 메모리의 소유권이 호출자에게 넘어가는지(그래서 호출자가 `free`해야 하는지), 아니면 함수 내부나 다른 어딘가가 소유권을 계속 갖고 있는지(그래서 호출자는 그저 빌려 쓰기만 하고 해제하면 안 되는지) 확인한다. 이 정보가 문서화되어 있지 않다면 함수 이름의 관례(`create_`, `new_`, `get_` 등)나 프로젝트 전체의 컨벤션을 근거로 판단해야 하며, 확신이 없으면 먼저 확인하고 넘어가는 것이 이중 해제나 메모리 누수를 막는 가장 안전한 방법이다.
