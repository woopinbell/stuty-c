# 입력 오류와 디버깅

## 실패 종류

프로그램이 잘못 동작하는 원인은 성격이 다른 몇 가지로 나뉜다.

- **입력 오류**: 사용자나 외부 시스템이 프로그램이 기대하지 않는 값을 준 경우. `atoi("abc")`처럼 숫자를 기대하는데 문자열이 들어오는 상황이 대표적이다.
- **논리 오류(버그)**: 코드가 컴파일도 되고 크래시도 안 나지만, 의도한 것과 다른 결과를 낸다. 내부 비즈니스 로직이 잘못 작성된 경우.
- **자원 확보 실패**: `malloc`, `fopen`처럼 운영체제 자원을 요청했는데 거절당한 경우.
- **정의되지 않은 동작(UB)**: 배열 범위를 벗어난 접근, 초기화하지 않은 변수 읽기처럼 C 표준이 결과를 보장하지 않는 코드. 크래시가 나기도 하고, 아무 문제 없이 동작하는 것처럼 보이기도 한다.
- **환경 실패**: 디스크가 꽉 찼다거나 네트워크가 끊긴 경우처럼 코드 자체는 옳아도 실행 환경이 요구를 못 채워주는 상황.

이 구분이 중요한 이유는 대응 방법이 서로 다르기 때문이다. 입력 오류는 검증 코드로 막고, UB는 sanitizer로 잡고, 자원 실패는 반환값 확인으로 처리한다. 원인을 먼저 분류하지 않고 무작정 디버거부터 켜면 엉뚱한 곳을 오래 들여다보게 된다.

## 입력 검증의 기본 원칙

- **경계에서 검증한다**: 외부에서 들어온 값이 프로그램 내부로 퍼지기 전, 가장 먼저 만나는 지점에서 걸러낸다. 함수 안쪽 깊은 곳에서 뒤늦게 검사하면 이미 잘못된 값이 여러 곳에 퍼진 뒤일 수 있다.
- **빨리 실패한다(fail fast)**: 잘못된 입력을 발견하면 그 자리에서 즉시 오류로 처리한다. "일단 진행하다가 문제가 생기면 그때 처리"하는 방식은 오류 발생 지점과 원인 지점이 멀어져 디버깅을 어렵게 만든다.
- **외부 입력은 절대 신뢰하지 않는다**: 명령줄 인자, 환경 변수, 파일 내용, 네트워크로 받은 데이터는 모두 "적대적일 수 있는 입력"으로 취급한다.
- **"형식이 잘못됨"과 "범위를 벗어남"을 구분한다**: `"12x"`처럼 애초에 숫자가 아닌 경우와, `"999999999999"`처럼 숫자이긴 하지만 `int` 범위를 벗어나는 경우는 원인이 다르므로 오류 메시지도 다르게 준다.

```c
long parse_port(const char *s) {
    char *end;
    errno = 0;
    long v = strtol(s, &end, 10);
    if (end == s || *end != '\0') {
        fprintf(stderr, "포트 번호 형식이 아닙니다: %s\n", s);
        exit(EXIT_FAILURE);
    }
    if (errno == ERANGE || v < 1 || v > 65535) {
        fprintf(stderr, "포트 범위(1-65535)를 벗어났습니다: %s\n", s);
        exit(EXIT_FAILURE);
    }
    return v;
}
```

## `atoi`보다 `strtol`을 사용하는 이유

`atoi`는 변환에 실패해도 알려줄 방법이 없다. `atoi("0")`도 `0`을 반환하고, `atoi("hello")`도 `0`을 반환한다. 두 경우가 똑같은 반환값을 내는 이상, 호출한 쪽에서는 "입력이 정말 `0`이었는지" 아니면 "변환이 실패해서 `0`이 나온 것인지" 구분할 방법이 없다. 게다가 `atoi`는 오버플로가 나면 동작이 표준상 정의되지 않는다.

`strtol`은 세 가지를 제공해서 이 문제를 해결한다.

1. 몇 번째 문자까지 숫자로 읽었는지 알려주는 `endptr`.
2. 범위를 벗어났을 때 `ERANGE`로 설정되는 `errno`.
3. `LONG_MIN`/`LONG_MAX`로 포화되는(saturate) 명확히 정의된 오버플로 동작.

```c
// atoi: 오류를 구분할 수 없다
int a = atoi("abc"); // 0
int b = atoi("0");   // 0, a와 구분 불가능

// strtol: endptr와 errno로 구분 가능
char *end;
errno = 0;
long v = strtol("abc", &end, 10);
// end == "abc" (한 글자도 못 읽음) → 변환 실패로 판단 가능
```

숫자만 다루는 아주 단순한 스크립트성 코드가 아니라면, 사용자 입력을 다루는 실무 코드에서는 `atoi`를 쓸 이유가 거의 없다.

## `strtol` 검사 순서 정리

`strtol` 호출 결과를 제대로 검사하려면 순서가 중요하다.

1. **호출 전에 `errno`를 `0`으로 초기화한다.** `strtol`은 성공 시 `errno`를 건드리지 않으므로, 이전 호출에서 남은 값이 그대로 있으면 오판할 수 있다.
2. **`strtol`을 호출한다.**
3. **`endptr`로 "한 글자도 못 읽었는지" 확인한다.** `end == str`이면 숫자로 읽은 문자가 하나도 없다는 뜻이다.
4. **`errno == ERANGE`로 오버플로/언더플로를 확인한다.**
5. **`*endptr`가 원하는 종결 문자인지 확인한다.** 문자열 전체가 숫자이길 기대한다면 `*end == '\0'`이어야 하고, 뒤에 다른 내용이 와도 되는 형식(`"123,456"`처럼 구분자가 있는 경우)이라면 그에 맞는 문자를 확인한다.

```c
errno = 0;
char *end;
long v = strtol(input, &end, 10);

if (end == input) {
    // 1) 숫자를 전혀 못 읽음
} else if (errno == ERANGE) {
    // 2) long 범위를 벗어남
} else if (*end != '\0') {
    // 3) 숫자 뒤에 예상 못한 문자가 있음, 예: "123abc"
} else {
    // 성공, v를 신뢰하고 사용
}
```

이 순서를 뒤바꾸면 문제가 생긴다. 예컨대 `errno` 검사를 먼저 하고 `endptr` 검사를 생략하면, `"123abc"`처럼 앞부분만 숫자인 입력을 성공으로 잘못 판단하게 된다.

## 오류 메시지와 종료 상태

오류를 알리는 방법은 두 채널로 나뉜다.

- **오류 메시지**: `stderr`로 출력하는 사람이 읽는 텍스트. `stdout`이 아니라 `stderr`로 보내야 하는 이유는, 파이프라인에서 정상 출력과 오류 메시지가 섞이지 않게 하기 위해서다 (`prog > out.txt`로 리다이렉트해도 오류 메시지는 여전히 화면에 보여야 한다).
- **종료 상태(exit status)**: `exit()`이나 `return`으로 프로그램이 셸에 돌려주는 정수값. 관례상 `0`은 성공, `0`이 아닌 값은 실패를 뜻한다. `<stdlib.h>`의 `EXIT_SUCCESS`(`0`)와 `EXIT_FAILURE`(보통 `1`)를 매직 넘버 대신 쓴다.

```c
if (argc < 2) {
    fprintf(stderr, "사용법: %s <파일명>\n", argv[0]);
    return EXIT_FAILURE;
}
```

### 종료 상태는 메시지와 별개의 인터페이스다

셸 스크립트나 CI 파이프라인은 프로그램의 출력 문자열을 파싱해서 성공 여부를 판단하지 않는다. `$?` (또는 `if program; then ...`)로 종료 상태만 확인한다. 즉 오류 메시지는 사람을 위한 것이고, 종료 상태는 프로그램을 위한 것이다.

이 둘을 혼동하면 실제로 벌어지는 문제가 있다. 오류가 났는데 메시지만 출력하고 `return 0`으로 끝내버리면, 사람이 화면을 직접 보지 않는 한(자동화된 스크립트에서 실행되는 경우) 실패를 아무도 감지하지 못한다.

```c
// 잘못된 예: 오류 메시지는 냈지만 종료 상태는 성공으로 보고
fprintf(stderr, "파일을 열 수 없습니다\n");
return 0; // 셸에서는 이 프로그램이 성공했다고 판단한다
```

## 오류 메시지와 자동 테스트

테스트 코드에서 오류 메시지를 검증할 때는 사람이 눈으로 콘솔을 읽는 방식이 아니라 프로그램적으로 확인해야 한다.

- 자식 프로세스를 실행하고 `stderr`를 파이프로 캡처해 특정 문자열이 포함되는지 검사한다.
- 종료 상태를 `waitpid` 등으로 확인해 기대한 값(`EXIT_FAILURE` 등)과 비교한다.
- 메시지 문구의 정확한 워딩보다는 "실패 케이스에서 0이 아닌 종료 상태가 나오는가", "핵심 키워드가 메시지에 포함되는가" 정도를 검증 대상으로 삼는 편이 문구가 바뀌어도 테스트가 쉽게 깨지지 않는다.

```c
// 테스트 코드에서: 실패 케이스가 정말 실패로 보고되는지 확인
int status = system("./myprog --bad-flag 2>/tmp/err.txt");
assert(WIFEXITED(status) && WEXITSTATUS(status) != 0);
```

## 상태를 변경하기 전에 입력 검증하기

입력을 다 검증하기 전에 전역 상태나 파일, 데이터 구조를 먼저 바꾸기 시작하면, 검증 중간에 오류가 발견됐을 때 이미 절반만 바뀐 상태가 남는다. 이걸 되돌리는(rollback) 코드를 따로 짜야 하고, 롤백 코드 자체에도 버그가 생길 여지가 늘어난다.

```c
// 나쁜 예: 검증 중간에 이미 파일에 쓰기 시작
void apply_config(const char *raw) {
    FILE *f = fopen("config.txt", "w");
    fputs(raw, f);          // 아직 값이 유효한지 확인 전인데 이미 씀
    if (!is_valid(raw)) {   // 여기서 실패하면 config.txt는 이미 오염됨
        fclose(f);
        return;
    }
    fclose(f);
}

// 좋은 예: 검증을 먼저 끝내고, 통과한 뒤에만 상태를 바꾼다
void apply_config(const char *raw) {
    if (!is_valid(raw)) {
        return; // 아무 상태도 바뀌지 않았다
    }
    FILE *f = fopen("config.txt", "w");
    fputs(raw, f);
    fclose(f);
}
```

가능하면 "검증을 전부 마친 뒤에만 상태를 바꾸는 함수"와 "실제로 상태를 바꾸는 함수"를 분리해 두면 이 원칙을 지키기 쉬워진다.

## 자원 확보 실패

`malloc`, `fopen`, `open` 같은 함수는 운영체제로부터 자원(메모리, 파일 디스크립터)을 요청한다. 요청이 거절되면 이들은 각각 `NULL`이나 `-1`을 반환한다. 이 반환값을 확인하지 않고 바로 사용하면 크래시로 이어진다.

```c
FILE *f = fopen("data.txt", "r");
if (!f) {
    perror("data.txt를 열 수 없습니다");
    return EXIT_FAILURE;
}

char *buf = malloc(size);
if (!buf) {
    fprintf(stderr, "메모리 할당 실패 (%zu바이트)\n", size);
    fclose(f); // 이미 확보한 다른 자원은 정리하고 나간다
    return EXIT_FAILURE;
}
```

자원 확보 실패를 다룰 때 흔히 놓치는 부분은, 여러 자원을 순서대로 확보하다가 두 번째에서 실패했을 때 첫 번째로 확보한 자원을 정리해야 한다는 점이다. 위 예시에서 `malloc`이 실패했을 때 이미 열어둔 `f`를 `fclose`하지 않으면 파일 디스크립터가 새는(leak) 것과 같다.

## 최소 재현 사례 만들기

버그를 만난 실제 입력이 수백 줄짜리 파일이나 복잡한 시나리오라면, 디버깅을 시작하기 전에 먼저 그 문제를 재현하는 가장 작은 입력으로 줄인다.

절차는 대략 다음과 같다.

1. 문제가 재현되는 상태에서 시작한다.
2. 입력의 절반을 지워보고 여전히 재현되는지 확인한다.
3. 재현되면 그 절반으로 계속 좁혀나가고, 재현이 안 되면 지운 절반을 되돌리고 다른 절반을 지워본다.
4. 더 이상 줄일 수 없을 때까지 반복한다.

이 방식을 델타 디버깅(delta debugging)이라 부른다. 손으로 하기 번거로우면 절반씩 지워보는 이 과정을 스크립트로 자동화할 수도 있다.

최소 재현 사례가 중요한 이유는, 코드 3줄에서 재현되는 버그와 코드 300줄에서 재현되는 버그는 원인을 찾는 데 걸리는 시간이 자릿수 단위로 다르기 때문이다. 또한 최소 재현 사례는 그대로 회귀 테스트로 남길 수 있다.

## 재현되지 않는 문제를 다룰 때

가끔씩만 발생하거나, 디버거를 붙이면 사라지는 버그는 보통 다음 중 하나가 원인이다.

- **초기화하지 않은 메모리를 읽는 경우**: 그 메모리에 우연히 어떤 값이 남아있는지에 따라 결과가 달라진다.
- **경쟁 상태(race condition)**: 스레드 실행 순서에 따라 결과가 바뀐다.
- **타이밍에 의존하는 코드**: 디버거가 실행 속도를 늦추면 타이밍이 달라져 버그가 숨는다(하이젠버그).

대응 전략:

- AddressSanitizer, ThreadSanitizer, Valgrind처럼 문제가 되는 메모리 접근을 "일어난 즉시" 잡아주는 도구를 쓴다. 재현이 안 될 때 진가를 발휘하는 것이 이런 도구들이다. 증상이 나타나는 시점이 아니라 원인이 발생하는 시점에서 잡아주기 때문이다.
- 같은 입력으로 반복 실행하는 스트레스 테스트 루프를 돌려 발생 확률을 높인다.
- 난수를 쓰는 코드라면 시드(seed)를 고정해서 같은 실행을 재현할 수 있게 만든다.
- print문을 추가하는 것 자체가 타이밍을 바꿔 버그를 숨길 수 있다는 점을 염두에 둔다.

## 디버그 빌드

디버거로 제대로 조사하려면 컴파일 방식부터 맞춰야 한다. 최적화가 켜진 배포용 빌드로는 디버거가 소스 코드와 실행 흐름을 일치시키지 못해 헛다리를 짚기 쉽다.

```sh
gcc -g -O0 -Wall -Wextra -o myprog myprog.c
```

### `-g`

디버그 심볼(주로 DWARF 형식)을 실행 파일에 넣는다. 이 정보가 있어야 디버거가 기계어 주소를 소스 코드의 파일명, 줄 번호, 변수 이름으로 되돌려 보여줄 수 있다. `-g` 없이 컴파일하면 디버거는 `print x` 같은 명령에 "변수를 찾을 수 없다"고 답한다.

### `-O0`

최적화를 끈다. 최적화가 켜지면 컴파일러가 변수를 레지스터에만 두고 메모리에 안 쓰거나, 함수를 인라인하거나, 코드 순서를 재배치한다. 그 결과 소스 코드 한 줄과 실제 실행되는 기계어 사이의 대응 관계가 무너져서, `step`으로 한 줄씩 따라가도 소스와 다른 곳을 넘나드는 것처럼 보이거나 `print`로 봐야 할 변수가 "최적화되어 사라짐(optimized out)"으로 나온다. `-O0`은 이런 왜곡을 없애 디버거가 소스 코드 그대로를 보여주게 한다.

## 디버거를 사용할 때의 기본 생각

디버거는 무작정 이곳저곳 눌러보는 도구가 아니라, 가설을 검증하는 도구다.

1. 먼저 "몇 번째 줄에서, 어떤 변수가 어떤 값이길래 문제가 생겼을 것"이라는 가설을 세운다.
2. 그 가설을 확인할 수 있는 지점에 중단점을 건다.
3. 실제 값을 확인해 가설이 맞는지 틀리는지 판단한다.
4. 틀렸다면 그 정보를 바탕으로 다음 가설을 세운다.

가설 없이 아무 데나 중단점을 걸고 한 줄씩 `next`만 누르는 방식은 큰 프로그램에서는 시간이 오래 걸리고, 정작 중요한 순간을 지나쳐 버리기 쉽다.

## GDB 기본 사용

```sh
gdb ./myprog
```

자주 쓰는 명령:

- `run` (또는 `r`): 프로그램 실행. 인자가 필요하면 `run arg1 arg2`.
- `break 함수명` 또는 `break 파일:줄번호`: 중단점 설정.
- `next` (`n`): 한 줄 실행, 함수 호출은 안으로 들어가지 않고 통째로 실행.
- `step` (`s`): 한 줄 실행, 함수 호출을 만나면 그 안으로 들어감.
- `print 변수` (`p`): 현재 값 출력.
- `backtrace` (`bt`): 현재 호출 스택 출력.
- `continue` (`c`): 다음 중단점까지 계속 실행.

```
(gdb) break main
(gdb) run
(gdb) next
(gdb) print argc
$1 = 2
(gdb) continue
```

## LLDB 기본 사용

LLDB는 GDB와 개념은 같고 명령 이름만 다르다.

```sh
lldb ./myprog
```

| 동작 | GDB | LLDB |
|---|---|---|
| 실행 | `run` / `r` | `run` / `r` |
| 중단점 | `break 함수명` | `breakpoint set -n 함수명` |
| 한 줄(호출 skip) | `next` / `n` | `next` / `n` |
| 한 줄(호출 진입) | `step` / `s` | `step` / `s` |
| 값 출력 | `print 변수` | `print 변수` (또는 `p`) |
| 호출 스택 | `backtrace` | `bt` |
| 계속 실행 | `continue` / `c` | `continue` / `c` |

```
(lldb) breakpoint set -n main
(lldb) run
(lldb) next
(lldb) print argc
(lldb) bt
```

macOS에서는 시스템 기본 컴파일러(clang)와 짝을 이루는 LLDB를 쓰는 경우가 많고, 리눅스에서는 GDB가 더 흔하지만 둘 다 큰 프로젝트에서 함께 쓰이므로 명령 대응을 알아두면 편하다.

## 중단점을 어디에 둘 것인가

- **함수 진입점**: 그 함수가 애초에 호출되는지, 어떤 인자로 호출되는지부터 확인하고 싶을 때.
- **의심되는 줄 바로 앞**: 크래시나 이상 동작이 일어나는 줄을 알고 있다면, 그 직전에 걸어서 상태를 확인한다.
- **조건부 중단점**: 반복문이 수천 번 도는데 특정 조건에서만 문제가 생긴다면, 매번 멈추는 대신 조건을 걸어 그 순간에만 멈추게 한다.

```
(gdb) break process_item if i == 42
```

- **watchpoint**: 특정 변수나 메모리 위치의 값이 바뀌는 순간에 멈춘다. "이 변수가 대체 어디서 이상한 값으로 바뀌는지 모르겠다"는 상황에 유용하다.

```
(gdb) watch counter
```

중단점을 너무 많이 걸어두면 `continue`를 반복해서 누르는 것 자체가 피곤해진다. 가설에 필요한 지점만 최소한으로 거는 편이 낫다.

## 호출 스택 읽기

`backtrace`(`bt`)는 현재 실행 지점부터 `main`까지 이어지는 함수 호출 사슬을 프레임(frame) 단위로 보여준다. 맨 위(`#0`)가 가장 안쪽, 즉 현재 실행 중인 함수다.

```
(gdb) bt
#0  validate_input (s=0x0) at parser.c:42
#1  0x0000555555555230 in parse_line (line=0x7fffffffe1a0 "") at parser.c:78
#2  0x0000555555555310 in main (argc=2, argv=0x7fffffffe2a8) at main.c:15
```

이 예시에서는 `main`이 `parse_line`을 불렀고, `parse_line`이 `validate_input`을 불렀는데, `validate_input`에 `NULL`(`s=0x0`)이 전달됐다는 사실을 한눈에 알 수 있다.

주의할 점은 **크래시가 일어난 위치(`#0`)가 항상 근본 원인의 위치는 아니라는 것**이다. `#0`은 증상이 드러난 곳이고, 진짜 원인(여기서는 왜 `parse_line`이 `NULL`을 넘겼는가)은 `frame 1`, `frame 2`로 옮겨가며(`up`, `down` 명령) 확인해야 나온다.

## AddressSanitizer와 UndefinedBehaviorSanitizer

Sanitizer는 컴파일 시점에 코드에 검사 로직을 자동으로 삽입해서, 잘못된 메모리 접근이나 정의되지 않은 동작이 "실제로 일어나는 그 순간" 프로그램을 즉시 중단시키고 원인을 알려주는 도구다. 버그의 증상(크래시, 이상한 값)이 아니라 원인 발생 지점에서 바로 잡아준다는 점이 디버거만으로 찾는 것과 결정적으로 다르다.

### AddressSanitizer

```sh
gcc -fsanitize=address -g -O0 -o myprog myprog.c
```

메모리 관련 오류를 잡는다:

- 버퍼 오버플로 (배열 범위를 벗어난 읽기/쓰기)
- use-after-free (해제한 메모리를 다시 씀)
- double free (같은 메모리를 두 번 `free`)
- 메모리 누수 (프로그램 종료 시 자동으로 보고)

```c
int *arr = malloc(4 * sizeof(int));
arr[4] = 1; // 범위를 1칸 벗어남, ASan이 즉시 잡아냄
```

### UndefinedBehaviorSanitizer

```sh
gcc -fsanitize=undefined -g -O0 -o myprog myprog.c
```

메모리 접근이 아닌, C 표준이 결과를 정의하지 않는 연산들을 잡는다:

- 부호 있는 정수 오버플로
- `NULL` 포인터 역참조
- 정렬(alignment)이 맞지 않는 메모리 접근
- 0으로 나누기

```c
int x = INT_MAX;
x = x + 1; // 부호 있는 정수 오버플로, UBSan이 즉시 보고
```

두 sanitizer는 동시에 켜서 쓰는 경우가 많다: `-fsanitize=address,undefined`.

## sanitizer의 한계

- **실행된 코드 경로만 검사한다**: sanitizer는 정적 분석이 아니라 런타임 검사이므로, 테스트가 실행하지 않은 코드 경로에 있는 버그는 잡지 못한다. 테스트 커버리지가 낮으면 sanitizer를 켜도 소용이 없다.
- **성능 오버헤드가 크다**: 실행 속도가 몇 배 느려질 수 있어 배포용 빌드에는 보통 포함하지 않는다.
- **모든 UB를 잡지는 못한다**: 표준이 정의하지 않는 동작이라고 전부 감지 가능한 것은 아니다. 일부는 우연히 "정상적으로 보이는" 결과를 내면서 지나간다.
- **코드 리뷰나 설계 검토를 대체하지 않는다**: 논리적으로 틀렸지만 메모리 접근이나 UB와 무관한 버그(예: 요구사항을 잘못 이해한 로직)는 sanitizer가 애초에 다루는 범위 밖이다.

## sanitizer 보고서를 읽는 순서

sanitizer가 출력하는 보고서는 정보량이 많아서 처음엔 압도되기 쉽다. 다음 순서로 읽으면 정리가 된다.

1. **오류 종류를 먼저 확인한다** (`heap-buffer-overflow`, `use-after-free`, `signed-integer-overflow` 등). 무엇을 찾아야 하는지가 여기서 정해진다.
2. **맨 위 스택 트레이스(오류가 일어난 지점)를 본다.** 어느 함수, 어느 줄에서 문제가 감지됐는지.
3. **`use-after-free`나 `heap-buffer-overflow`라면 할당/해제 스택 트레이스를 본다.** ASan은 "이 메모리가 어디서 할당됐고 어디서 해제됐는지"까지 같이 보여주는 경우가 많다. 이 정보가 진짜 원인 지점을 가리킬 때가 많다.
4. **오류 지점에서 시작해 할당/해제 지점까지 코드 흐름을 따라가며 왜 어긋났는지 재구성한다.**

가장 아래에 붙는 "요약(SUMMARY)" 줄만 보고 판단하지 말고, 최소한 두 번째 항목까지는 항상 읽는다.

## 경고를 오류로 다루기

```sh
gcc -Wall -Wextra -Werror -o myprog myprog.c
```

`-Wall -Wextra`는 흔한 실수 패턴(초기화 안 된 변수 사용 가능성, 부호 비교, 사용하지 않는 변수 등)에 대해 경고를 켠다. `-Werror`는 그 경고를 컴파일 오류로 격상시켜, 경고가 하나라도 있으면 빌드 자체가 실패하게 만든다.

경고를 그냥 경고로 남겨두면 시간이 지날수록 "늘 나오던 경고니까 무시해도 된다"는 학습된 무시가 쌓이고, 그 사이에 진짜 심각한 경고가 섞여 들어와도 눈에 띄지 않는다. `-Werror`로 강제하면 경고가 발생하는 즉시 처리하지 않고는 넘어갈 수 없다.

## 디버깅용 빌드와 배포용 빌드의 차이

| 항목 | 디버그 빌드 | 배포 빌드 |
|---|---|---|
| 최적화 | `-O0` (또는 `-Og`) | `-O2` (또는 `-O3`) |
| 디버그 심볼 | `-g` 포함 | 보통 제외하거나 분리 |
| `assert()` | 활성화 | `NDEBUG` 정의 시 비활성화 |
| sanitizer | 켤 수 있음 | 성능 때문에 보통 끔 |

`assert()`는 `NDEBUG` 매크로가 정의되면 아무 코드도 생성하지 않는 것으로 사라진다. 즉 디버그 빌드에서는 `assert(ptr != NULL)`이 실제로 검사를 수행하지만, `-DNDEBUG`로 컴파일한 배포 빌드에서는 이 줄 자체가 통째로 사라진다. 그래서 `assert`는 "반드시 일어나야 하는 입력 검증"이 아니라 "개발자의 가정이 맞는지 확인하는 안전장치"로만 써야 한다. 사용자 입력 검증처럼 배포 환경에서도 반드시 실행돼야 하는 검사는 `assert` 대신 일반 `if` 문으로 작성한다.

## 테스트할 입력 나누기

같은 함수를 검증할 때도 어떤 성격의 입력을 테스트하는지에 따라 목적이 다르다. 크게 세 가지로 나눠서 준비한다.

### 정상 사례

일반적으로 기대되는, 유효한 입력. 이 함수가 존재하는 이유인 "주된 용도"를 검증한다.

```c
assert(parse_port("8080") == 8080);
```

### 경계 사례

값의 경계선에 있는 입력: 빈 문자열, 최솟값, 최댓값, 길이가 0인 배열, 정확히 1글자짜리 입력 등.

```c
assert(parse_port("1") == 1);         // 최솟값
assert(parse_port("65535") == 65535); // 최댓값
```

### 실패 사례

의도적으로 잘못된 입력을 줘서, 오류 처리 경로가 제대로 동작하는지 확인한다.

```c
// 형식이 아예 틀림, 범위를 벗어남 등을 각각 검증
assert(parse_port_fails("abc"));
assert(parse_port_fails("99999")); // 범위 초과
assert(parse_port_fails(""));      // 빈 문자열
```

세 범주 중 하나라도 빠지면 커버리지에 구멍이 생긴다. 특히 실패 사례를 생략하고 정상 사례만 테스트하는 경우가 흔한데, 오류 처리 코드는 정상 경로보다 테스트되지 않은 채 방치되기 쉬운 부분이다.

## 경계 바로 바깥도 테스트하기

경계값 자체(`0`, `INT_MAX`)뿐 아니라 그 바로 바깥(`-1`, `INT_MAX + 1`에 해당하는 값)도 함께 테스트해야 off-by-one 버그를 잡을 수 있다. `<=`를 써야 할 자리에 `<`를 쓴 것 같은 실수는 경계값 하나만 테스트해서는 드러나지 않고, 경계에서 한 걸음 벗어난 값을 같이 확인해야 드러난다.

```c
// 포트 범위가 1~65535라면
assert(parse_port_fails("0"));      // 최솟값 바로 아래
assert(parse_port_fails("65536"));  // 최댓값 바로 위
assert(parse_port("1") == 1);       // 최솟값 자체는 통과해야 함
assert(parse_port("65535") == 65535); // 최댓값 자체는 통과해야 함
```

`0`과 `1`, `65535`와 `65536`을 나란히 두고 봐야 "경계가 정확히 어디에 그어져 있는지"가 검증된다.

## 실패 시 상태 유지 테스트

입력 검증에 실패했을 때, 함수가 호출되기 전 상태를 그대로 유지하는지도 테스트 대상이다. "상태를 변경하기 전에 입력 검증하기"에서 다룬 원칙이 실제로 지켜지는지 확인하는 것이다.

```c
Config before = current_config; // 실패 전 상태 저장
apply_config("잘못된 입력");    // 실패해야 하는 호출
assert(memcmp(&before, &current_config, sizeof(Config)) == 0);
// 실패했는데도 상태가 조금이라도 바뀌었다면 이 assert가 잡아낸다
```

이런 테스트는 "실패했다"는 사실만 확인하는 테스트보다 한 단계 더 엄격하다. 실패는 정상적으로 보고됐지만 내부적으로 일부 상태가 이미 변경된 채 남아있는, 겉으로는 잘 안 드러나는 버그를 잡아낸다.

## 디버깅할 때 피해야 할 습관

경험이 쌓이기 전까지 반복하기 쉬운 비효율적인 접근들이 있다.

### 무작정 출력문 추가하기

가설 없이 의심 가는 곳마다 `printf`를 뿌리는 방식은 출력이 너무 많아져 정작 필요한 정보를 찾기 어렵게 만든다. 또한 출력문 자체가 타이밍에 영향을 줘서, 경쟁 상태처럼 타이밍에 민감한 버그는 출력문을 넣는 순간 사라지거나 위치가 바뀔 수 있다. 디버거의 중단점과 `print` 명령으로 같은 정보를 실행 중에 확인하면 코드를 수정하고 재컴파일할 필요도 없다.

### 오류가 난 줄만 보기

크래시나 segfault가 난 그 줄만 들여다보고 "여기가 문제"라고 결론짓는 경우가 많은데, 그 줄은 대개 증상이 드러난 곳일 뿐 원인은 호출 스택 위쪽(더 이전에 실행된 코드)에 있는 경우가 흔하다. `NULL` 포인터를 역참조해서 죽었다면, 진짜 물어야 할 질문은 "왜 이 지점에서 크래시가 났는가"가 아니라 "누가, 왜 `NULL`을 여기까지 전달했는가"다.

### 증상만 없애기

크래시가 난다고 그 지점에 `NULL` 체크를 추가해서 조용히 넘어가게 만드는 식의 패치는 근본 원인을 남겨둔 채 겉으로 드러나는 증상만 지운다. 원인이 되는 잘못된 값은 여전히 프로그램 어딘가를 떠돌고 있고, 나중에 전혀 다른 위치에서 다시 문제를 일으킨다. 왜 그 값이 애초에 잘못된 상태로 만들어졌는지까지 추적해서 고쳐야 재발을 막을 수 있다.
