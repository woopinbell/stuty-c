# 값, 분기, 반복

## 정수 타입과 범위

C의 정수 타입은 언어 표준이 정하는 최소 크기를 가질 뿐, 실제 크기는 플랫폼과 컴파일러에 따라 달라진다. `int`는 최소 16비트를 보장하지만 대부분의 현대 환경에서는 32비트이고, `long`은 플랫폼에 따라 32비트일 수도 64비트일 수도 있다. 이 차이를 무시하고 코드를 짜면 한 플랫폼에서는 멀쩡히 돌아가던 계산이 다른 플랫폼에서는 조용히 잘못된 값을 낸다.

크기가 코드에 명시적으로 중요한 경우(파일 포맷을 다루거나 네트워크로 값을 주고받을 때)에는 `<stdint.h>`가 제공하는 `int32_t`, `uint16_t`, `int64_t` 같은 고정폭 타입을 쓴다. 반대로 "이 시스템에서 가장 자연스러운 크기면 충분하다"는 경우에는 `int`를 그대로 쓰는 편이 이식성과 가독성 면에서 낫다.

```c
#include <stdint.h>
#include <limits.h>

int a;        // 최소 16비트, 대개 32비트
long b;       // 플랫폼에 따라 32비트 또는 64비트
int32_t c;    // 항상 정확히 32비트
uint16_t d;   // 항상 정확히 16비트, 부호 없음

printf("%d %d\n", INT_MIN, INT_MAX);   // 현재 플랫폼의 int 범위
```

각 타입의 실제 범위는 `<limits.h>`가 정의하는 `INT_MIN`, `INT_MAX`, `UINT_MAX` 등의 매크로로 확인한다. 이 값을 하드코딩하지 말고 매크로를 쓰는 습관을 들이면, 오버플로우 검사나 경계값 처리 코드가 플랫폼이 바뀌어도 그대로 맞는다.

## 부호 있는 값과 부호 없는 값

같은 비트 수라도 부호 있는 타입과 부호 없는 타입은 표현할 수 있는 값의 범위가 다르다. 32비트 `int`는 `-2,147,483,648`에서 `2,147,483,647`까지를 표현하고, 같은 32비트인 `unsigned int`는 0부터 `4,294,967,295`까지를 표현한다. 부호 비트 하나를 크기 쪽으로 돌려 쓰기 때문이다.

문제는 부호 있는 값과 부호 없는 값을 같은 식에서 섞어 쓸 때 생긴다. C는 이런 경우 부호 있는 값을 부호 없는 값으로 암묵적으로 변환하는 규칙을 갖고 있어서, 의도치 않게 음수가 거대한 양수로 둔갑한다.

```c
int x = -1;
unsigned int y = 3;

if (x < y) {
    printf("x가 더 작다\n");
} else {
    printf("x가 더 크거나 같다\n");   // 실제로는 이쪽이 실행된다
}
```

위 코드에서 `x`는 `-1`이지만 비교 시점에 `unsigned int`로 변환되어 `4294967295`가 되므로, `x < y`는 거짓이다. 사람이 읽을 때 기대하는 결과와 컴파일러가 실제로 계산하는 결과가 정반대로 갈리는 대표적인 함정이다. 크기나 개수처럼 음수가 나올 수 없는 값에는 `size_t` 같은 부호 없는 타입을 쓰는 게 자연스럽지만, 그 값을 부호 있는 값과 비교하거나 뺄셈에 쓸 때는 항상 변환 규칙을 의식해야 한다.

## 조건문

`if`/`else if`/`else`는 여러 조건을 위에서부터 순서대로 검사하다가 처음으로 참이 되는 분기 하나만 실행한다. 조건이 서로 배타적이지 않다면, 순서를 어떻게 두느냐에 따라 실행되는 분기가 달라질 수 있다는 점을 기억해야 한다.

```c
int score = 85;

if (score >= 90) {
    printf("A\n");
} else if (score >= 80) {
    printf("B\n");
} else if (score >= 70) {
    printf("C\n");
} else {
    printf("F\n");
}
```

여기서 조건을 큰 값부터 작은 값 순서로 배치한 이유가 중요하다. 만약 `score >= 70`을 맨 위에 뒀다면 90점짜리 점수도 `C`로 처리되어 버린다. 뒤의 조건까지 갈 기회 자체가 없기 때문이다. 조건이 겹치는 범위를 다룰 때는 항상 어느 조건이 먼저 걸리는지, 그 순서가 의도와 맞는지를 따져봐야 한다.

C에서는 `0`이 거짓, `0`이 아닌 모든 값이 참으로 취급된다는 점도 조건문을 읽을 때 놓치기 쉽다. `if (ptr)`은 `ptr`이 `NULL`이 아닐 때 참이고, `if (count)`는 `count`가 `0`이 아닐 때 참이다.

## 논리 연산자의 짧은 평가

### `&&`(and)

`&&`는 왼쪽 피연산자를 먼저 평가하고, 그 값이 거짓(`0`)이면 오른쪽은 아예 평가하지 않고 전체 결과를 거짓으로 확정한다. 이 성질을 "짧은 평가(short-circuit evaluation)"라고 부른다.

```c
int *ptr = NULL;

if (ptr != NULL && *ptr > 0) {
    printf("양수\n");
}
```

`ptr != NULL`이 거짓이면 `*ptr > 0`은 실행되지 않는다. 순서를 바꿔 `*ptr > 0 && ptr != NULL`이라고 쓰면 `ptr`이 `NULL`인 경우 역참조부터 시도해 버려서 크래시가 난다. **앞의 조건이 뒤의 조건을 안전하게 만들어주는 관계라면, 반드시 안전을 보장하는 조건을 왼쪽에 둬야 한다**.

### `||`(or)

`||`는 반대로 왼쪽이 참이면 오른쪽을 평가하지 않고 전체를 참으로 확정한다. 값비싼 연산이나 부작용이 있는 함수 호출을 뒤쪽에 배치하면, 앞의 조건만으로 답이 나올 때 그 호출 자체를 건너뛸 수 있다.

```c
if (cache_hit || compute_expensive_result()) {
    // ...
}
```

`cache_hit`이 참이면 `compute_expensive_result()`는 호출조차 되지 않는다. 다만 이 함수가 매번 호출돼야만 하는 부작용(로그 기록, 카운터 증가 등)을 갖고 있다면, 짧은 평가 때문에 그 부작용이 조건에 따라 누락될 수 있다는 점을 반드시 염두에 둬야 한다.

### 범위 검사와 함께 사용하기

값이 어떤 구간 안에 있는지 검사할 때는 `&&`로 두 부등식을 묶는 게 가장 흔한 형태다.

```c
int age = 25;

if (age >= 18 && age < 65) {
    printf("근로 가능 연령대\n");
}
```

경계값을 어느 쪽에 포함시킬지(`>=`인지 `>`인지, `<`인지 `<=`인지)는 요구사항에 따라 달라지므로, 범위 검사를 쓸 때마다 양쪽 경계가 포함인지 제외인지를 주석이나 변수명으로 분명히 해두는 편이 나중의 실수를 줄인다.

## 반복문과 유지해야 할 조건

반복문을 정확하게 짜려면 다섯 요소(초기 상태, 반복 조건, 본문, 갱신, 종료)를 각각 따로 떼어 생각하는 게 도움이 된다. 이 다섯 가지가 서로 어긋나면 무한 루프나 한 칸씩 어긋나는 오프바이원(off-by-one) 버그로 이어진다.

### 초기 상태

반복을 시작하기 전에 반복 변수와 관련 상태가 어떤 값에서 출발하는지를 정한다. 배열을 순회한다면 인덱스는 보통 `0`에서, 역순이라면 `길이 - 1`에서 시작한다.

### 반복 조건

매 반복이 시작되기 전에 검사되어, 참인 동안에만 본문이 실행되는 조건이다. 이 조건이 처음부터 거짓이면 본문은 한 번도 실행되지 않는다(`while`의 경우). 조건에 쓰인 비교 연산자(`<`인지 `<=`인지)가 배열의 끝을 정확히 가리키는지 항상 확인해야 한다.

### 본문

실제로 반복해서 수행할 작업이다. 본문 안에서 반복 변수 자체를 예상치 못하게 건드리면(예: 루프 안에서 인덱스를 추가로 증가시키는 코드가 섞여 있으면) 갱신 단계와 충돌해 의도한 횟수만큼 반복되지 않는다.

### 갱신

다음 반복으로 넘어가기 전에 반복 변수를 변화시키는 단계다. 갱신을 빠뜨리면 반복 조건이 영원히 참으로 남아 무한 루프가 되고, 갱신 방향이 반복 조건과 맞지 않으면(예: 조건은 감소를 기대하는데 갱신은 증가시키는 경우) 역시 무한 루프가 된다.

### 종료

반복 조건이 거짓이 되어 반복문을 빠져나오는 시점이다. 종료 시점의 반복 변수 값이 이후 코드에서 그대로 쓰이는 경우가 많으므로(예: "몇 번째에서 멈췄는지"), 종료 직후 그 변수가 정확히 어떤 값을 갖는지 짚어보는 습관이 필요하다.

## `for` 반복문

`for` 문은 초기 상태, 반복 조건, 갱신을 한 줄에 모아 써서, 위에서 나눠 설명한 다섯 요소 중 세 가지를 한눈에 보이게 만든다.

```c
for (int i = 0; i < 10; i++) {
    printf("%d\n", i);
}
```

여기서 `int i = 0`이 초기 상태, `i < 10`이 반복 조건, `i++`가 갱신이다. 이 셋을 한곳에 몰아 쓰기 때문에, `for` 문을 읽을 때는 세 부분을 따로따로 확인하는 게 안전하다. 특히 반복 조건에 `<`를 쓸지 `<=`를 쓸지는 배열 크기와 인덱스 범위를 정확히 계산해야 결정할 수 있다. 배열 `arr[10]`을 처음부터 끝까지 순회하려면 `i < 10`이어야 하고, `i <= 10`으로 쓰면 존재하지 않는 `arr[10]`에 접근하게 된다.

세 부분 중 어느 것도 생략할 수 있다는 점도 알아두면 좋다. `for (;;)`는 조건이 항상 참인 무한 루프이며, 내부에서 `break`로 빠져나오는 형태로 자주 쓰인다.

## 누적 상태

반복문 밖에서 선언한 변수에 매 반복마다 값을 더하거나, 조건에 맞는 값으로 교체해 나가는 패턴이다. 합계, 평균, 최솟값, 최댓값을 구하는 코드 대부분이 이 형태를 따른다.

```c
int sum = 0;
int numbers[5] = {3, 7, 1, 9, 4};

for (int i = 0; i < 5; i++) {
    sum += numbers[i];
}
```

`sum`은 반복문이 시작되기 전에 반드시 알맞은 초깃값(합계라면 `0`)으로 초기화되어 있어야 한다. 초기화를 빠뜨리면 쓰레기값 위에 계속 더해지는 결과가 나온다.

### 최솟값과 최댓값의 초기화

최솟값, 최댓값을 누적해서 구할 때는 초깃값을 무엇으로 잡느냐가 결과를 좌우한다. 흔히 저지르는 실수는 `0`으로 초기화하는 것인데, 배열의 모든 값이 음수라면 최댓값이 `0`으로 잘못 계산된다.

```c
int numbers[5] = {-8, -3, -15, -1, -6};
int max = numbers[0];   // 배열의 첫 원소로 초기화

for (int i = 1; i < 5; i++) {
    if (numbers[i] > max) {
        max = numbers[i];
    }
}
```

가장 안전한 방법은 배열의 첫 원소로 초기화하고 두 번째 원소부터 비교를 시작하는 것이다. 타입의 최솟값(`INT_MIN`)으로 초기화하는 방법도 있지만, 배열이 비어 있을 가능성이 있는 경우에는 두 방법 모두 별도의 빈 배열 처리가 필요하다.

### 상태를 갱신하는 순서

누적 상태를 갱신하는 코드 안에서 여러 변수가 서로에게 의존한다면, 어느 것을 먼저 갱신하느냐가 결과를 바꿀 수 있다. 예를 들어 이전 값을 참조해야 하는 계산이 있다면, 그 계산을 끝내기 전에 원본 변수를 덮어써서는 안 된다.

```c
int prev = numbers[0];
int diff_sum = 0;

for (int i = 1; i < 5; i++) {
    diff_sum += numbers[i] - prev;   // prev를 먼저 써야 한다
    prev = numbers[i];               // 그다음에 갱신
}
```

`prev`를 먼저 갱신해 버리면 `numbers[i] - prev`가 항상 `0`이 되어 버린다. 누적 로직을 짤 때는 "이번 반복에서 옛 값과 새 값이 동시에 필요한 지점이 있는가"를 먼저 파악하고, 옛 값을 다 쓴 다음에 갱신하는 순서를 지켜야 한다.

## overflow를 계산 전에 검사하기

부호 있는 정수의 덧셈, 뺄셈이 그 타입이 표현할 수 있는 범위를 벗어나면 오버플로우가 발생한다. C 표준에서 부호 있는 정수 오버플로우는 정의되지 않은 동작(undefined behavior)이므로, 계산을 실행한 뒤에 결과를 보고 오버플로우 여부를 판단하는 방식은 애초에 성립하지 않는다. 컴파일러가 오버플로우가 없다고 가정하고 최적화해 버리면 검사 코드 자체가 통째로 사라질 수 있다. 그래서 반드시 계산을 하기 전에, 피연산자만으로 오버플로우 여부를 미리 판단해야 한다.

두 정수 `left`와 `right`를 더한다고 할 때, `right`의 부호에 따라 검사식이 달라진다.

### `right > 0`

`right`가 양수면 덧셈의 결과가 `left`보다 커져야 정상이다. 결과가 `INT_MAX`를 넘어서려면 `left`가 `INT_MAX - right`보다 커야 한다.

```c
#include <limits.h>

int left = INT_MAX - 5;
int right = 10;

if (right > 0 && left > INT_MAX - right) {
    printf("overflow 발생\n");
} else {
    int result = left + right;
    printf("%d\n", result);
}
```

`left + right`를 먼저 계산해서 `INT_MAX`를 넘었는지 확인하는 방식은 그 계산 자체가 정의되지 않은 동작이라 신뢰할 수 없다. 반드시 `left > INT_MAX - right`처럼 덧셈을 뺄셈으로 바꿔, 오버플로우가 나지 않는 연산만으로 미리 검사해야 한다.

### `right < 0`

`right`가 음수면 반대로 결과가 `left`보다 작아져야 정상이다. 결과가 `INT_MIN`보다 작아지려면 `left`가 `INT_MIN - right`보다 작아야 한다.

```c
if (right < 0 && left < INT_MIN - right) {
    printf("underflow 발생\n");
}
```

여기서도 `INT_MIN - right`는 `right`가 음수이므로 실제로는 덧셈에 가깝고, `INT_MIN`에 가까운 값을 다시 빼는 형태라 그 자체로 오버플로우를 일으키지 않는다는 점이 핵심이다.

### 안전한 경우에만 계산

`right`가 `0`인 경우는 오버플로우가 날 수 없으므로 어느 조건에도 걸리지 않고 곧바로 안전하게 더할 수 있다. 위 두 조건을 합쳐서 정리하면, 실제 덧셈은 오버플로우가 없다고 확인된 뒤에만 실행하는 구조가 된다.

```c
int safe_add(int left, int right, int *result) {
    if (right > 0 && left > INT_MAX - right) {
        return 0;   // overflow
    }
    if (right < 0 && left < INT_MIN - right) {
        return 0;   // underflow
    }
    *result = left + right;
    return 1;
}
```

이 패턴의 핵심은 "먼저 계산하고 결과를 검사"가 아니라 **"계산 전에 피연산자만으로 안전성을 확인하고, 안전할 때만 계산"**이라는 순서 자체에 있다.

### 부호 없는 정수 overflow와의 차이

부호 없는 정수는 사정이 다르다. C 표준은 부호 없는 정수의 오버플로우를 정의되지 않은 동작이 아니라 모듈로 연산으로 명확히 정의한다. `UINT_MAX`를 넘는 값은 자동으로 `0`부터 다시 순환한다. 그래서 부호 없는 덧셈에서는 결과를 계산한 뒤에 검사하는 방식이 실제로 안전하게 동작한다.

```c
unsigned int left = UINT_MAX - 5;
unsigned int right = 10;
unsigned int result = left + right;   // 표준에 의해 wrap-around가 보장됨

if (result < left) {
    printf("wrap-around 발생\n");   // 결과가 원래 값보다 작아지면 넘친 것
}
```

부호 있는 정수는 계산 전에 미리 막아야 하고, 부호 없는 정수는 계산 후에 결과를 보고 판단해도 된다는 이 차이는 표준이 두 경우의 오버플로우를 서로 다르게 정의하고 있기 때문에 생긴다. 이 차이를 혼동해서 부호 있는 정수에 "결과 확인" 방식을 그대로 쓰면, 검사 코드가 컴파일러 최적화에 의해 사라질 위험을 안게 된다.

## `switch`

`switch`는 하나의 정수형(또는 열거형) 값을 여러 `case` 상수와 비교해 분기하는 문이다. `if`/`else if` 연쇄가 매번 조건식을 다시 평가하는 것과 달리, `switch`는 하나의 값을 기준으로 어느 라벨로 뛸지 결정한다는 점에서 의미가 다르다. 그래서 각 `case`는 반드시 컴파일 타임에 정해지는 상수여야 하고, 범위 비교(`case x > 5`) 같은 건 쓸 수 없다.

```c
int day = 3;

switch (day) {
    case 1:
        printf("월요일\n");
        break;
    case 2:
        printf("화요일\n");
        break;
    case 3:
        printf("수요일\n");
        break;
    default:
        printf("알 수 없는 요일\n");
        break;
}
```

`break`를 빠뜨리면 실행 흐름이 다음 `case`로 그대로 흘러 들어간다(fall-through). 이 성질은 실수의 원인이 되기도 하지만, 여러 `case`가 같은 동작을 공유해야 할 때는 의도적으로 활용된다.

```c
switch (day) {
    case 6:
    case 7:
        printf("주말\n");
        break;
    default:
        printf("평일\n");
        break;
}
```

의도적인 fall-through와 실수로 빠뜨린 `break`를 코드만 보고 구분하기 어렵다는 점 때문에, 의도적으로 흐름을 이어지게 둔 `case`에는 `// fall through`처럼 주석을 남겨 다음에 이 코드를 읽는 사람이 실수인지 의도인지 헷갈리지 않게 하는 습관이 널리 쓰인다. `default`는 어떤 `case`와도 맞지 않는 값을 처리하며, 관례상 마지막에 두지만 문법적으로는 어느 위치에나 올 수 있다.
