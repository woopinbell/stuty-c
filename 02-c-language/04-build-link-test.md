# 빌드, 링크, 테스트

## 직접 명령부터 확인하기

Makefile을 쓰기 전에, 그 Makefile이 결국 실행할 명령을 손으로 먼저 쳐 봐야 한다. 컴파일은 소스 하나를 오브젝트 파일로 바꾸는 단계이고, 링크는 여러 오브젝트 파일과 라이브러리를 묶어 실행 파일을 만드는 단계다. 예를 들어 `main.c`와 `util.c`로 이루어진 프로그램이라면 다음처럼 두 단계로 나눠 실행해 본다.

```sh
gcc -Wall -Wextra -std=c11 -c main.c -o main.o
gcc -Wall -Wextra -std=c11 -c util.c -o util.o
gcc main.o util.o -o app
```

이렇게 손으로 먼저 확인해 두면, 나중에 Make가 내부적으로 만들어내는 명령이 이상하게 실패했을 때 "Make가 이상한 게 아니라 이 컴파일 명령 자체가 원래 안 되는 것"인지 아닌지 바로 구분할 수 있다. Makefile을 처음부터 만들면서 동시에 디버깅하려고 하면 두 가지 문제(빌드 시스템 문제, 컴파일 자체 문제)가 뒤섞여 원인을 찾기 어렵다.

## 빌드는 입력과 결과의 관계

Make의 핵심 모델은 "이 파일(target)은 저 파일들(prerequisites)로부터 만들어진다"는 의존 관계의 그래프다. 규칙 하나는 다음 세 가지로 이루어진다.

```make
target: prerequisite1 prerequisite2
    command
```

여기서 target은 만들어질 결과물(오브젝트 파일, 실행 파일 등), prerequisite는 그 결과물을 만드는 데 필요한 입력, command는 입력에서 결과물을 만드는 실제 셸 명령이다. command 줄 앞에는 반드시 탭(tab) 문자가 와야 하며, 스페이스로 들여쓰면 "missing separator" 오류가 난다. 이 셋을 하나의 문장으로 읽으면 **"target은 prerequisite들이 target보다 최신이거나 target이 아직 없을 때, command를 실행해서 만든다"**가 된다.

## Make가 다시 빌드할지 결정하는 기준

Make는 명령을 미리 다 실행해보고 결과를 비교하는 게 아니라, 오직 파일의 수정 시각(mtime)만 비교한다. target 파일이 아예 없거나, prerequisite 중 하나라도 target보다 mtime이 더 최신이면 그 규칙의 command를 실행한다. 반대로 target이 모든 prerequisite보다 최신이면 "up to date"로 판단하고 아무것도 하지 않는다.

이 기준 때문에 흔히 두 가지 실수가 생긴다. 첫째, 시계가 맞지 않는 네트워크 파일시스템이나 `touch`로 시각을 억지로 조작한 파일이 섞이면 Make가 잘못된 판단을 내린다. 둘째, 소스는 그대로인데 컴파일 옵션(예: `-O2`에서 `-O0`으로)만 바꿨을 때는 mtime이 바뀌지 않았으므로 Make가 재빌드 필요성을 못 느낀다. 옵션이 바뀌는 걸 감지하려면 옵션 문자열을 별도 파일에 저장해 그 파일을 prerequisite로 걸어두는 방식을 쓰기도 한다.

## 컴파일 옵션과 링크 옵션

컴파일 옵션(CFLAGS)은 `.c`를 `.o`로 바꾸는 단계에서만 의미가 있고, 링크 옵션(LDFLAGS, LDLIBS)은 오브젝트들을 묶어 실행 파일을 만드는 단계에서만 의미가 있다. 이 둘을 섞어 쓰면 "옵션을 줬는데 왜 안 먹지"라는 혼란이 생긴다. 대표적으로 `-c`, `-Wall`, `-std=c11`, `-I경로`(헤더 검색 경로)는 컴파일 단계 옵션이고, `-L경로`(라이브러리 검색 경로), `-l이름`(라이브러리 이름), `-shared`는 링크 단계 옵션이다.

```make
CFLAGS  = -Wall -Wextra -std=c11 -Iinclude
LDFLAGS = -Lbuild/lib
LDLIBS  = -lm -lpthread
```

관례적으로 `-l` 라이브러리 목록은 링크 명령의 맨 뒤에 둔다(왜 뒤에 둬야 하는지는 아래 "링크 순서"에서 다룬다).

### 컴파일과 링크 모두에 필요한 옵션

`-g`(디버그 정보 포함), `-O0`/`-O2`(최적화 수준), `-fsanitize=address` 같은 옵션은 컴파일 단계와 링크 단계 양쪽에 모두 줘야 한다. 컴파일 시에만 `-fsanitize=address`를 주면 오브젝트 코드에는 계측이 들어가지만 링크 시 sanitizer 런타임 라이브러리가 연결되지 않아 링크 오류나 실행 시 오작동이 난다. 반대로 링크 시에만 주면 애초에 계측된 코드가 없으므로 의미가 없다. 이런 이유로 두 단계에 공통으로 필요한 플래그는 별도 변수(예: `COMMON_FLAGS`)로 빼서 CFLAGS와 LDFLAGS 양쪽에 포함시키는 방식을 흔히 쓴다.

```make
COMMON_FLAGS = -g -fsanitize=address
CFLAGS  += $(COMMON_FLAGS)
LDFLAGS += $(COMMON_FLAGS)
```

## 기본 규칙

같은 형태의 규칙을 소스 파일 개수만큼 반복해서 적으면 파일이 늘어날 때마다 Makefile을 계속 고쳐야 한다. Make는 확장자 기반의 암시적 규칙을 내장하고 있어서, `%.o: %.c` 같은 패턴을 따로 적지 않아도 `CC`, `CFLAGS` 변수만 설정하면 `.c`에서 `.o`를 만드는 규칙을 자동으로 적용한다. 다만 헤더 검색 경로나 프로젝트 고유 경고 옵션이 필요한 대부분의 실전 프로젝트에서는 내장 규칙만으로 부족해서, 아래 "패턴 규칙"처럼 직접 규칙을 정의하는 경우가 많다.

### 디렉터리 생성과 order-only prerequisite

오브젝트 파일을 `build/obj/` 같은 별도 디렉터리에 모아 두려면, 그 디렉터리가 먼저 존재해야 컴파일 명령이 성공한다. 이때 디렉터리를 일반 prerequisite로 걸면 문제가 생긴다. 디렉터리에 새 파일이 생겨도 디렉터리 자체의 mtime이 갱신되므로, 오브젝트 파일 하나를 새로 만들 때마다 디렉터리보다 mtime이 앞선다고 착각해 관련 없는 target까지 계속 재빌드 대상으로 잡히기 때문이다.

이를 피하려면 `|` 뒤에 오는 order-only prerequisite를 쓴다. order-only prerequisite는 "target을 만들기 전에 존재만 하면 된다"는 뜻이고, 이 prerequisite의 mtime은 재빌드 판단에 전혀 쓰이지 않는다.

```make
build/obj/%.o: src/%.c | build/obj
	$(CC) $(CFLAGS) -c $< -o $@

build/obj:
	mkdir -p $@
```

## 패턴 규칙

패턴 규칙은 `%`를 와일드카드로 써서 "이런 이름 형태의 target은 이런 형태의 prerequisite로부터 만든다"를 한 줄로 표현한다. `$@`는 target 이름, `$<`는 첫 번째 prerequisite, `$^`는 모든 prerequisite를 가리키는 자동 변수다.

```make
build/obj/%.o: src/%.c
	$(CC) $(CFLAGS) -c $< -o $@
```

이 규칙 하나로 `src/` 아래 소스 파일이 몇 개든, 이름 대응만 맞으면 개별 규칙을 추가로 적을 필요가 없다. 실전에서는 여기에 `wildcard`와 `patsubst` 함수를 조합해 소스 목록에서 오브젝트 목록을 자동 생성한다.

```make
SRCS = $(wildcard src/*.c)
OBJS = $(patsubst src/%.c,build/obj/%.o,$(SRCS))
```

## 헤더 의존성

패턴 규칙 `build/obj/%.o: src/%.c`만으로는 `.o`가 대응하는 `.c`에만 의존하는 셈이라, 그 `.c`가 `#include`하는 헤더가 바뀌어도 Make는 재빌드 필요성을 감지하지 못한다. 헤더 하나만 고쳤는데 `make`를 실행해도 아무 일도 일어나지 않으면 이 문제일 가능성이 크다. 헤더까지 의존 관계에 넣는 가장 무식하지만 확실한 방법은 모든 오브젝트가 모든 공용 헤더에 의존한다고 명시하는 것이다.

```make
build/obj/%.o: src/%.c include/common.h
	$(CC) $(CFLAGS) -c $< -o $@
```

하지만 이 방식은 헤더가 늘어날 때마다 손으로 갱신해야 하고, 실제로 그 헤더를 쓰지 않는 소스까지 불필요하게 재빌드된다는 단점이 있다. 이 단점을 해결하는 방법이 바로 아래 "자동 의존성 파일"이다.

## 자동 의존성 파일

컴파일러 자체가 소스 파일이 실제로 어떤 헤더들을 include하는지 알고 있으므로, 컴파일러에게 그 목록을 Makefile 규칙 형태로 뽑아내게 하고 Make가 그 결과를 다시 읽어들이게 하면 헤더 의존성을 손으로 관리할 필요가 없다. gcc/clang은 `-MMD -MP` 옵션으로 컴파일과 동시에 `.d` 파일을 생성한다.

```make
CFLAGS += -MMD -MP
DEPS = $(OBJS:.o=.d)

-include $(DEPS)
```

`-include`는 파일이 아직 없어도(최초 빌드 시점) 오류 없이 넘어가는 include 지시자다. 첫 빌드 후에는 `.d` 파일들이 생겨 있으므로 두 번째 빌드부터 헤더 의존성이 정확히 반영된다.

### `-MMD`

`-MMD`는 컴파일할 때 사용된 헤더 목록을 `.d` 파일에 Makefile 규칙 형태로 함께 써준다. `-MD`와 차이는, `-MD`는 시스템 헤더(`<...>`로 include하고 시스템 경로에 있는 것)까지 의존성에 포함시키는 반면 `-MMD`는 프로젝트 안에 있는 헤더(대개 `"..."`로 include한 것)만 추적한다는 점이다. 시스템 헤더는 어차피 바뀌지 않는다고 가정할 수 있으므로, 실전에서는 불필요한 재빌드를 줄이기 위해 `-MMD`를 쓰는 경우가 많다.

### `-MP`

`-MP`는 각 헤더에 대해 "이 헤더 : (아무 의존성 없음)"이라는 더미 규칙을 하나씩 추가로 만들어준다. 이 옵션이 없으면, 헤더 파일을 삭제하거나 이름을 바꿨을 때 예전에 생성된 `.d` 파일 안에 더 이상 존재하지 않는 헤더에 대한 target이 남아 있게 되어 Make가 "No rule to make target"이라는 오류로 멈춘다. `-MP`가 만드는 더미 규칙이 있으면 그 헤더가 사라진 상태에서도 규칙을 못 찾는 일 없이 그냥 무시하고 넘어간다.

## 정적 라이브러리

정적 라이브러리(`.a` 파일)는 여러 오브젝트 파일을 `ar` 아카이브 유틸리티로 하나로 묶어 놓은 것이다. 실행 파일을 링크할 때 정적 라이브러리 안에서 실제로 참조되는 오브젝트만 골라 최종 실행 파일에 포함시킨다는 점이 공유 라이브러리와 다르다.

```make
build/lib/libutil.a: $(OBJS)
	ar rcs $@ $^
```

`rcs` 옵션은 `r`(아카이브에 파일을 추가/교체), `c`(아카이브가 없으면 새로 생성하되 경고를 내지 않음), `s`(아카이브 안에 심볼 인덱스를 생성해 링커가 빠르게 심볼을 찾을 수 있게 함)를 합친 것이다.

### 왜 기존 아카이브를 지울 수 있는가

`ar rcs`는 기존 아카이브가 있으면 그 안의 오브젝트를 그대로 둔 채 새 오브젝트만 추가/교체하는 방식으로 동작한다. 문제는 소스 파일 하나를 삭제했을 때 발생한다. 대응하는 `.o`가 더는 생성되지 않으므로 `$^`(prerequisite 목록)에서도 빠지지만, 예전에 그 `.o`를 넣어 만든 아카이브 안에는 죽은 오브젝트가 그대로 남아 있다. 이 상태로는 실제로 삭제된 함수가 여전히 라이브러리 안에 존재하는 것처럼 보여, 그 함수를 지웠는데도 링크 오류가 나지 않는 등 실제 소스 상태와 아카이브 내용이 어긋난다.

이를 피하려면 아카이브 규칙에서 target을 먼저 지우고 처음부터 다시 만들도록 강제한다.

```make
build/lib/libutil.a: $(OBJS)
	rm -f $@
	ar rcs $@ $^
```

## 정적 라이브러리 내용 확인

아카이브 안에 어떤 오브젝트가 들어 있는지, 그리고 각 오브젝트가 어떤 심볼(함수, 전역 변수)을 정의, 참조하는지 확인하려면 `ar`과 `nm`을 함께 쓴다.

```sh
ar t build/lib/libutil.a      # 아카이브에 포함된 오브젝트 파일 목록
nm build/lib/libutil.a        # 각 오브젝트가 정의/참조하는 심볼 목록
```

`nm` 출력에서 `T`는 그 오브젝트가 정의하는 전역 함수, `U`는 정의는 없고 참조만 하는(undefined) 심볼을 뜻한다. "링크가 안 되는데 왜 안 되는지 모르겠다"는 상황에서는 대개 필요한 심볼이 어느 오브젝트에도 `T`로 잡혀 있지 않다는 뜻이므로, 이 명령으로 원인을 좁힐 수 있다.

## 링크 규칙

링크 규칙은 컴파일이 끝난 오브젝트 파일들과 필요하면 정적/공유 라이브러리를 입력으로 받아 최종 실행 파일을 만든다.

```make
build/bin/app: $(OBJS) build/lib/libutil.a
	$(CC) $(LDFLAGS) $(OBJS) -o $@ -Lbuild/lib -lutil $(LDLIBS)
```

여기서 `$(OBJS)`처럼 프로젝트 자체 오브젝트는 위치가 크게 중요하지 않지만, `-l`로 지정하는 라이브러리는 순서가 결과에 영향을 준다(아래 "링크 순서" 참고). 링크 규칙의 prerequisite에는 라이브러리 파일 자체(`build/lib/libutil.a`)도 넣어야, 라이브러리 소스가 바뀌어 라이브러리가 새로 만들어졌을 때 실행 파일도 재링크된다.

## 링크 순서

전통적인(GNU ld 계열) 링커는 명령줄에 나열된 순서대로 파일을 한 번씩만 훑으면서, 그 시점까지 undefined로 남아 있는 심볼을 뒤에 나오는 파일에서 찾아 채워 나간다. 그래서 오브젝트 파일과 정적 라이브러리는 "그 심볼을 필요로 하는 쪽이 먼저, 그 심볼을 제공하는 쪽이 나중에" 오는 순서로 나열해야 한다. `main.o`가 `libutil.a` 안의 함수를 호출한다면 반드시 `main.o -lutil` 순서여야지, `-lutil main.o` 순서로 주면 링커가 `libutil.a`를 훑는 시점에는 아직 그 함수가 필요하다는 걸 모르므로 undefined reference 오류가 난다.

### 라이브러리끼리 서로 의존하는 경우

라이브러리 A가 라이브러리 B의 함수를 쓰고, 동시에 라이브러리 B도 라이브러리 A의 함수를 쓰는 순환 의존 관계라면, 단순히 "필요한 쪽을 먼저" 규칙만으로는 순서를 정할 수 없다. 이런 경우 같은 라이브러리 목록을 두 번 반복해서 주거나, GNU ld의 `--start-group ... --end-group`(또는 `-Wl,--start-group`) 옵션을 써서 그 안의 라이브러리들을 undefined 심볼이 남지 않을 때까지 반복해서 훑도록 링커에 지시한다.

```make
$(CC) $(OBJS) -Wl,--start-group -la -lb -Wl,--end-group -o $@
```

다만 이 방식은 링크 시간을 늘리므로, 가능하면 순환 의존 자체를 설계 단계에서 없애는 편이 근본적인 해결책이다.

## `.PHONY`

Make는 기본적으로 target 이름을 파일 이름으로 취급한다. 그런데 `clean`, `test`, `all`처럼 실제 파일을 만드는 게 아니라 "동작"을 의미하는 target도 흔히 쓴다. 문제는 만약 프로젝트 디렉터리 안에 우연히 `clean`이라는 이름의 파일이 실제로 존재하면, Make가 그 파일이 이미 최신 상태라고 판단해 `clean` target의 command를 아예 실행하지 않는다는 점이다.

`.PHONY`는 특정 target이 파일이 아니라 항상 실행되어야 하는 이름뿐인 target임을 Make에 알려준다.

```make
.PHONY: all clean test

clean:
	rm -rf build
```

`.PHONY`로 선언된 target은 동일한 이름의 파일이 존재하는지 여부와 무관하게, 그리고 그 자체의 "mtime"이라는 개념이 없으므로 항상 오래된 것으로 취급되어 매번 command가 실행된다.

## 재링크와 재빌드 방지

오브젝트 파일이 하나도 바뀌지 않았는데 `make`를 실행할 때마다 링크가 다시 일어난다면, 대개 링크 규칙의 target이나 prerequisite를 mtime 비교가 정확히 되지 않는 형태로 적었기 때문이다. 흔한 원인은 `.PHONY`로 잘못 선언된 target을 실제 파일 target처럼 쓰는 경우, 또는 항상 값이 바뀌는 명령(예: `` `date` `` 결과를 파일 이름에 넣는 등)을 prerequisite 계산에 섞어 쓰는 경우다. 반대로 실제로 오브젝트가 바뀌었는데도 재링크가 안 된다면, 링크 규칙의 prerequisite 목록에 그 오브젝트나 라이브러리가 빠져 있는지 확인해야 한다. `make -d`(디버그 모드) 또는 `make --trace`로 실행하면 Make가 어떤 파일의 mtime을 비교해서 재빌드를 결정했는지 단계별로 출력해주므로, "왜 다시 빌드되는지/안 되는지" 판단이 안 설 때 가장 먼저 써볼 만한 도구다.

## 기본 target과 `all`

Makefile 맨 위에 나오는 첫 번째 target이 인자 없이 `make`만 실행했을 때의 기본 target이 된다. 관례적으로 `all`이라는 이름의 target을 파일 맨 위에 두고, 그 prerequisite로 실제 빌드하고 싶은 최종 산출물들을 나열한다.

```make
.PHONY: all
all: build/bin/app
```

이렇게 관례를 지키면 Makefile을 처음 보는 사람도 `make`만 치면 무엇이 만들어지는지 파일 상단만 보고 짐작할 수 있고, 나중에 target이 여러 개로 늘어나도(`app`, `libutil.a`, 문서 등) `all`의 prerequisite 목록만 늘리면 되므로 "첫 번째 target이 우연히 바뀌어 기본 동작이 달라지는" 사고를 막을 수 있다.

## 테스트 target

테스트도 대개 `.PHONY` target으로 정의한다. 테스트를 돌리기 전에 먼저 최신 바이너리가 빌드되어 있어야 하므로, 테스트 target은 빌드 target을 prerequisite로 가진다.

```make
.PHONY: test
test: build/bin/app
	./build/bin/app --self-test
```

이렇게 의존 관계를 걸어두면 소스를 고친 뒤 재빌드를 깜빡하고 오래된 바이너리로 테스트를 실행하는 실수를 Make가 자동으로 막아준다.

## 테스트와 빌드 실패를 구분하기

`make test`를 실행했을 때 실패가 나면, 그게 "빌드 자체가 안 된 것"인지 "빌드는 됐는데 테스트 로직이 실패한 것"인지 로그만 봐서는 헷갈릴 수 있다. Make는 규칙 안의 명령이 0이 아닌 종료 코드를 반환하면 그 즉시 실행을 멈추고 오류로 보고하는데, 컴파일러가 실패해도 종료 코드가 0이 아니고 테스트 바이너리가 실패해도 종료 코드가 0이 아니므로 겉보기 동작이 비슷하다.

구분하는 가장 확실한 방법은 출력 로그를 끝까지 읽어, 컴파일러 오류 메시지(`error:`가 포함된 gcc/clang 특유의 형식)가 있는지, 아니면 `make`의 진행 로그(어떤 명령을 실행 중인지)가 컴파일 단계까지는 정상적으로 지나가고 테스트 실행 단계에서 실패 메시지가 나오는지를 보는 것이다. 두 상황을 명확히 나누고 싶다면 테스트 target의 prerequisite 실패와 커맨드 자체의 실패가 서로 다른 메시지를 내도록, 셸 스크립트 쪽에서 "빌드 실패"와 "테스트 실패"를 구분해 출력하게 만들어두는 방법도 있다.

## Sanitizer target

AddressSanitizer, UndefinedBehaviorSanitizer 같은 sanitizer는 컴파일 시 코드에 검사 로직을 계측해 넣어 메모리 오류나 정의되지 않은 동작을 실행 중에 잡아낸다. 다만 계측이 들어간 바이너리는 일반 빌드보다 느리고 메모리도 더 쓰므로, 평소 빌드와 sanitizer 빌드를 같은 오브젝트로 공유하지 않고 별도 target으로 분리하는 것이 일반적이다.

```make
.PHONY: sanitize
sanitize: CFLAGS += -fsanitize=address,undefined -g -O0
sanitize: LDFLAGS += -fsanitize=address,undefined
sanitize: build/bin/app-sanitized
	./build/bin/app-sanitized --self-test
```

### 일반 오브젝트와 sanitizer 오브젝트

같은 `%.o` 패턴 규칙을 그대로 쓰면서 target별로 CFLAGS만 다르게 주면, 일반 빌드 때 만든 `build/obj/main.o`와 sanitizer 빌드 때 만든 `build/obj/main.o`가 같은 파일 이름을 놓고 서로 다른 옵션으로 계속 다시 쓰이는 상황이 생긴다. Make 입장에서는 target 이름만 보고 mtime 비교를 하므로, "옵션이 다른데 이름은 같은" 두 버전이 번갈아 서로를 오래된 것으로 판단해 매번 재컴파일이 일어난다. 이를 피하려면 sanitizer용 오브젝트는 `build/obj-san/%.o`처럼 아예 다른 디렉터리(또는 다른 확장자)에 만들어, 일반 오브젝트와 물리적으로 겹치지 않게 한다.

## target별 변수와 의존성 주의

앞서 `sanitize: CFLAGS += ...`처럼 target별로 변수 값을 다르게 주는 문법을 target-specific variable이라고 부른다. 이 문법은 해당 target을 만들 때 실행되는 command 안에서만, 그리고 그 target의 prerequisite를 만드는 재귀적인 규칙 평가 과정에서도 적용된다는 점을 알아둬야 한다. 즉 `sanitize` target이 `build/bin/app-sanitized`를 prerequisite로 두고, 그 target이 다시 오브젝트들을 prerequisite로 둔다면, `sanitize`에서 설정한 CFLAGS가 그 오브젝트들을 컴파일하는 데도 전달된다. 다만 이는 target 이름 자체가 서로 겹치지 않을 때 이야기이고, 위에서 다룬 것처럼 오브젝트 디렉터리를 분리하지 않았다면 일반 빌드와 sanitizer 빌드가 같은 오브젝트 이름을 놓고 충돌하는 문제는 여전히 남는다.

## ThreadSanitizer

ThreadSanitizer(`-fsanitize=thread`)는 레이스 컨디션과 잘못된 락 사용을 검출하는 sanitizer로, AddressSanitizer와 동시에 켤 수 없다는 제약이 있다. 둘 다 실행 시점에 메모리 접근을 가로채는 방식이 서로 충돌하기 때문이다. 그래서 프로젝트에 sanitizer target을 여러 개 두는 경우가 많다.

```make
.PHONY: tsan
tsan: CFLAGS += -fsanitize=thread -g -O1
tsan: LDFLAGS += -fsanitize=thread
tsan: build/bin/app-tsan
	./build/bin/app-tsan --self-test
```

ThreadSanitizer는 계측 오버헤드가 커서(대략 5~15배 느려지고 메모리도 몇 배 더 쓴다) 전체 테스트 스위트를 매번 이 옵션으로 돌리기보다는, 동시성 관련 코드를 수정했을 때나 CI의 별도 단계에서만 돌리는 방식이 흔하다.

## 정리 target

`clean`은 빌드 산출물을 지워서 "아무것도 빌드되지 않은 상태"로 되돌리는 target이다. 반드시 `.PHONY`로 선언해야 하며, 실수로 소스 디렉터리까지 지우지 않도록 빌드 산출물이 모이는 디렉터리(`build/` 등)만 정확히 지정해야 한다.

```make
.PHONY: clean
clean:
	rm -rf build
```

`clean`을 만든 뒤에는 `make clean && make all`을 실행해서 정말로 빈 상태에서부터 전체 빌드가 성공하는지 확인해봐야 한다. 평소에는 이전 빌드에서 남은 오브젝트나 디렉터리 덕분에 우연히 성공했던 규칙이, 완전히 빈 상태에서는 order-only prerequisite 누락 등으로 실패하는 경우가 실제로 자주 있다.

## 테스트는 무엇을 확인해야 하는가

C로 짠 프로그램의 테스트는 "정상 입력을 넣었을 때 정답이 나오는가"만 확인해서는 부족하다. C는 메모리를 직접 관리하고 타입 검사가 느슨하기 때문에, 정상 경로만 통과하는 테스트로는 실제로 발생하는 버그의 상당수(경계값 초과, 잘못된 free, 자원 누수)를 걸러내지 못한다. 아래 하위 항목들은 C 프로그램 테스트에서 특히 신경 써야 하는 카테고리들이다.

### 잘못된 인자

함수에 NULL 포인터, 범위를 벗어난 인덱스, 음수가 들어오면 안 되는 자리에 음수가 들어오는 등 "호출하는 쪽이 계약을 어긴" 상황을 테스트해야 한다. 이런 테스트는 함수가 죽지 않고 정의된 오류 코드를 돌려주는지, 혹은 명시적으로 그런 입력을 허용하지 않는 함수라면 assert로 즉시 실패하는지를 확인한다.

### 경계값

배열의 첫 원소와 마지막 원소, 크기가 0인 컬렉션, 버퍼 크기와 정확히 같은 길이의 문자열처럼 off-by-one 오류가 가장 잘 드러나는 지점을 별도로 테스트한다. `strncpy`, `memcpy`처럼 크기를 명시적으로 받는 함수를 쓸 때는 "정확히 버퍼 크기만큼" 들어오는 경우를 반드시 테스트 케이스에 포함시켜야 한다.

### overflow

정수 연산에서 오버플로가 일어날 수 있는 지점(곱셈으로 크기를 계산해 `malloc`에 넘기는 코드 등)은 의도적으로 큰 값을 넣어 오버플로가 발생하는지, 발생했을 때 어떻게 처리되는지를 테스트한다. 부호 있는 정수의 오버플로는 C 표준상 정의되지 않은 동작이므로, 이런 테스트는 UBSan과 함께 돌려야 실제로 오버플로가 발생했는지를 신뢰성 있게 잡아낼 수 있다.

### 할당 실패

`malloc`, `calloc` 등이 NULL을 반환하는 상황(메모리 부족)을 코드가 제대로 처리하는지 테스트한다. 실제 환경에서 메모리 부족을 재현하기는 어려우므로, 테스트에서는 흔히 malloc을 감싸는 래퍼 함수를 만들어 N번째 호출부터 의도적으로 NULL을 반환하게 하는 방식(fault injection)을 쓴다.

### 파일 디스크립터

`open`한 파일이나 소켓을 모든 경로(정상 종료, 에러로 인한 조기 리턴)에서 빠짐없이 `close`하는지 확인한다. 테스트에서는 함수 호출 전후로 `/proc/self/fd`(리눅스 기준) 안의 항목 수를 비교하거나, `lsof -p`로 프로세스가 열고 있는 파일 디스크립터 수를 비교해서 누수가 없는지 검증하는 방법을 쓴다.

### 자식 프로세스 종료 상태

`fork`/`exec`로 자식 프로세스를 만드는 코드는 자식이 정상 종료했는지, 시그널로 죽었는지, 종료 코드가 몇인지를 `waitpid`의 결과에서 `WIFEXITED`, `WEXITSTATUS`, `WIFSIGNALED` 매크로로 정확히 구분해야 한다. 테스트에서는 정상 종료, 0이 아닌 코드로 종료, 시그널(SIGSEGV 등)로 강제 종료되는 세 가지 경우를 모두 흉내 내는 자식 프로세스를 만들어 각각 부모가 올바르게 판별하는지 확인한다.

### timeout과 교착 상태

락을 여러 개 잡는 코드나 조건 변수를 기다리는 코드는, 조건이 영원히 만족되지 않을 때 테스트 자체가 무한정 멈춰버릴 위험이 있다. 이런 테스트는 반드시 자체 타임아웃을 둬서(예: `pthread_cond_timedwait` 사용, 또는 테스트 러너 레벨에서 `timeout` 명령으로 감싸기) 교착 상태가 "테스트 실패"로 확실히 보고되게 만들어야 한다. 타임아웃 없이 짠 동시성 테스트는 CI에서 그냥 멈춰버려 원인 파악이 훨씬 어려워진다.

### 동시 실행

여러 스레드가 같은 자원에 동시에 접근하는 코드는 한두 번 실행해서 통과했다고 안전하다고 볼 수 없다. 레이스 컨디션은 특정 스케줄링 타이밍에서만 드러나기 때문이다. 이런 테스트는 여러 번 반복 실행하거나(예: 같은 테스트를 수백 번 루프), ThreadSanitizer를 켠 빌드로 별도로 돌려서 스케줄링에 의존하지 않고 레이스 자체를 정적으로 가깝게 잡아내는 방식을 함께 써야 한다.

## 테스트 자체도 재현 가능해야한다

테스트가 실행할 때마다 다른 결과를 내면(플레이키 테스트), 실패했을 때 그게 실제 버그인지 테스트 환경 문제인지 판단할 수 없어 테스트에 대한 신뢰가 무너진다. 재현 가능한 테스트를 만들려면 난수를 쓸 때는 고정된 시드를 쓰고, 시스템 시각이나 환경 변수처럼 실행 환경에 따라 달라지는 값에 의존하는 로직은 테스트에서 그 값을 직접 주입할 수 있게(의존성 주입) 코드를 구성하며, 테스트 간에 전역 상태나 임시 파일 경로가 공유되지 않도록 각 테스트가 자신만의 격리된 자원을 쓰게 만들어야 한다.

## 독립 실행 확인

테스트 스위트 전체를 한 번에 돌렸을 때는 통과하는데 특정 테스트 하나만 따로 돌리면 실패한다면(혹은 그 반대라면), 테스트 간에 순서 의존성이나 상태 공유가 숨어 있다는 신호다. 흔한 원인은 이전 테스트가 만든 임시 파일이나 전역 변수를 다음 테스트가 정리 없이 그대로 이어받는 경우다. 이를 미리 잡아내려면 CI에서 전체 스위트 실행과는 별도로, 각 테스트를 무작위 순서로 섞어 실행하거나 하나씩 개별로 실행하는 단계를 추가해두는 것이 효과적이다.

## 예시 Makefile

지금까지 다룬 요소들을 하나로 합치면 대략 다음과 같은 형태가 된다.

```make
CC      = gcc
CFLAGS  = -Wall -Wextra -std=c11 -Iinclude -MMD -MP
LDFLAGS =
LDLIBS  = -lpthread

SRCS = $(wildcard src/*.c)
OBJS = $(patsubst src/%.c,build/obj/%.o,$(SRCS))
DEPS = $(OBJS:.o=.d)

.PHONY: all clean test sanitize

all: build/bin/app

build/bin/app: $(OBJS) | build/bin
	$(CC) $(LDFLAGS) $(OBJS) -o $@ $(LDLIBS)

build/obj/%.o: src/%.c | build/obj
	$(CC) $(CFLAGS) -c $< -o $@

build/obj build/bin:
	mkdir -p $@

test: build/bin/app
	./build/bin/app --self-test

sanitize: CFLAGS += -fsanitize=address,undefined -g -O0
sanitize: LDFLAGS += -fsanitize=address,undefined
sanitize: build/bin/app
	./build/bin/app --self-test

clean:
	rm -rf build

-include $(DEPS)
```

이 예시는 프로젝트 규모나 라이브러리 구성에 따라 달라지지만, 핵심 골격(자동 소스/오브젝트 목록 생성, 헤더 자동 의존성, 디렉터리를 order-only prerequisite로 분리, `.PHONY` target, sanitizer target 분리)은 대부분의 C 프로젝트에 그대로 적용할 수 있다.

## 빌드 파일을 읽을 때 확인할 사항

남이 짠 Makefile을 처음 볼 때는 다음 순서로 훑으면 빠르게 구조를 파악할 수 있다. 먼저 맨 위 몇 줄의 변수 정의(CC, CFLAGS, LDFLAGS 등)를 봐서 어떤 컴파일러와 옵션을 쓰는지 확인한다. 다음으로 `.PHONY` 선언을 찾아 이 Makefile이 제공하는 "동작"이 무엇인지(빌드, 테스트, 정리, sanitizer 등) 목록화한다. 그다음 `all` 또는 파일 맨 처음 target을 찾아 기본 실행 시 무엇이 만들어지는지 확인하고, 마지막으로 패턴 규칙과 `-include`로 불러오는 의존성 파일이 있는지를 봐서 헤더 변경이 재빌드에 반영되는 구조인지 판단한다. 이 네 가지만 확인해도 낯선 Makefile의 전체 그림을 대략 그릴 수 있고, 그 이후에 개별 target을 필요할 때마다 자세히 읽으면 된다.
