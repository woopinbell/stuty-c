# 자료구조와 API 작성

## 먼저 유효한 상태를 적기

자료구조를 설계할 때 가장 먼저 할 일은 함수를 나열하는 게 아니라 "이 구조체가 어떤 상태에 있으면 유효한가"를 문장으로 적는 것이다. 예를 들어 동적 배열이라면 `len <= cap`이 항상 성립해야 하고, `cap > 0`이면 `data`는 NULL이 아니어야 한다. 이 문장들이 곧 불변식(invariant)이며, 이후에 만들 모든 함수는 "호출 전에도 이 불변식이 성립했고, 호출 후에도 성립한다"는 것을 지켜야 한다.

```c
typedef struct {
    int *data;
    size_t len;   // 현재 원소 개수
    size_t cap;   // 할당된 공간
} int_vec;

// 불변식: len <= cap, cap == 0이면 data == NULL, cap > 0이면 data != NULL
```

유효한 상태를 먼저 적어두지 않으면, 나중에 버그를 발견했을 때 "이게 버그인지 원래 이런 상태를 허용하는지"조차 판단할 기준이 없다. 불변식을 먼저 문서화해두면 디버깅할 때 `assert`로 바로 검증할 수 있다.

## 불변식과 입력 검사는 같은 것이 아닙니다

불변식은 "구조체 내부적으로 항상 참이어야 하는 것"이고, 입력 검사는 "함수 바깥에서 들어온 값이 이 함수가 기대하는 조건을 만족하는가"를 확인하는 것이다. 이 둘을 같은 코드 경로로 처리하면 문제가 생긴다. 불변식이 깨졌다는 것은 라이브러리 내부 로직에 버그가 있다는 뜻이고, 입력 검사 실패는 호출자가 잘못된 값을 넘겼다는 뜻이다. 전자는 `assert`로 즉시 프로그램을 멈춰야 하고(디버그 빌드에서는 특히), 후자는 오류 코드를 반환해서 호출자가 복구할 기회를 줘야 한다.

```c
int int_vec_get(const int_vec *v, size_t idx, int *out) {
    assert(v->len <= v->cap);      // 불변식: 내부 버그면 여기서 죽는다
    if (idx >= v->len) {           // 입력 검사: 호출자의 실수, 정상적인 오류
        return -1;
    }
    *out = v->data[idx];
    return 0;
}
```

`assert`로 입력 검사를 대신하면, 릴리스 빌드에서 `NDEBUG`로 `assert`가 사라졌을 때 잘못된 인덱스가 그대로 통과해버린다. 반대로 모든 것을 오류 코드로 처리하면 내부 버그도 "정상적으로 실패하는 경우"처럼 취급되어 발견이 늦어진다.

## 공개 구조체와 불투명 타입

구조체를 헤더에 그대로 노출하면(공개 구조체) 호출자가 필드를 직접 읽고 쓸 수 있어 편리하지만, 그 순간부터 필드 이름과 레이아웃이 API 계약의 일부가 되어버린다. 나중에 내부 표현을 바꾸고 싶어도 이미 그 필드에 의존하는 코드가 있으면 바꿀 수 없다. 반대로 불투명 타입은 헤더에 선언만 두고 정의는 `.c` 파일에 숨겨서, 호출자가 반드시 제공된 함수를 통해서만 구조체를 다루게 만든다.

```c
// vec.h - 공개 구조체 방식
typedef struct {
    int *data;
    size_t len, cap;
} int_vec;   // 호출자가 v.len = 100; 처럼 직접 필드를 건드릴 수 있다
```

공개 구조체는 스택에 값으로 두거나 임베디드 환경처럼 동적 할당 없이 크기를 컴파일 타임에 알아야 하는 경우에 유리하다. **반면 내부 표현을 자유롭게 바꿀 여지를 남기고 싶거나, 잘못된 직접 조작을 막고 싶다면 불투명 타입이 낫다**.

### 불투명 타입

불투명 타입은 헤더에서 구조체 내용을 숨기고 포인터만 노출하는 방식이다.

```c
// vec.h
typedef struct int_vec int_vec;   // 불완전 타입 선언, 내용은 비공개

int_vec *int_vec_create(void);
void int_vec_destroy(int_vec *v);
int int_vec_push(int_vec *v, int value);
```

```c
// vec.c
struct int_vec {
    int *data;
    size_t len, cap;
};
```

호출자는 `sizeof(struct int_vec)`조차 알 수 없으므로 스택에 값으로 선언할 수 없고 반드시 `int_vec_create`가 반환한 포인터를 통해서만 다뤄야 한다. 그 대가로 매 객체마다 힙 할당이 하나 더 생기지만, 라이브러리 쪽에서는 구조체 레이아웃을 바이너리 호환성 걱정 없이 자유롭게 바꿀 수 있다.

## 함수별 성공과 실패 정하기

함수를 작성하기 전에 "이 함수가 실패할 수 있는 모든 경우"를 먼저 나열해야 한다. 메모리 할당 실패, 잘못된 인자, 크기 오버플로, 상태 불일치 등을 미리 정리해두지 않으면 구현 중간에 "이 경우엔 어떻게 하지"라는 질문이 생길 때마다 즉흥적으로 처리하게 되고, 결과적으로 같은 라이브러리 안에서도 함수마다 실패 처리 방식이 제각각이 된다.

```c
// int_vec_push가 실패할 수 있는 경우:
// 1. v가 NULL                 → 정의되지 않은 동작으로 둘지, 검사할지 미리 정한다
// 2. 용량 확장 중 malloc 실패 → -1 반환, v는 push 이전 상태 그대로 유지
// 3. len이 SIZE_MAX에 도달    → 오버플로 방지를 위해 -1 반환
int int_vec_push(int_vec *v, int value);
```

성공과 실패를 함수 작성 전에 정해두면 반환 타입(오류 코드 vs bool vs NULL 반환)도 자연스럽게 결정되고, 이후 모든 함수가 같은 규칙을 따르게 만들기 쉬워진다.

## 사전 조건과 사후 조건

사전 조건(precondition)은 함수를 호출하기 전에 호출자가 보장해야 하는 것이고, 사후 조건(postcondition)은 함수가 정상적으로 끝났을 때 보장하는 것이다. 이 둘을 함수 시그니처 옆에 주석으로 명시해두면, 구현을 볼 필요 없이 함수 선언만 보고도 안전하게 쓸 수 있다.

```c
// 사전 조건: v != NULL, idx < v->len
// 사후 조건: 반환값은 원래 v->data[idx]였던 값과 같다.
//            v의 len, cap, 다른 원소들은 변경되지 않는다.
int int_vec_get(const int_vec *v, size_t idx);
```

사전 조건을 명시하지 않으면 호출자는 "NULL을 넘기면 안전한지, idx가 범위를 벗어나면 어떻게 되는지"를 구현 코드를 읽어서 알아내야 한다. 사후 조건을 명시하지 않으면 "이 함수를 호출한 뒤 다른 포인터가 무효화되지는 않는지" 같은 것을 보장할 수 없다.

## 실패하기 쉬운 작업을 먼저 수행하기

함수 안에서 여러 단계를 거쳐야 한다면, 실패할 가능성이 있는 작업(메모리 할당, 파일 열기 등)을 먼저 하고 실패할 수 없는 작업(포인터 대입, 카운터 증가)을 나중에 해야 한다. 이렇게 순서를 정하면, 중간에 실패했을 때 이미 변경된 상태를 되돌릴 필요가 없다.

```c
int int_vec_push(int_vec *v, int value) {
    if (v->len == v->cap) {
        size_t new_cap = v->cap == 0 ? 4 : v->cap * 2;
        int *new_data = realloc(v->data, new_cap * sizeof(int));
        if (new_data == NULL) {
            return -1;        // 할당 실패로 v는 아직 아무것도 바뀌지 않은 상태
        }
        v->data = new_data;
        v->cap = new_cap;
    }
    v->data[v->len] = value;  // 여기부터는 실패할 수 없는 작업
    v->len += 1;
    return 0;
}
```

만약 순서가 반대라서 `v->len += 1`을 먼저 하고 나중에 `realloc`이 실패한다면, `len`은 이미 늘었는데 그만큼의 공간은 없는 불일치 상태가 되어버린다. 실패하기 쉬운 작업을 앞에 두면 이런 절반의 실패 상태 자체가 발생하지 않는다.

## 출력 매개변수는 성공 후 변경하기

함수가 포인터를 통해 결과를 돌려주는 출력 매개변수(out parameter)를 쓸 때는, 함수 내부의 모든 실패 가능 지점을 통과한 뒤 가장 마지막에 출력 매개변수를 채워야 한다. 중간에 실패할 수도 있는데 출력 매개변수를 미리 채워버리면, 호출자가 반환값을 확인하지 않고 실수로 출력 매개변수를 읽었을 때 절반만 쓰인 쓰레기 값을 보게 된다.

```c
int parse_config_line(const char *line, config_entry *out) {
    config_entry tmp;
    if (!split_key_value(line, &tmp)) {
        return -1;              // out은 전혀 건드리지 않았다
    }
    if (!validate_entry(&tmp)) {
        return -1;              // 여기서도 out은 그대로
    }
    *out = tmp;                 // 모든 검증을 통과한 뒤 마지막에 한 번만 대입
    return 0;
}
```

지역 변수에 먼저 결과를 만들고 마지막에 한 번의 대입으로 출력 매개변수에 복사하면, 함수가 중간 어디서 실패하든 출력 매개변수는 호출 전 값 그대로 유지된다는 것을 보장할 수 있다.

## 초기화와 정리

**모든 자료구조는 "만들어질 때 어떤 상태로 시작하는가"와 "다 쓰고 나면 무엇을 정리해야 하는가"가 짝을 이뤄야 한다**. 초기화 함수가 할당한 자원은 반드시 대응하는 정리 함수가 해제해야 하고, 이 둘의 이름과 동작은 대칭적이어야 한다(`_init`/`_destroy`, `_create`/`_free` 등).

```c
void int_vec_init(int_vec *v) {
    v->data = NULL;
    v->len = 0;
    v->cap = 0;
}

void int_vec_destroy(int_vec *v) {
    free(v->data);
    v->data = NULL;   // 재사용/재초기화 대비
    v->len = 0;
    v->cap = 0;
}
```

`_init`은 스택이나 다른 구조체 안에 이미 존재하는 메모리를 유효한 상태로 만드는 것이고, `_create`는 힙에 새 객체를 할당하는 것이다. 이 둘을 헷갈리게 이름 붙이면(`_init`인데 내부적으로 malloc으로 객체 자체를 새로 만든다든가) 호출자가 소유권을 착각하게 된다.

### 초기화되지 않은 객체

초기화하지 않은 구조체는 스택 위의 쓰레기 값을 그대로 담고 있으므로, 이 상태에서 아무 함수나 호출하면 정의되지 않은 동작이 된다. 특히 `int_vec_destroy`를 초기화 전에 호출하면 `free`에 쓰레기 포인터가 넘어가 크래시로 이어질 수 있다.

```c
int_vec v;              // v.data는 아직 쓰레기 값
int_vec_destroy(&v);    // 정의되지 않은 동작: free(쓰레기 포인터)
```

이 문제를 막는 흔한 방법은 스택 선언과 동시에 초기화를 강제하는 매크로나 항상 0으로 채워진 정적 초기값을 제공하는 것이다.

```c
#define INT_VEC_INIT { .data = NULL, .len = 0, .cap = 0 }
int_vec v = INT_VEC_INIT;   // 초기화를 빠뜨릴 수 없다
```

### 다시 초기화하기

이미 정리(destroy)한 객체를 다시 `_init`해서 재사용할 수 있는지는 API 계약에 명시적으로 정해야 한다. `int_vec_destroy`가 `data`를 NULL로, `len`과 `cap`을 0으로 되돌려놓는다면, 그 상태는 사실상 `int_vec_init` 직후 상태와 동일하므로 재사용이 안전하다. 이 대칭성을 지키지 않고 `destroy` 후 필드를 쓰레기 값으로 남겨두면, 재사용하려는 호출자는 반드시 다시 `_init`을 호출해야 하며 그렇지 않으면 이중 해제(double free)로 이어진다.

```c
int_vec v = INT_VEC_INIT;
int_vec_push(&v, 1);
int_vec_destroy(&v);
int_vec_init(&v);     // destroy가 v를 init과 같은 상태로 되돌렸으므로 안전하게 재시작 가능
int_vec_push(&v, 2);
int_vec_destroy(&v);
```

## 소유권과 정리 책임

포인터를 함수 인자로 넘기거나 반환할 때는 "이 메모리를 누가 해제할 책임을 지는가"를 항상 명시해야 한다. 이름이나 시그니처만 봐서는 알 수 없는 경우가 많기 때문에, 크게 세 가지 패턴으로 나눠 생각하면 된다: 함수가 소유권을 가져가는 경우(caller가 넘긴 뒤 더는 쓰면 안 됨), 함수가 소유권을 넘겨주는 경우(caller가 반환값을 반드시 해제해야 함), 함수가 그냥 빌려 쓰는 경우(호출이 끝나면 caller의 소유권은 그대로).

```c
// 소유권을 가져감: v는 이 함수 호출 후 str이 가리키던 메모리를 관리한다.
   caller는 이후 str을 free하면 안 된다.
void int_vec_set_label(int_vec *v, char *str);

// 소유권을 넘겨줌: caller가 반환된 포인터를 free()해야 한다.
char *int_vec_to_string(const int_vec *v);

// 그냥 빌려 씀: v는 호출 동안만 읽고, 소유권에 아무 영향도 없다.
void int_vec_print(const int_vec *v);
```

이 규칙을 함수 이름 규칙이나 헤더 주석으로 일관되게 표시해두지 않으면, 같은 라이브러리 안에서도 어떤 함수는 소유권을 가져가고 어떤 함수는 빌려 쓰는지 매번 구현을 읽어야 알 수 있게 되어 메모리 누수나 이중 해제의 원인이 된다.

## 할당 함수 주입

라이브러리 내부에서 `malloc`/`free`를 직접 호출하는 대신, 생성 함수에서 할당자 함수 포인터를 받아 그것을 쓰도록 만들면 호출자가 커스텀 할당 전략(메모리 풀, 아레나, 임베디드 환경의 정적 버퍼 등)을 끼워 넣을 수 있다.

```c
typedef void *(*alloc_fn)(void *ctx, size_t size);
typedef void  (*free_fn)(void *ctx, void *ptr);

typedef struct {
    alloc_fn alloc;
    free_fn  free;
    void    *ctx;
} allocator;

int_vec *int_vec_create_with(const allocator *a) {
    int_vec *v = a->alloc(a->ctx, sizeof(int_vec));
    if (v == NULL) return NULL;
    v->data = NULL;
    v->len = v->cap = 0;
    return v;
}
```

호출자는 표준 `malloc`을 감싼 기본 `allocator`를 넘길 수도 있고, 임베디드 환경에서는 고정 크기 정적 버퍼에서 잘라주는 할당자를 넘길 수도 있다. 라이브러리 코드 자체는 어떤 전략이 쓰이는지 몰라도 된다.

### allocator 콜백의 계약

`alloc` 콜백은 요청한 크기 이상의, 적절히 정렬된 메모리를 반환하거나 실패 시 NULL을 반환해야 한다. `free` 콜백은 같은 `ctx`로 만들어진 포인터만 받는다고 가정할 수 있어야 하며, NULL 포인터를 받았을 때 아무 일도 하지 않아야 한다(표준 `free(NULL)`과 같은 관례).

```text
alloc 콜백 계약:
- 반환값이 NULL이 아니면 최소 size 바이트, malloc과 동일한 정렬 보장
- 실패 시 NULL 반환 (라이브러리는 이 경우를 오류로 처리)
free 콜백 계약:
- ptr == NULL이면 아무 일도 하지 않는다
- ptr은 반드시 같은 allocator의 alloc이 반환한 값이어야 한다
```

이 계약을 명시하지 않으면, 호출자가 만든 커스텀 할당자가 정렬을 보장하지 않아 구조체 내부에서 정렬이 필요한 타입(예: `double`, SIMD 벡터)을 쓸 때 미묘하게 깨지는 버그가 생길 수 있다.

## 이름은 실제 동작을 드러내기

함수 이름은 그 함수가 실제로 하는 일과 부작용까지 드러내야 한다. `int_vec_get`이라는 이름만 보면 단순 조회로 보이지만 실제로는 내부적으로 정렬을 수행한다면, 그 이름은 거짓말을 하고 있는 것이다. 특히 할당이 일어나는지, 원본을 변경하는지는 이름에서 최대한 드러나야 한다.

```c
int_vec *int_vec_clone(const int_vec *v);   // 이름에 '복제'가 있으니 새 메모리 할당을 예상할 수 있다
void int_vec_sort_inplace(int_vec *v);      // 'inplace'로 원본이 바뀐다는 것을 명시
int_vec *int_vec_sorted(const int_vec *v);  // 원본은 그대로, 정렬된 새 벡터를 반환
```

`int_vec_sort`처럼 애매한 이름만 붙이면 호출자는 원본이 바뀌는지, 새 객체가 만들어지는지 함수 시그니처나 문서를 다시 확인해야 한다. `_inplace`, `_copy`, `_new` 같은 접미사를 일관되게 쓰면 이름만 보고도 부작용을 예상할 수 있다.

## 상태를 바꾸는 함수와 조회 함수를 구분하기

함수를 만들 때 "이 호출이 구조체의 상태를 바꾸는가, 아니면 그냥 읽기만 하는가"를 먼저 정하고, 조회 함수는 반드시 `const` 포인터를 받도록 강제해야 한다. 이렇게 하면 컴파일러가 실수로 조회 함수 안에서 상태를 바꾸는 코드를 쓰는 것을 막아준다.

```c
size_t int_vec_len(const int_vec *v);          // 조회: const로 상태 불변을 컴파일러가 강제
int    int_vec_push(int_vec *v, int value);    // 변경: const가 없으므로 상태를 바꿀 수 있음이 시그니처에 드러남
```

시그니처만 보고도 "이 함수를 호출하면 내 구조체가 바뀌는지"를 알 수 있다는 것은 큰 이점이다. 반대로 모든 함수가 non-const 포인터를 받는다면, 호출자는 매번 구현을 읽어야 안전하게 쓸 수 있다.

## 오류 코드

오류를 표현하는 방법은 여러 가지다: `int` 반환값(0은 성공, 음수는 실패), `bool` 반환, NULL 포인터 반환, 별도의 enum 오류 타입, `errno` 스타일의 전역 상태. 라이브러리 전체에서 하나의 방식을 일관되게 쓰는 것이 중요하고, 어떤 값이 성공이고 실패인지는 헤더 문서에 명시해야 한다.

```c
typedef enum {
    VEC_OK = 0,
    VEC_ERR_NOMEM,
    VEC_ERR_OUT_OF_RANGE,
    VEC_ERR_OVERFLOW,
} vec_status;

vec_status int_vec_push(int_vec *v, int value);
```

단순한 `int`(0/-1) 대신 enum을 쓰면 호출자가 실패 이유별로 다르게 대응할 수 있다(메모리 부족이면 재시도, 범위 오류면 프로그램 버그로 간주 등). 다만 enum 오류 코드는 함수가 정상적인 "값"을 반환해야 하는 경우(`int_vec_get`처럼 정수를 돌려줘야 하는 함수)에는 쓰기 어려우므로, 그런 함수는 출력 매개변수와 오류 코드를 분리하는 편이 낫다.

## 정수와 크기 검사

크기나 개수를 다루는 계산에서 정수 오버플로는 조용히 잘못된 동작으로 이어지는 가장 흔한 버그 원인 중 하나다. 특히 `개수 * 원소크기` 같은 곱셈을 `malloc`에 그대로 넘기면, 곱셈이 오버플로해서 작은 값이 되고 그 결과 실제보다 훨씬 작은 버퍼가 할당되어 이후 쓰기가 버퍼 밖을 침범할 수 있다.

```c
int_vec *int_vec_with_capacity(size_t n) {
    if (n > SIZE_MAX / sizeof(int)) {   // n * sizeof(int)가 오버플로하는지 곱셈 전에 검사
        return NULL;
    }
    int_vec *v = malloc(sizeof(int_vec));
    if (v == NULL) return NULL;
    v->data = malloc(n * sizeof(int));
    if (v->data == NULL) { free(v); return NULL; }
    v->len = 0;
    v->cap = n;
    return v;
}
```

`calloc(n, sizeof(int))`을 쓰면 이런 오버플로 검사를 라이브러리가 대신 해주므로, 곱셈이 필요한 할당에서는 직접 `malloc(n * size)`를 쓰는 것보다 `calloc`을 쓰는 편이 더 안전하다.

## capacity 증가 정책

동적 배열의 용량을 늘릴 때 필요한 만큼만 정확히 늘리면(예: 원소가 하나 필요할 때마다 `cap + 1`) `push`를 반복할 때마다 매번 `realloc`이 일어나 전체 삽입이 O(n²)이 되어버린다. 대신 용량이 부족할 때마다 현재 용량의 배수(보통 1.5배~2배)로 늘리면, `push`를 n번 반복했을 때 총 `realloc` 호출 횟수가 O(log n)으로 줄어 전체 삽입이 상환(amortized) O(n)이 된다.

```c
if (v->len == v->cap) {
    size_t new_cap = v->cap == 0 ? 4 : v->cap * 2;   // 2배씩 증가
    // new_cap 계산 자체도 오버플로 검사가 필요하다: v->cap * 2가 SIZE_MAX를 넘는 경우
    if (new_cap < v->cap) {
        return VEC_ERR_OVERFLOW;
    }
    ...
}
```

2배씩 늘리는 대신 1.5배를 쓰기도 하는데, 이는 이전에 해제된 블록들을 이어붙여서 재사용할 수 있는 여지를 늘려 메모리 단편화를 줄이려는 목적이다. 어떤 배수를 쓰든, 늘어난 용량만큼 남는 메모리 낭비와 재할당 빈도 사이의 트레이드오프라는 점은 같다.

## 별칭과 자기 참조

별칭(aliasing)이란 두 개 이상의 포인터나 참조가 같은 메모리를 가리키는 상황을 말한다. `memcpy`나 `realloc`처럼 포인터를 다루는 함수들은 별칭 상황에서 정의되지 않은 동작을 하거나 위험해질 수 있으므로, API 문서에서 "이 함수에 별칭이 있는 인자를 넘겨도 되는가"를 명시해야 한다.

```c
// int_vec_append(dst, src)를 int_vec_append(&v, &v)처럼 자기 자신에게 호출하면?
// 구현이 이를 고려하지 않았다면 정의되지 않은 동작이 될 수 있다.
int int_vec_append(int_vec *dst, const int_vec *src);
```

### `realloc`으로 입력 포인터가 무효화될 수 있음

`realloc`은 성공하면 기존 블록을 그대로 확장할 수도 있지만, 공간이 부족하면 완전히 새로운 위치에 블록을 할당하고 기존 블록을 해제한 뒤 새 주소를 반환할 수도 있다. 이때 기존 포인터를 참조하던 다른 변수나 구조체 필드가 남아 있다면, 그 포인터들은 모두 해제된 메모리를 가리키는 댕글링 포인터가 된다.

```c
int *old = v->data;
int *new_data = realloc(v->data, new_cap * sizeof(int));
if (new_data == NULL) {
    // old는 여전히 유효하다: realloc 실패 시 원본 블록은 그대로 남는다
    return VEC_ERR_NOMEM;
}
v->data = new_data;
// 여기서부터 old는 realloc이 블록을 이동시켰다면 이미 무효한 포인터일 수 있다.
// old를 더 쓰면 안 되고, 반드시 v->data(새 포인터)만 써야 한다.
```

이 문제는 구조체 안에 자기 자신의 원소를 가리키는 포인터를 별도로 캐싱해뒀을 때 특히 위험하다. `realloc` 이후 그 캐시된 포인터를 갱신하지 않으면 댕글링 포인터가 조용히 남는다.

### 원본과 대상 복사 영역이 겹칠 수 있음

`memcpy`는 원본과 대상 영역이 겹치지 않는다고 가정하고 최적화되어 있어서, 겹치는 영역에 쓰면 정의되지 않은 동작이 된다. 같은 배열 안에서 원소들을 앞이나 뒤로 밀어야 하는 경우(예: 배열 중간에서 원소 삭제 후 뒤 원소들을 앞으로 당기기)에는 반드시 겹침을 허용하는 `memmove`를 써야 한다.

```c
void int_vec_remove_at(int_vec *v, size_t idx) {
    assert(idx < v->len);
    size_t tail_count = v->len - idx - 1;
    if (tail_count > 0) {
        // &v->data[idx]와 &v->data[idx+1]이 가리키는 영역은 서로 겹친다 -> memmove 필수
        memmove(&v->data[idx], &v->data[idx + 1], tail_count * sizeof(int));
    }
    v->len -= 1;
}
```

두 영역이 절대 겹치지 않는다는 것을 함수가 직접 보장할 수 있는 경우(예: 서로 다른 두 개의 독립된 배열을 합칠 때)에만 `memcpy`를 쓰고, 조금이라도 같은 배열 안에서 위치를 옮기는 연산이라면 `memmove`를 기본으로 선택하는 편이 안전하다.

## API를 읽을 때 확인할 사항

낯선 C 라이브러리의 헤더를 처음 읽을 때는 다음을 순서대로 확인하면 함정을 크게 줄일 수 있다: 각 함수가 어떤 사전 조건을 요구하는지, 반환값으로 성공과 실패를 어떻게 구분하는지, 포인터 인자나 반환값의 소유권이 누구에게 있는지, 구조체가 공개 타입인지 불투명 타입인지, 그리고 함수 이름에 붙은 접미사(`_init`/`_create`, `_inplace`/`_copy` 등)가 실제 부작용과 일치하는지.

```text
헤더를 읽을 때 스스로에게 물어야 할 질문들의 예:
1. int_vec_get(v, idx)에서 idx가 범위를 벗어나면? (사전 조건 위반, 문서에 명시돼 있는가)
2. int_vec_to_string(v)이 반환한 char*는 내가 free해야 하는가?
3. int_vec_sort(v)는 v를 제자리에서 바꾸는가, 새 벡터를 반환하는가?
4. 이 구조체는 스택에 값으로 선언 가능한가, 아니면 반드시 _create를 거쳐야 하는가?
```

이 질문들에 대한 답이 헤더 주석만으로 즉시 나오지 않는다면, 그 API는 구현을 열어봐야만 안전하게 쓸 수 있는 API라는 뜻이고 이는 API 설계 단계에서 놓친 지점이 있다는 신호로 봐야 한다.
