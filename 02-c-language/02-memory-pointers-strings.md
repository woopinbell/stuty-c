# 메모리, 포인터, 문자열

## 객체와 주소

C에서 변수는 결국 메모리 안의 한 구간을 가리키는 이름이다. `int x = 5;`라고 쓰면 컴파일러는 `x`라는 이름과 특정 크기(보통 4바이트)의 메모리 구간을 연결하고, `&x`는 그 구간이 시작하는 주소를 값으로 돌려준다. 포인터는 이 주소를 담는 별도의 객체일 뿐이다. `int *p = &x;`는 "정수를 가리키는 포인터"라는 타입을 가진 새 변수 `p`를 만들고, 그 안에 `x`의 주소를 저장한다.

포인터에 타입이 붙는 이유는 역참조(`*p`) 시 몇 바이트를 읽고 그 비트 패턴을 어떻게 해석할지 컴파일러가 알아야 하기 때문이다. `int *`와 `char *`는 둘 다 주소를 담지만, `*p`를 했을 때 하나는 4바이트를 `int`로, 하나는 1바이트를 `char`로 읽는다. 이 타입 정보가 없으면 포인터 산술(다음 절)도 정의할 수 없다.

```c
int x = 5;
int *p = &x;
printf("%d\n", *p);   // 5
*p = 10;
printf("%d\n", x);    // 10, p를 통해 x 자체를 바꿨다
```

## NULL 포인터

NULL 포인터는 "아무 객체도 가리키지 않는다"는 것을 명시적으로 나타내는 값이다. 초기화하지 않은 포인터(와일드 포인터)와 구분해야 한다. 초기화하지 않은 포인터는 쓰레기 값을 담고 있어서 역참조하면 어디를 건드릴지 예측 불가능하지만, NULL 포인터는 최소한 "지금은 유효하지 않다"는 사실 자체는 검사 가능하다.

`malloc` 실패, 리스트의 끝, 아직 할당되지 않은 자원 등을 표현할 때 관례적으로 NULL을 쓴다. 문제는 NULL 포인터를 역참조하면 정의되지 않은 동작(대부분의 플랫폼에서는 세그먼테이션 폴트)이 발생한다는 점이다. 그래서 포인터를 반환하는 함수를 쓸 때는 사용하기 전에 NULL 검사를 하는 습관이 필요하다.

```c
char *buf = malloc(100);
if (buf == NULL) {
    // 할당 실패 처리, 여기서 buf를 그대로 쓰면 안 된다
    return -1;
}
```

포인터를 해제한 뒤 곧바로 NULL로 덮어써 두는 것도 흔한 방어 기법이다(이후 "얕은 복사와 이중 해제"에서 왜 중요한지 다룬다).

## 저장 기간과 객체 수명

객체가 언제 만들어지고 언제 사라지는지는 그 객체의 *저장 기간*(storage duration)에 따라 결정된다. C는 크게 자동, 정적, 할당 세 가지 저장 기간을 구분하며, 포인터가 가리키는 객체의 수명이 포인터 자신의 수명보다 먼저 끝나버리면 댕글링 포인터가 생긴다. 이 절 전체가 결국 그 문제를 피하기 위한 배경 지식이다.

### 자동 저장 기간

함수 안에서 선언한 지역 변수는 자동 저장 기간을 가진다. 그 변수가 선언된 블록에 진입할 때 스택에 생성되고, 블록을 빠져나가는 순간(보통 함수가 리턴할 때) 소멸한다. 함수가 지역 변수의 주소를 반환하면 안 되는 이유가 바로 이것이다. 함수가 리턴하는 순간 그 스택 프레임은 재사용 가능한 영역으로 반환되고, 포인터는 더 이상 유효하지 않은 주소를 가리키게 된다.

```c
int *dangerous(void) {
    int local = 42;
    return &local;   // 잘못됨: local은 함수가 끝나면 사라진다
}
```

### 정적 저장 기간

`static` 지역 변수나 파일 스코프 변수, 전역 변수는 정적 저장 기간을 가진다. 프로그램이 시작될 때 생성되어 프로그램이 종료될 때까지 유지되므로, 이런 변수의 주소는 함수 호출이 끝나도 안전하게 반환할 수 있다. 다만 정적 저장 기간 객체는 프로그램 전체에서 하나만 존재하므로, 재진입이 필요한 함수(같은 함수가 동시에 여러 곳에서 실행되는 상황)에서는 상태 공유 문제가 생길 수 있다.

### 할당 저장 기간

`malloc`, `calloc`, `realloc`으로 얻은 메모리는 할당 저장 기간을 가진다. 이 메모리는 명시적으로 `free`를 호출하기 전까지 계속 살아있다. 함수를 빠져나가도, 심지어 그 메모리를 가리키던 포인터 변수가 스코프를 벗어나도 메모리 자체는 해제되지 않는다. 이 특성 덕분에 함수 안에서 만든 데이터를 함수 밖으로 안전하게 전달할 수 있지만, 반대로 `free`를 잊으면 메모리 누수로 이어진다.

## 할당 성공 여부와 크기 계산

`malloc`은 요청한 크기의 메모리를 확보하지 못하면 NULL을 반환한다. 반환값을 검사하지 않고 바로 역참조하면 NULL 포인터 역참조로 프로그램이 죽는다. 또한 크기 계산에서 정수 오버플로가 발생하면 의도한 것보다 훨씬 작은 메모리가 할당되어, 이후 그 메모리에 쓰기 작업을 할 때 버퍼 오버플로로 이어질 수 있다.

```c
size_t n = 1000000000;
int *arr = malloc(n * sizeof(int));   // n * sizeof(int)가 오버플로할 수 있다
if (arr == NULL) {
    // 실패 처리
}
```

크기를 계산할 때는 오버플로 여부를 먼저 확인하거나, 표준 라이브러리가 제공하는 `calloc(nmemb, size)`처럼 곱셈 오버플로를 내부적으로 검사해주는 함수를 쓰는 편이 안전하다.

### `malloc(0)`

`malloc(0)`을 호출했을 때의 동작은 구현 정의다. NULL을 반환할 수도 있고, `free`로 해제 가능한 유효한(하지만 역참조해서는 안 되는) 포인터를 반환할 수도 있다. 어느 쪽이든 반환값이 NULL이 아니라고 해서 "할당이 성공했으니 0바이트짜리 객체에 뭔가 쓸 수 있다"고 착각하면 안 된다. 크기가 0이 될 수 있는 경로가 있다면, `malloc`을 호출하기 전에 그 경우를 별도로 처리하는 편이 이식성 있는 코드가 된다.

## `realloc`의 의미와 실패 처리

`realloc(ptr, new_size)`는 기존에 할당된 블록의 크기를 바꾼다. 내부적으로는 세 가지 경우가 있다. 같은 위치에서 크기만 조정되거나, 새 위치에 더 큰 블록을 할당하고 기존 데이터를 복사한 뒤 원래 블록을 해제하거나, 실패해서 아무것도 하지 않고 NULL을 반환한다. 이 중 어느 경우가 일어날지는 호출자가 미리 알 수 없다는 점이 실패 처리 방식을 좌우한다.

```c
char *buf = malloc(10);
char *tmp = realloc(buf, 100);
if (tmp == NULL) {
    // realloc 실패: buf는 여전히 유효하고 해제되지 않은 채 남아있다
    free(buf);
    return -1;
}
buf = tmp;   // 성공했을 때만 원래 포인터를 덮어쓴다
```

`realloc`의 반환값을 원래 포인터 변수에 직접 대입하면(`buf = realloc(buf, 100);`) 실패 시 NULL이 `buf`에 들어가면서 원래 블록의 주소를 잃어버려 메모리 누수가 생긴다. 반드시 임시 변수에 받아서 NULL 여부를 확인한 뒤 대입해야 한다.

### `realloc` 성공 후 기존 별칭

`realloc`이 메모리를 새 위치로 옮기는 경우, 기존 포인터가 가리키던 주소는 더 이상 유효하지 않다. 문제는 같은 블록을 가리키던 다른 별칭(alias) 포인터가 프로그램 어딘가에 남아있을 수 있다는 점이다. `realloc` 호출 하나만으로는 그 별칭들을 갱신해주지 않으므로, 이동이 일어났다면 옛 별칭은 전부 댕글링 포인터가 된다. 여러 포인터가 같은 블록을 가리키는 구조를 설계할 때는 `realloc`을 호출하는 지점을 하나로 모으고, 이동이 일어났을 때 관련된 모든 별칭을 갱신할 책임을 어디서 질지 미리 정해야 한다.

### `realloc(pointer, 0)`

`realloc(ptr, 0)`의 동작도 `malloc(0)`처럼 구현마다 다르게 정의될 수 있다. 어떤 구현은 `ptr`을 해제하고 NULL을 반환하지만, 표준에 따라서는 NULL이 아닌 최소 크기 포인터를 돌려줄 수도 있다. 크기 0으로 줄이는 경로를 "free와 동일하다"고 가정하고 작성한 코드는 이식성이 떨어진다. 크기가 0이 될 수 있다면 `realloc`을 호출하기 전에 명시적으로 분기해서 `free`를 직접 호출하는 편이 의도를 명확히 한다.

## 소유권

동적으로 할당된 메모리는 그 메모리를 해제할 책임이 있는 코드가 정확히 하나 있어야 한다. 이를 소유권이라고 부른다. 소유권이 불명확하면 두 가지 실패 양상이 나온다: 아무도 해제하지 않아서 생기는 메모리 누수, 그리고 둘 이상이 해제를 시도해서 생기는 이중 해제다. 함수가 포인터를 반환하거나 인자로 받을 때, "이 포인터를 해제할 책임이 호출자에게 넘어가는지, 아니면 함수 내부(또는 구조체)가 계속 소유하는지"를 함수의 계약(문서화)으로 명시해야 한다.

```c
// 관례: 이 함수가 반환하는 포인터는 호출자가 free 해야 한다.
char *make_greeting(const char *name) {
    char *buf = malloc(strlen(name) + 8);
    sprintf(buf, "Hello, %s", name);
    return buf;
}
```

이런 계약이 주석이나 문서로만 존재하고 타입 시스템으로 강제되지 않는다는 점이 C 메모리 관리의 근본적인 어려움이다. 프로젝트 차원에서 네이밍 규칙(예: `_owned`, `_borrowed` 접미사)이나 일관된 패턴을 정해두면 실수를 줄일 수 있다.

## 얕은 복사와 이중 해제

구조체를 대입하거나 포인터 필드를 그대로 복사하면, 그 필드가 가리키는 메모리 자체가 복제되는 게 아니라 같은 주소를 가리키는 포인터가 하나 더 생긴다. 이것이 얕은 복사다. 두 구조체가 같은 힙 메모리를 공유하게 된 상태에서 어느 한쪽이 그 메모리를 `free`하면, 다른 쪽은 이미 해제된 메모리를 가리키는 댕글링 포인터를 들고 있게 된다.

```c
typedef struct { char *name; } Person;

Person a = { .name = malloc(10) };
strcpy(a.name, "Alice");

Person b = a;        // 얕은 복사: b.name은 a.name과 같은 주소를 가리킨다
free(a.name);
free(b.name);        // 이중 해제, 정의되지 않은 동작
```

이중 해제는 미묘한 버그다. 당장 크래시가 나지 않는 경우도 많아서, 힙 관리자의 내부 상태가 조용히 손상된 채 훨씬 나중에 관련 없어 보이는 코드에서 크래시가 발생하기도 한다. 이를 피하려면 깊은 복사(포인터가 가리키는 내용까지 새로 할당해서 복제)를 하거나, 애초에 소유권을 한쪽에만 두고 다른 쪽은 참조만 하도록 설계해야 한다.

## 배열 범위와 포인터 연산

배열 이름은 대부분의 맥락에서 첫 원소를 가리키는 포인터로 decay(붕괴)된다. 포인터에 정수를 더하는 연산은 바이트 단위가 아니라 "그 포인터가 가리키는 타입의 크기" 단위로 이동한다. `p + 1`은 `p`가 `int *`라면 4바이트, `double *`라면 8바이트 뒤를 가리킨다.

표준이 보장하는 유효한 포인터 산술의 범위는 배열의 첫 원소부터 "마지막 원소 바로 다음 한 칸"까지다. 그 이상으로 벗어난 포인터를 만들거나 역참조하는 것은 정의되지 않은 동작이다.

```c
int arr[5] = {0, 1, 2, 3, 4};
int *p = arr;
int *end = arr + 5;   // 유효: 마지막 원소 바로 다음을 가리키는 포인터 (역참조는 안 됨)
int *bad = arr + 6;   // 정의되지 않은 동작: 배열 범위를 벗어난 포인터 생성 자체가 문제
```

`end`처럼 **"마지막 다음 한 칸"을 가리키는 포인터는 역참조만 하지 않으면 유효**하며, 반복문의 종료 조건(`for (p = arr; p != end; p++)`)으로 흔히 쓰인다.

## 포인터 차이와 오프셋

같은 배열 안의 두 포인터를 빼면 그 사이에 몇 개의 원소가 있는지를 나타내는 정수(`ptrdiff_t` 타입)가 나온다. 이 연산도 두 포인터가 같은 배열(또는 그 바로 다음 한 칸까지)을 가리킬 때만 정의된다. 서로 다른 배열에 속한 포인터끼리 빼는 것은 정의되지 않은 동작이다.

```c
int arr[10];
int *p1 = &arr[2];
int *p2 = &arr[7];
ptrdiff_t diff = p2 - p1;   // 5, 원소 5개 차이, 바이트 차이가 아니다
```

포인터 차이 결과를 `int`에 담으면 배열이 매우 클 때 오버플로할 수 있으므로, 반드시 `ptrdiff_t`(또는 최소한 `long` 이상)로 받아야 한다.

## C 문자열과 버퍼

C에서 문자열은 별도의 타입이 아니라 관례다. `char` 배열 안에 문자들이 연속으로 들어있고, 문자열의 끝을 널 종료 문자(`'\0'`)로 표시한다. 그래서 "문자열의 길이"와 "문자열을 담고 있는 버퍼의 크기"는 서로 다른 개념이다. 버퍼는 실제 문자 수보다 항상 최소 1바이트(널 종료 문자 몫) 더 커야 한다.

```c
char buf[6];
strcpy(buf, "hello");   // "hello"는 5글자 + 널 종료 문자 1바이트 = 6바이트, buf 크기와 정확히 일치
```

버퍼 크기를 문자 수와 혼동해서 널 종료 문자를 위한 공간을 빼먹는 실수(off-by-one)가 C 문자열 버그의 가장 흔한 원인이다.

## `strlen`의 전제

`strlen`은 주어진 포인터에서 시작해서 널 종료 문자가 나올 때까지 메모리를 순차적으로 읽어 그 사이의 바이트 수를 센다. 이 함수가 올바르게 동작하려면 그 메모리 구간 어딘가에 반드시 널 종료 문자가 존재해야 한다는 전제가 필요하다. 널 종료되지 않은 `char` 배열에 `strlen`을 호출하면, 배열 경계를 넘어 계속 읽어나가며 정의되지 않은 동작이 발생한다.

`memcpy`나 반복문으로 문자 배열을 채울 때, 원본이 널 종료되어 있다고 가정하지 말고 실제로 널 종료 문자가 포함되는지 항상 확인해야 한다.

## 문자열 복사 크기 계산

`strcpy(dst, src)`는 `dst`가 `src`를 담기에 충분한 크기(널 종료 문자 포함)인지 검사하지 않는다. 안전하게 쓰려면 복사하기 전에 `dst`의 크기가 `strlen(src) + 1` 이상인지 호출자가 직접 보장해야 한다.

`strncpy(dst, src, n)`는 더 안전해 보이지만 함정이 있다. `src`의 길이가 `n` 이상이면 `dst`에 널 종료 문자를 붙여주지 않는다. 그래서 `strncpy`를 쓴 뒤에는 `dst[n-1] = '\0';`을 직접 해주거나, 복사된 결과가 항상 널 종료됨을 별도로 보장하는 패턴이 필요하다.

```c
char dst[10];
strncpy(dst, src, sizeof(dst) - 1);
dst[sizeof(dst) - 1] = '\0';   // strncpy가 널 종료를 보장하지 않을 경우를 대비
```

## 길이와 용량을 함께 관리하는 문자열

매번 `strlen`으로 길이를 다시 계산하는 대신, 길이(현재 문자 수)와 용량(버퍼 전체 크기)을 별도의 필드로 함께 들고 있는 구조체를 쓰면 문자열 연산의 비용과 안전성이 크게 달라진다. `strlen`은 O(n) 연산이라 반복적으로 호출하면 누적 비용이 커지고, 길이를 별도로 추적하면 이 비용을 없앨 수 있다.

```c
typedef struct {
    char *data;
    size_t length;    // 현재 문자 수 (널 종료 문자 제외)
    size_t capacity;  // data가 가리키는 버퍼의 전체 크기
} String;
```

이런 구조를 쓰면 문자열에 내용을 덧붙일 때(`append`) 매번 정확한 크기로 `realloc`하는 대신, 용량에 여유를 두고 미리 늘려서(예: 부족할 때 두 배씩 확장) 재할당 횟수 자체를 줄이는 전략도 가능해진다.

## `memcpy`와 `memmove`

`memcpy`와 `memmove`는 둘 다 지정한 바이트 수만큼 메모리를 복사하지만, 원본과 대상이 겹치는 경우의 동작이 다르다. `memcpy`는 두 영역이 겹치지 않는다고 가정하고 최적화되어 있어서, 겹치는 영역에 쓰면 정의되지 않은 동작이 발생할 수 있다. `memmove`는 겹치는 경우에도 올바르게 동작하도록 원본을 먼저 임시 버퍼로 옮기거나 복사 방향을 조정하는 식으로 구현되어 있다. 대신 그만큼 약간의 오버헤드가 붙는다.

```c
char buf[] = "abcdefgh";
memmove(buf + 2, buf, 4);   // buf 내부에서 겹치는 영역으로 이동. memmove만 안전
// 결과: "ababcdgh"
```

두 포인터가 서로 다른 할당에서 나왔다는 확신이 없다면(즉 겹칠 가능성을 배제할 수 없다면) `memmove`를 기본으로 쓰는 편이 안전하다.

## 별칭과 내부 포인터

"별칭"은 서로 다른 두 포인터(또는 포인터와 배열 인덱스)가 같은 메모리 영역을 가리키는 상황을 말한다. 별칭 자체는 문제가 아니지만, 컴파일러가 두 포인터가 겹치지 않는다고 가정하고 최적화한 코드에서 실제로는 겹칠 때 예상과 다른 결과가 나올 수 있다. 함수 인자로 포인터 두 개를 받는 함수(`memcpy`가 대표적)는 대개 "인자들이 겹치지 않는다"는 전제를 문서에 명시하고, 그 전제를 어기는 호출은 정의되지 않은 동작으로 취급한다.

구조체 안에 다른 객체를 가리키는 포인터(내부 포인터)를 저장해둔 경우, 그 포인터가 가리키는 대상의 수명이 구조체 자신의 수명보다 짧으면 구조체가 살아있는 동안 내부 포인터가 댕글링 상태가 될 수 있다. 내부 포인터를 쓸 때는 그 포인터가 가리키는 대상의 수명이 최소한 포인터를 담고 있는 객체의 수명만큼은 유지된다는 것을 설계 단계에서 보장해야 한다.

## 별칭 입력과 `realloc`

`realloc`에 넘기는 포인터와 그 포인터가 가리키는 데이터를 참조하는 다른 별칭이 함께 존재하는 상황은 특히 주의가 필요하다. `realloc`이 메모리를 이동시키면, 그 시점 이전에 계산해둔 "블록 내부를 가리키는 다른 포인터"는 전부 무효화된다. 오프셋(원래 포인터로부터의 상대적 위치)만 기억해두고, `realloc`이 끝난 뒤 새 포인터를 기준으로 다시 계산하는 식으로 처리해야 이런 무효화를 피할 수 있다.

```c
char *buf = malloc(100);
char *mid = buf + 50;      // buf 내부를 가리키는 별칭

char *tmp = realloc(buf, 200);
if (tmp != NULL) {
    buf = tmp;
    mid = buf + 50;        // 오프셋을 기준으로 다시 계산, 옛 mid를 그대로 쓰면 안 된다
}
```

## `const`

포인터 선언에서 `const`가 붙는 위치에 따라 의미가 달라진다. `const char *p`는 "`p`를 통해 가리키는 대상을 바꿀 수 없다"는 뜻이고(포인터 자체는 다른 곳을 가리키도록 재대입 가능), `char *const p`는 "`p` 자체가 항상 같은 주소를 가리켜야 한다"는 뜻이다(가리키는 내용은 다른 경로로 바뀔 수 있음). 두 `const`를 함께 쓰면(`const char *const p`) 둘 다 고정된다.

```c
void print_name(const char *name) {   // name이 가리키는 문자열을 이 함수가 바꾸지 않겠다는 계약
    printf("%s\n", name);
}
```

함수 인자에 `const`를 붙이는 것은 단순한 스타일이 아니라, 호출자에게 "이 함수는 네가 넘긴 데이터를 수정하지 않는다"는 계약을 컴파일러가 검사할 수 있는 형태로 명시하는 것이다. 이 계약을 어기고 함수 내부에서 `const` 포인터를 비-`const` 포인터로 캐스팅해 수정을 시도하면 정의되지 않은 동작이 될 수 있다(특히 원본 객체가 실제로 `const`로 선언된 경우).

## 정리 함수

여러 자원(메모리, 파일 핸들, 락 등)을 순서대로 할당하는 코드에서는, 중간 단계에서 실패했을 때 그 시점까지 확보한 자원만 정확히 해제해야 한다. 이를 체계적으로 하는 흔한 패턴이 `goto`를 이용한 정리(cleanup) 경로다. 각 실패 지점에서 이미 획득한 자원만 해제하는 레이블로 건너뛴다.

```c
int setup(void) {
    char *a = malloc(10);
    if (a == NULL) goto fail_a;

    char *b = malloc(20);
    if (b == NULL) goto fail_b;

    FILE *f = fopen("data.txt", "r");
    if (f == NULL) goto fail_f;

    fclose(f);
    free(b);
    free(a);
    return 0;

fail_f:
    free(b);
fail_b:
    free(a);
fail_a:
    return -1;
}
```

`goto`를 이런 식으로 쓰는 것은 임의의 점프가 아니라, 자원 해제 순서(획득의 역순)를 명시적으로 강제하는 관용구다. 자원 종류가 많아질수록 각 실패 지점에서 정확히 무엇이 이미 획득되어 있는지를 놓치지 않는 것이 이 패턴의 핵심이다.

## 메모리 코드를 읽을 때 확인할 사항

낯선 C 코드에서 메모리 관련 버그를 찾을 때 확인할 만한 지점들을 정리하면 다음과 같다.

- 모든 `malloc`/`calloc`/`realloc` 호출의 반환값이 NULL 검사를 거치는가.
- 각 할당된 블록에 대해 `free`를 호출하는 경로가 (정상 종료든 에러 처리든) 모든 실행 흐름에 존재하는가. 특히 함수 중간의 `return`이나 `goto`가 정리 코드를 건너뛰지 않는가.
- 같은 블록을 가리키는 포인터가 여러 개 있다면, 그중 정확히 하나만 `free`를 호출하는가(소유권이 명확한가).
- `free`한 뒤 그 포인터를 다시 역참조하거나 재사용하는 코드가 없는가(댕글링 포인터), `free`한 포인터를 NULL로 즉시 덮어썼는가.
- `realloc`의 반환값을 임시 변수로 받아 NULL을 검사한 뒤에만 원래 포인터에 대입하는가.
- 포인터 산술이나 배열 인덱싱이 할당된 범위(또는 배열의 "마지막 다음 한 칸")를 벗어나지 않는가.
- 문자열을 다루는 함수 호출마다 대상 버퍼가 널 종료 문자를 포함해 충분한 크기인지 계산이 맞는가.
- 크기를 계산하는 곱셈, 덧셈에서 정수 오버플로 가능성이 있는가, 특히 사용자 입력이 크기 계산에 관여하는 경우.
