# C 프로그램의 구성과 전처리

## 빌드 단계

C 소스 파일 하나가 실행 파일이 되기까지는 눈에 보이지 않는 네 단계를 거친다: 

```text
전처리(preprocessing)
→ 컴파일(compilation, 소스를 어셈블리로 변환)
→ 어셈블(assembly, 어셈블리를 기계어 오브젝트 코드로 변환)
→ 링크(linking, 여러 오브젝트 파일과 라이브러리를 하나의 실행 파일로 결합)
```

흔히 "컴파일"이라는 말로 이 네 단계 전체를 뭉뚱그려 부르지만, 각 단계는 서로 다른 도구가 담당하고 서로 다른 종류의 오류를 낸다.

이 구분이 왜 중요하냐면, 에러 메시지가 어느 단계에서 났는지에 따라 원인이 완전히 다르기 때문이다. 전처리 단계 오류(매크로 오용, `#include` 경로 실패)는 문법과 무관하게 발생하고, 컴파일 단계 오류(타입 불일치, 문법 오류)는 번역 단위 하나 안에서만 보이고, 링크 단계 오류("undefined reference")는 여러 번역 단위를 합칠 때만 드러난다. 세 단계를 구분하지 못하면 링커 오류를 컴파일러 오류로 착각해 엉뚱한 곳(타입 선언)을 고치려 드는 실수를 하게 된다.

```c
// main.c
#include "util.h"
int main(void) {
    return add(1, 2);
}
```

```bash
gcc -E main.c -o main.i     # 1) 전처리만: #include, 매크로가 展開된 순수 C 텍스트
gcc -S main.i -o main.s     # 2) 컴파일: 어셈블리 코드 생성
gcc -c main.s -o main.o     # 3) 어셈블: 오브젝트 파일(기계어 + 심볼 테이블) 생성
gcc main.o util.o -o main   # 4) 링크: 여러 .o를 실행 파일로 결합
```

## 각 단계의 결과 확인하기

빌드 과정을 눈으로 직접 확인할 수 있어야 어느 단계에서 문제가 생겼는지 진단할 수 있다. gcc/clang은 각 단계 직후에 멈춰서 결과물을 파일로 남기는 플래그를 제공한다.

- `gcc -E foo.c`: 전처리 결과만 표준 출력으로 보여준다. 매크로가 실제로 어떤 텍스트로 치환되는지, `#include`가 어떤 내용을 끌어왔는지를 그대로 볼 수 있다. 매크로가 예상과 다르게 동작할 때 가장 먼저 확인해야 할 단계다.
- `gcc -S foo.c`: `.s` 어셈블리 파일을 생성하고 멈춘다. 컴파일러 최적화가 실제로 어떤 기계어를 만들어내는지 확인할 때 쓴다.
- `gcc -c foo.c`: `.o` 오브젝트 파일을 생성하고 링크는 하지 않다. 여러 파일을 각각 컴파일만 해두고 나중에 한꺼번에 링크하는 증분 빌드의 기본 단위이다.

흔히 저지르는 실수는 `-E` 결과를 안 보고 매크로 버그를 코드만 눈으로 읽으며 추측하는 것이다. 매크로는 텍스트 치환이기 때문에, 실제로 치환된 최종 텍스트를 보지 않으면 괄호 하나 빠진 것 같은 문제를 놓치기 쉽다.

## 전처리기는 전처리 토큰을 처리한다

전처리기는 C의 타입이나 문법을 전혀 모른다. 전처리기가 다루는 최소 단위는 "전처리 토큰(preprocessing token)"이며, 이는 식별자, 숫자, 문자열 리터럴, 연산자, 구두점 정도로만 구분되는 텍스트 조각이다. 즉 `#define`으로 만든 매크로는 함수 호출이 아니라 순수한 문자열 치환이고, 이 사실을 잊으면 아래 서브섹션들에서 다루는 함정 대부분에 걸리게 된다.

### 객체형 매크로

```c
#define PI 3.14159
#define BUFFER_SIZE (1024)
```

가장 단순한 형태로, 이름을 특정 텍스트로 그대로 치환한다. 흔한 실수는 값에 괄호를 두르지 않는 것이다. `#define TWO 1+1`이라고 정의하면 `TWO * 3`은 `1+1 * 3`으로 치환되어 `4`가 되지, 기대했던 `6`이 되지 않는다. 상수 매크로는 값 전체를 괄호로 감싸는 것이 안전하다.

### 함수형 매크로

```c
#define SQUARE(x) ((x) * (x))
```

인자를 받는 것처럼 보이지만 실제로는 여전히 텍스트 치환이다. `SQUARE(x)`가 아니라 `SQUARE(a + b)`처럼 호출하면, 인자 `x`와 전체 식 양쪽 모두를 괄호로 감싸지 않은 매크로(`#define SQUARE(x) x * x`)는 `a + b * a + b`로 치환되어 값이 완전히 달라진다. 또 다른 함정은 부작용이 있는 인자이다. `SQUARE(i++)`는 `((i++) * (i++))`로 치환되어 `i`가 한 번이 아니라 두 번 증가하며, 이 부작용은 순서가 규정되지 않아 결과가 정의되지 않은 동작(undefined behavior)이다. 이런 이유로 함수형 매크로는 부작용이 있는 인자와 함께 쓰지 않는 것이 원칙이다.

### 여러 줄 매크로

한 줄이 넘는 매크로는 각 줄 끝에 백슬래시(`\`)를 붙여 이어간다.

```c
#define SWAP(a, b, T) \
    do { \
        T tmp = (a); \
        (a) = (b); \
        (b) = tmp; \
    } while (0)
```

`do { ... } while (0)`으로 감싸는 이유는 매크로 호출부가 세미콜론을 포함한 하나의 문장처럼 동작하게 만들기 위해서이다. 이 관용구 없이 그냥 `{ ... }`로만 감싸면, `if (cond) SWAP(a, b, int); else ...` 같은 코드에서 세미콜론이 중복되며 `else`가 엉뚱한 `if`에 붙는 컴파일 오류가 난다.

### 문자열화 연산자 `#`

```c
#define STR(x) #x
#define XSTR(x) STR(x)
#define VERSION 3

STR(VERSION)    // VERSION
XSTR(VERSION)   // 3
```

`#` 연산자는 매크로 인자를 그대로 문자열 리터럴로 바꾼다. `STR(VERSION)`은 `VERSION`을 먼저 확장하지 않고 바로 `"VERSION"`이 되어버린다. 인자를 먼저 확장한 뒤 문자열화하고 싶다면, 인자를 확장하는 매크로(`STR`)를 한 번 더 감싼 매크로(`XSTR`)를 거쳐야 한다. `XSTR(VERSION)`은 먼저 `VERSION`을 `3`으로 확장한 다음 `STR(3)`을 호출해 `"3"`이 된다. 이 두 단계 간접화는 C 전처리기의 표준적인 관용구이다.

### 미리 정의된 매크로

컴파일러가 자동으로 정의해주는 매크로들이다: `__FILE__`(현재 소스 파일명), `__LINE__`(현재 줄 번호), `__DATE__`/`__TIME__`(컴파일 시각), `__STDC__`(표준 C 컴파일러 여부). 주로 로그나 assert 매크로에서 위치 정보를 자동으로 남길 때 쓴다.

```c
#define LOG_HERE() printf("%s:%d\n", __FILE__, __LINE__)
```

### 가변 인자 매크로

```c
#define LOG(fmt, ...) printf(fmt, __VA_ARGS__)
```

가변 인자 매크로는 함수의 가변 인자(`...`)와 비슷하게 인자 개수를 고정하지 않는다. 흔히 겪는 문제는 가변 인자가 하나도 없을 때(`LOG("done")`)이다. `fmt` 뒤에 콤마가 남아 문법 오류가 난다. GNU 확장인 `##__VA_ARGS__`(`printf(fmt, ##__VA_ARGS__)`)를 쓰면 가변 인자가 비어 있을 때 그 앞의 콤마까지 함께 제거해준다. 표준 C에서는 이 문제를 C++20/C23에서 도입된 `__VA_OPT__`로 해결한다.

### 조건부 컴파일

```c
#if defined(_WIN32)
    #include <windows.h>
#elif defined(__linux__)
    #include <unistd.h>
#else
    #error "지원하지 않는 플랫폼"
#endif
```

`#ifdef`/`#ifndef`/`#if`/`#elif`/`#else`/`#endif`는 특정 조건에서만 코드를 컴파일에 포함시킨다. 플랫폼별 분기, 디버그 전용 코드(`#ifdef DEBUG`), 기능 플래그에 흔히 쓰인다. 조건부 컴파일된 코드는 조건이 거짓인 경로가 애초에 컴파일러 눈에 보이지 않으므로, 코드가 오래 방치되면 조건이 거짓이던 쪽이 조용히 깨져 있어도 알아채기 어렵다는 점을 유의해야 한다.

### Include guard

```c
#ifndef UTIL_H
#define UTIL_H

int add(int a, int b);

#endif // UTIL_H
```

같은 헤더가 한 번역 단위에 두 번 이상 `#include`되면(다른 헤더가 서로를 include하는 경우 흔함) 선언이 중복되어 컴파일 오류가 난다. Include guard는 헤더가 처음 include될 때 매크로를 정의해두고, 이후 재포함 시도에서는 `#ifndef`가 거짓이 되어 내용 전체를 건너뛰게 만든다. 사실상 모든 컴파일러가 지원하는 `#pragma once`가 더 짧지만 표준은 아니므로, 이식성을 중시하는 코드베이스는 여전히 include guard를 쓴다.

### 토큰 결합 연산자 `##`

```c
#define MAKE_GETTER(name) int get_##name(void) { return name##_value; }
MAKE_GETTER(width)
// → int get_width(void) { return width_value; }
```

`##`는 두 토큰을 하나로 붙여 새로운 토큰을 만든다. 매크로로 반복적인 이름의 함수나 변수를 찍어낼 때(getter/setter 생성, 고유 식별자 생성) 흔히 쓴다. `#`(문자열화)와 마찬가지로 `##`의 피연산자는 먼저 확장되지 않으므로, 인자를 먼저 확장하고 싶다면 여기서도 간접 매크로 한 겹이 필요하다.

## 번역 단위

번역 단위(translation unit)는 컴파일러가 한 번에 컴파일하는 최종 텍스트 전체를 말한다. `.c` 파일 하나에 그 파일이 재귀적으로 `#include`한 모든 헤더 내용이 전처리 단계에서 실제로 텍스트로 치환되어 들어간 결과물이다. 프로젝트에 `.c` 파일이 10개 있으면 번역 단위도 10개이고, 컴파일러는 이들을 서로 독립적으로 컴파일한다.

이 독립성이 왜 중요하냐면, 각 번역 단위를 따로 컴파일할 수 있어야 파일 하나만 수정했을 때 그 파일만 재컴파일하고 나머지 오브젝트 파일은 재사용하는 증분 빌드가 가능해지기 때문이다. 반대로, 번역 단위 하나 안에서만 알 수 있는 정보(예: 다른 파일에 정의된 함수의 존재)는 링크 단계가 되어야 비로소 확인된다. 그래서 다른 파일의 함수를 쓰려면 그 함수의 선언을 헤더로 가져와 컴파일러에게 미리 알려줘야 한다.

## 선언과 정의

선언(declaration)은 컴파일러에게 "이런 이름과 타입을 가진 무언가가 존재한다"고만 알려줄 뿐 실제 메모리를 할당하거나 코드를 생성하지 않는다. 정의(definition)는 실제로 저장 공간을 만들거나(변수) 함수 본문을 생성한다(함수).

```c
extern int counter;      // 선언: counter는 어딘가에 존재한다
int counter = 0;         // 정의: 여기에 저장 공간이 만들어진다

int add(int a, int b);   // 선언: 시그니처만 알림
int add(int a, int b) {  // 정의: 본문이 있으므로 정의
    return a + b;
}
```

같은 개체에 대한 선언은 여러 번역 단위에 걸쳐 여러 번 나타나도 되지만, 정의는 프로그램 전체에서 정확히 한 번만 존재해야 한다(One Definition Rule). 이 규칙을 어기면 링크 단계에서 "multiple definition" 오류가 난다. 헤더에 `int counter = 0;`처럼 정의를 그대로 적어놓고 그 헤더를 여러 `.c` 파일에서 include하면, 번역 단위마다 정의가 복제되어 바로 이 오류를 만나게 된다.

## 헤더 작성

헤더 파일은 원칙적으로 선언만 담아야 한다. 함수 원형, `extern` 변수 선언, 타입 정의(`struct`, `typedef`), 매크로. 여러 `.c` 파일이 같은 헤더를 include해도, 선언은 몇 번 반복돼도 괜찮기 때문에 안전하다.

정의를 헤더에 넣으면 안 되는 이유는 바로 위에서 다룬 One Definition Rule 때문이다. 예외는 `inline` 함수와 매크로이다. `inline` 함수는 각 번역 단위에 정의가 복제되어도 링커가 이를 하나로 병합하도록 표준에서 허용하고 있고, 매크로는애초에 링크 단계에 존재하지도 않는(전처리 단계에서 이미 사라지는) 순수 텍스트이기 때문이다.

## 내부 링키지

```c
// util.c
static int cache_hits = 0;      // 내부 링키지: 이 파일 밖에서는 보이지 않음
static void reset_cache(void) { cache_hits = 0; }
```

파일 스코프에서 `static` 키워드는 그 이름의 링키지를 내부(internal)로 제한한다. 같은 번역 단위 안에서는 자유롭게 쓸 수 있지만, 다른 `.c` 파일에서는 `extern`으로 아무리 선언해도 이 심볼을 찾을 수 없다. 오직 이 파일 내부에서만 쓰는 헬퍼 함수나 전역 상태를 `static`으로 표시해두면, 다른 파일이 같은 이름을 실수로 재사용해도 충돌이 나지 않고, 이 함수/변수가 외부에 노출되지 않다는 의도를 컴파일러 수준에서 강제할 수 있다.

## 스코프, 링키지, 저장 기간

C의 모든 식별자는 서로 독립적인 세 가지 속성을 동시에 가진다.

- **스코프(scope)**: 식별자 이름이 보이는 텍스트 범위. 블록 스코프(중괄호 안), 파일 스코프(번역 단위 전체), 함수 스코프(레이블), 함수 프로토타입 스코프(매개변수 이름).
- **링키지(linkage)**: 서로 다른 선언이 같은 개체를 가리키는지 결정하는 속성. 외부 링키지(전역 기본값, 프로그램 전체에서 하나), 내부 링키지(`static`, 번역 단위 안에서만), 링키지 없음(블록 스코프 지역 변수).
- **저장 기간(storage duration)**: 개체가 메모리에 실제로 살아있는 기간. 자동(automatic, 블록 진입~탈출), 정적(static, 프로그램 시작~종료), 동적 할당(allocated, `malloc`~`free`), 스레드(thread, C11부터 `_Thread_local`).

세 속성은 독립적이라는 점이 핵심이다. 예를 들어 함수 안의 `static int counter;`는 블록 스코프(함수 밖에서 이름이 안 보임) + 링키지 없음 + 정적 저장 기간(함수를 벗어나도 값이 유지됨)을 동시에 가지는, 흔히 헷갈리는 조합이다. 스코프만 보고 "지역 변수니까 함수가 끝나면 사라지겠지"라고 넘겨짚으면 이 조합에서 틀리다.

## 오브젝트 파일과 심볼 확인

```bash
nm main.o
```

```
0000000000000000 T main
                 U add
```

`nm`은 오브젝트 파일 안의 심볼 테이블을 보여준다. 대문자는 외부 링키지(다른 파일에서 참조 가능), 소문자는 내부 링키지를 뜻하며, 흔한 기호는 `T`/`t`(text, 코드), `D`/`d`(초기화된 전역 데이터), `B`/`b`(초기화되지 않은 전역 데이터, BSS), `U`(undefined, 이 파일에서 쓰지만 정의는 다른 곳에 있음을 뜻함)이다.

이 명령이 실전에서 유용한 이유는 "undefined reference" 링크 오류를 진단할 때이다. 어떤 함수가 `U`로 표시되어 있는데 링크에 포함시킨 다른 오브젝트 파일들 어디에도 그 이름이 `T`로 정의되어 있지 않다면, 오브젝트 파일을 빠뜨렸거나(링크 커맨드에 `.o`/라이브러리 누락), 이름이 미묘하게 다르거나(오타, 네임 맹글링이 관여하는 C++ 링크 상황), `static`으로 선언해 내부 링키지로 갇혀버린 심볼을 외부에서 참조하려 한 경우이다. 소스 코드를 보지 않고도 `nm`만으로 이 세 가지 원인을 좁혀나갈 수 있다.
